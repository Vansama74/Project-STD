## 2. CQ 故障屏开关改名对照（2026-08-24）

原实现为三段级联 + 反直觉命名（`CQ_FAULT_SCREEN_FORCE_ON` 输入 →
`CQ_FAULT_SCREEN_ENABLED` 输出），压平为单层中立宏 `CQ_FAULT_SCREEN`：

| 旧名 | 旧角色 | 新名/替代 | 备注 |
|---|---|---|---|
| `CQ_FAULT_SCREEN_FORCE_ON` | 构建入口显式覆盖输入 | `-DCQ_FAULT_SCREEN=1/0` | 已废弃，不保留兼容别名 |
| `CQ_FAULT_SCREEN_ENABLED` | 三段级联输出、代码使用点 | `CQ_FAULT_SCREEN` | 已废弃，不保留兼容别名 |

语义不变：默认值跟随构建口径（PROTO_CHONGQING → 1，其他 → 0），构建入口可
显式覆盖。使用点：`app_cq_proto.c` `cq_proto_timer_task` 的
`#if CQ_FAULT_SCREEN`（关闭分支：不计数、不渲染）。

## 4. 口径指纹 stamp 与重链接依赖（Makefile，2026-09-14 修复）

**缺陷**：elf 的依赖原本只有 `.o` 列表——源文件列表（`PROTO` 剔除 LDI 目录、`DISP`
替换模组文件）与编译开关（`DEFINES`/`CFLAGS`）不在依赖图上。切换口径后若 elf 时间
戳更新，`make` 会跳过重链接、**静默复用上一口径的 elf**（产物与命令行口径不符）；
历史上靠「先手工删除 `build/$(CONFIG)/Project_STD.*`」规避，且删产物并不重编对象，
仍会混入上一口径的 `.o`（见 §4.1）。

**实现**（`Makefile`）：

- 生成口径指纹 `build/$(CONFIG)/.build_stamp`，内容 = `STAMP_VERSION` + `CONFIG` /
  `TOOLCHAIN` / `PROTO` / `DISP` / `DEFINES` / `CFLAGS` / `LDFLAGS` /
  `MAKEFILE_CKSUM`（`cksum Makefile` 内容指纹）/ `SRC_FILES`（源列表）；
- 写入方式「先写 `.tmp` → `cmp` 比较 → 相同则丢弃、不同才 `mv`」：**内容变化才改写**
  （mtime 更新），内容相同不触碰文件 → 口径不变时增量构建照常（重复 `make` 零编译
  零链接，实测 0.1s）；
- `.build_stamp` 同时是**每个 `.o` 与 elf 的先决条件**：口径变化 → 全部 `.o` 重编译
  + elf 重链接（杜绝旧口径对象参与新口径链接），`hex`/`bin` 经 elf 联动；
- `MAKEFILE_CKSUM` 使**未来新增开关**（即使不流入 `CFLAGS`）只要改动 Makefile 就触发
  一次全量重建——新开关无需额外接线；
- 另加 `-MMD -MP` 头文件依赖（`.d` 与 `.o` 同目录，`-include $(DEP_ALL)` 引入）：
  头文件改动触发依赖它的 TU 重编译（实测 `touch app_scroll.h` → 4 个 TU 重编译 +
  重链接，第二次 `make` 零动作）；
- `.DEFAULT_GOAL := all`：stamp 规则位于 `all` 之前，若不加显式默认目标会劫持无参数
  `make`（只跑 stamp、不产 elf）。

**使用纪律（变更）**：切口径**不再需要手工删产物**；同一口径可安全重复 `make`。
`make clean` 仍删除整个 `build/$(CONFIG)`（含 stamp、`.d`）——并**连带删除 EIDE 在同
目录的构建产物**（既有行为，非本次引入）。

### 4.1 该缺陷造成的既有采样偏差（已更正）

2026-09-14 那轮四口径采样中，`PROTO=ALL` 两行是「删 elf 后 `make`、对象沿用上一
CQ 口径」的**污染态**：混入 CQ 口径对象后，`app_cq_proto.o` 的 `CQ_FAULT_SCREEN=1`
引用链把 `cq_render_fault_screen`（316B，位于 `app_cq_proto_cmd.o`）+ 两条故障屏文案
（rodata 30B）+ `app_factory_test_active`（12B）经 `--gc-sections` 保留下来，另
`cq_proto_timer_task` +56、`_udp_cq_read_port` +28（符号合计 +442 → 段面 **+416 text /
+40 rodata**）。**RAM 段（data/bss/ccmram）不受影响**，故 SRAM/CCM 账目不变。同期
两口径「改动前基线」用 `make -B`（全量重编）采样，本身干净，本轮已用干净重采逐项
复现。更正后数字见 `doc/06_SRAM内部分数据迁移/04_current_memory_occupancy.md` §7。

### 4.2 构建卫生纪律（2026-09-14 补，R1/R2/R3）

stamp 保证「切口径必然重编 + 重链接」，但**不覆盖「同一口径下共享产物被外部构建器覆写」**；
以下三条为互补纪律（实证见 `.analysis/9k23881580/stamp_verify_report.md`、
`gz_ol_udp_binding_report.md` §1-2 及本轮复核）。

**R1｜EIDE 构建覆写 `build/Debug/` 共享产物后，`make` 会静默复用 EIDE 的 elf（必须 `make clean && make`）**

- 事实：EIDE Debug 与 make **共用 `build/Debug/`**（同名 `Project_STD.elf/.hex/.bin`）。
  EIDE 构建以**更新的 mtime** 覆写这三个产物；此后若命令行口径与上一次 make 相同
  （stamp 内容不变 → `cmp` 相同 → 不触碰 stamp、mtime 不更新），`make -j8` 判定
  「elf 比全部 `.o` 与 stamp 新」→ **0 编译 0 链接**，**静默保留 EIDE 的错口径 elf**。
  **口径指纹只跟踪口径内容，无法感知「elf 被同口径产物覆写」这一 mtime-only 事件。**
  实证：2026-09-14 15:33 EIDE 产物曾落在 `build/Debug/`（同目录含 `.obj/`、`.lnp`、
  `builder.params` 等 EIDE 独有产物；其 `.ccmram` 与 make 四口径任一值均不符）。
  机理复核（本轮）：`touch build/Debug/Project_STD.elf && make -j8` → 仅补跑 objcopy
  （hex/bin 落后于被 touch 的 elf），**不重链接**、elf md5 不变。
- **⚠ 2026-09-17 晚 补充观测（口径可以不同也照样复用）**：EIDE 在 21:25 构建完成（CQ 口径 +
  `DISP=22_1665`，`.text=136904 .rodata=110768 .ccmram=19724`）后，紧接着的 `make -j8`（默认口径
  `ALL`/`1_263`）**同样 0 编译 0 链接**，其打印的 size 即 EIDE 产物尺寸——即 **EIDE 产物只要
  mtime 新于 stamp，即使口径与 make 当前口径完全不同，`make -j8` 也不会重链接**（stamp 规则
  只比 mtime，不比「elf 是哪套口径产出的」）。`make clean && make` 后恢复 make 口径
  （实测 `.text=174996 .rodata=204848 .data=1680 .ccmram=38332 .bss=124772 ._user_heap_stack=2564`）。
  ⇒ 纪律不变且更强：**EIDE 构建后必须 `make clean && make`**（或给 EIDE 配独立输出目录），
  否则「make 成功」不能证明 `build/Debug` 里是 make 口径的产物。
- 纪律：**EIDE 构建之后必须 `make clean && make`**（或给 EIDE 配独立输出目录）；
  重复 `make` 的「0 编译 0 链接 + md5 不变」**仅当最后一次构建确为 make 时**才可作为
  产物新鲜度的证据。
- 烧录前核对（`arm-none-eabi-size -A build/Debug/Project_STD.elf`；默认口径 GCC Debug
  `PROTO=ALL` `DISP=1_263`，**含默认开启的 `APP_DIAG_BANNER`**）：`.text=170596  .rodata=201736
  .data=1672  .ccmram=11164  .bss=126436  ._user_heap_stack=2564`（2026-09-17 云南治超裁决轮口径；
  权威值见 doc/06-04 修订段「2026-09-17」条，以该处为准）；

**R2｜`make -n` 干跑显示「全量过期」属预期现象**
