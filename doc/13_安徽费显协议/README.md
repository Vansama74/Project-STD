## 1. 协议事实（12 命令）

帧格式：`5A`(起始) + 屏号(1B，本设备 01) + 命令(1B) + 数据长(1B 二进制) + 数据(变长) + CRC(1B) + `A5`(结束符)。帧总长 = 数据长 + 6，数据长 1 字节上限 255 → 整帧 ≤ 261。**CRC 字段协议文档注明「无检验，默认为 0」→ 不校验**。传输：串口（RS232/RS485），协议文档未指定波特率 → 沿用 DIP1 统一选择（9600/115200，8N1）。文本编码：协议标注 ANSI（中文 Windows 语境即 GBK），渲染 `FONT_ENC_GBK` 直通。

### 1.1 动态显示权威文档核对（2026-09-08）

以用户提供的权威协议文档 `2026-S304 费显通信协议.doc`（2026-09-04 修订版，3 页）核对动态显示接线。文档第 8/9 节原文要点：

- 第 8 节「动态显示」帧例：`5A 01 86 08 01 04 00 10 41 B0 A1 30 00 A5`
  —— 数据长 08 = 运动模式(01) + 速度(04，×2MS=8ms) + 停留时间(00 10，×100MS=16×100ms=1.6s) + 文本区(41 B0 A1 30，ANSI 4B)；
  「命令 86 第一行，87 第二行，88 第三行，89 第四行，依次类推，**数据长度:运动模式至文本区**」。
- 第 9 节「运态停止」：`5A 01 86 04 00 00 00 00 00 A5`（数据长 4、四字节全 0），命令 86~89 同样对应第 1~4 行。
- 第 7 节静态显示附带行首约束：四行行首 Y = 00/10/20/30（16 点阵行高）。**2026-09-09 裁决动态与静态显示均改 FONT_24**；16 点阵口径仅为协议文档原文。**2026-09-15 终裁（静态侧，§1.2）**：0x85 坐标直用像素、X 在前（x=data[0]、y=data[1]），固件不做行号换算——上位机按文档发 00/10/20/30 时固件就在像素 y=0/16/32/48 处起显；同日的「行号映射 row=Y/16→row×24」与「字节对调（y=data[0]）」两轮中间口径均已撤销（RTT 实测四帧同字节证伪行号假说，§1.2）。**动态侧 `row×24` 维持不变（§8 #13 待上位机联调最终确认）**。

**核对结论**：实现与文档一致的项——速度 1B ×2ms、停留时间 2B ×100ms 大端、停止帧格式、86~89 行号映射。**2026-09-09 裁决**：字号 FONT_16→FONT_24，行区域 Y=row×24/h=24（00/18/30/48，按字号推导的假设待联调）、停止帧=冻结不清行（app_scroll_stop 语义）。**文档未定义的项**（保持现状并标注待联调）——运动模式取值含义（仅示例值 01，无取值表）、停留行为（循环滚动中「停留」做什么）、速度范围、文本长度上限、颜色、字号（**字号已由用户裁决 FONT_24**，其余仍待）。

应答：**协议文档未定义任何应答 → 单向不回**（对齐青海单向模式）。

### 1.2 0x85 静态显示坐标语义——2026-09-15 终裁（坐标直用像素、X 在前）

**协议文档原文（2026-S304 第 7 节，libreoffice 提取）**：

```
起始  屏号  命令  数据长度  （X、Y）   文本区（ANSI码）            CRC   结束符
 5a   01   85    0b       00 10    b0 a1 30 f7 fe 41 a1 e6  00    a5
数据长度= 行、列至文本长度。
X – 横坐标    Y - 纵坐标
坐标以左上角起点为0点，横向为X坐标，纵向为Y坐标。
费显需支持四行，第一行第一列：X,Y=00，00；第二行第一列：X,Y=00,10；
第三行第一列：X,Y=00，20；第四行第一列：X,Y=00，30。
```

文档自身矛盾（表头「（X、Y）」X 在前 vs 数据长度公式「**行、列**」行在前）＋两次实测症状，曾于 2026-09-15 当天催生两轮中间口径——**均已被终裁撤销**（历史推演细节见 git/会话记录，此处仅留口径表）：

| 轮次 | 口径 | 状态 |
| --- | --- | --- |
| 第一轮 | 「行号换算」：`row=Y/16 → pixel_y=row×24`（00/10/20/30 → 0/24/48/72，对齐动态行 row×24） | **已撤销** |
| 第二轮 | 「字节对调」：`y=data[0]`（行）、`x=data[1]`（列）——双症状推演认为行字节在第 1 字节 | **已撤销** |
| **终裁（2026-09-15 上午，最新，取代此前所有 0x85 坐标口径）** | **x=data[0]、y=data[1]，均直接作为像素坐标渲染** | **现行** |

**终裁内容（用户两条裁决）**：

1. 坐标字段 `x=data[0]`、`y=data[1]`——X 在前，与文档表头「（X、Y）」一致、与 0x82/0x83 点命令完全同构；
2. **坐标直接作为像素值渲染**：显示位置是 (0,16) 就从 (0,16) 开始显示，**不允许**固件自动换算跳到 (0,0) 或 (0,24)。

**RTT 实测证据（2026-09-15，终裁的直接动因）**——上位机发送「第一/二/三/四行」静态显示四帧，RTT 帧级诊断输出逐字节**完全相同**：

```
[anhui] 0x85 b0=00 b1=00 -> x=0 y=0 row=0 py=0 len=1 t=31 00 00 00
```

（该行为撤销前（第二轮）的诊断格式，`row/py` 字段即被撤销的换算输出；`b0/b1` 为数据区前两字节原始序、`t` 为文本前 4 字节。）

**判读**：

- 四帧坐标均为 **(0,0)**、文本仅 1 字节 `0x31`('1')——**行号信息不在数据区坐标字节里**（data[0]/data[1] 两字节恒 00），第二轮「行字节在第 1 字节」假说被实测证伪；前两轮的「双症状推演」亦不再成立——症状根源是当时台上固件口径与屏几何的组合，不是字节序；
- 四帧同内容 → 全部渲染在 (0,0) 是该帧语义下的**正确行为**（固件忠实执行帧内容）；
- **上位机侧待确认**：若意图分行，上位机需在 Y 字节真实发送 00/10/20/30（即像素 y=0/16/32/48）——届时屏幕必须从对应像素行起显示，诊断行 `b1=10/20/30` 即实证；亦不排除行帧走上位机其他通道（本次四帧均经当前测试通道收到，未见分流）；
- 日志中夹着的 `tcp_connect to port 9529` SYN_SENT 失败重连是**当时镜像**本机 TCP Client 的 lwIP 调试输出（旧默认远端 192.168.2.17:9529），**与 0x85 测试无关**（核实结论见 §9）。**现行（2026-09-18）**：通道默认 `0.0.0.0:0`，未配置不连，不再对 9529 自动 SYN。

**诊断打印保留**（后续联调判据）：`app_anhui_proto_cmd.c` `ANHUI_RTT_DIAG`（默认跟随 `APP_DIAG_BANNER`，可单独覆盖 0/1）在 0x85 执行入口每帧打印

```
[anhui] 0x85 b0=xx b1=xx -> x=u y=u len=u t=xx xx xx xx
```

（b0/b1 = 数据区前两字节**原始序**，与 x/y 直用值一致；t = 文本前 4 字节。）下次实测若上位机真发 (0,16)：屏幕必须从 y=16 起显示、诊断行 `b1=10` 即实证。

**0x82/0x83 未随动**：文档明写「x(最大值128),y最大值(64)」为 X 前 Y 后，本来就是直用像素，无变化；本轮亦未对其加诊断打印。

## 3. 模块设计与接入点

- 目录/命名：`ProtocolParser_Anhui/`，前缀 `app_anhui_proto_`（`ah_` 前缀被 AH_MQTT 占用，doc/08 命名规则下用 `anhui`）；文件拆分与青海/贵州同构（proto / proto_parse / proto_cmd / proto_voice）。
- 注册五步：`RB_PROVIDE_WEAK`（RS485+RS232 同槽 weak 合并）→ `app_proto_acquire_buf` → `app_proto_register`（双通道各独立 mask）→ `app_proto_bind_channel`（CH_ID_RS485 + CH_ID_RS232）→ `app_proto_set_frame_queue`；`sw_app_initcall(anhui_proto_init)`。
- probe：**长度字段定界**（对齐治超 5.3 模式）——首字节 0x5A 快拒 → 命令字预筛（提前 FAKE 掉 5A 噪声流，避免大长度字段把链式探测拖死在 WAIT）→ 数据长算整帧 → 尾字节 0xA5 校验 → READY；屏号非 01 → SKIP 整帧消费。CRC 不校验（文档注明无检验）。PURE 契约（仅 rb_peek，仅 READY/SKIP 写 `*total_len`）。
- 队列：`ANHUI_PAYLOAD_MAX 261`（数据长 1B 上限 255 → 6+255）、`ANHUI_QUEUE_DEPTH 3`；`_Static_assert` ≤ RB 768。**队列体+控制块+任务帧缓冲为静态 SRAM（与青海/贵州/云南等协议模块一致，CQ 才是 CCMRAM 例外）**（§6、doc/06-04 记账）。
- 处理任务：`anhui_handle_task` 栈 256×4；帧缓冲 static（SRAM，不入栈）；parse 纯函数 → `anhui_execute_cmd` 查表分派。
- 应答：无（协议未定义）。
- 波特率：无协议改波特率命令，沿用 DIP1（9600/115200）全局选择。



## 4. 帧头冲突纪律

- 安徽帧头 `0x5A` 在 RS485/RS232 槽**唯一**：既有串口协议首字节为 `0x7B`（青海/山东/贵州/云南/四川MTC）/ `0x0A`（四川ETC）/ `0xFF`（四川治超/RLS），首字节互斥快拒成立，**无需 EIDE 目录排除**。
- IAP 的 `0x5A5A5A5A` 仅绑定 UDP（RJ45 槽），与串口槽不相交，无冲突。
- 安徽为 5A/A5 帧族，**非** `{` **帧族 → 不定义** `g_brace_proto_guard`；与青海/山东/贵州/云南/四川MTC 可同编共存（probe 注册序无关紧要，帧头互斥）。
