# 显示系统驱动手册
> 当前态权威（合并自 12 个过程记录，2026-11-27）；历史流水见 doc/00_变更历史.md

## 1 总览

### 1.1 显示架构

- **分层**：协议/渲染（`Application/`）→ 设备基类 `dev_display_t` + 虚表 `dev_display_ops_t`（`Device/Display/dev_display.c/.h`）→ 各模组派生驱动（`Device/Display/dev_display_*.c`）→ HUB75 平台原语（`Platform/` 下 `pl_hub75_*`）。
- **注册**：派生驱动由 `hw_dev_initcall` 在 RTOS 启动前执行 `dev_display_init()`（绑定 `prepare`/`scan`/`set_row` 虚表 + 预计算查表 + `dev_display_register()`）。
- **双缓冲**：
  - `pixel_map`：逻辑帧缓冲，行优先，1B/像素，颜色索引 0..7（黑红绿黄蓝紫青白）；
  - `hub75_buff`：扫描输出缓冲，按「通道 × 扫描行」组织，布局随模组而异。
  - `prepare()` 负责逻辑像素 → 硬件扫描缓冲的重排（复杂映射全部在此）；`scan()` 只顺序消费 `hub75_buff` 输出 HUB75 时序（只读缓存、只写 GPIO）；`set_row()` 与模组行驱动芯片类型严格匹配。`pixel_map` 与 `hub75_buff` 是两层语义，不能混用。
- **BSRR 查表**：各驱动把「颜色索引 → 该通道 R/G/B 引脚 BSRR 值」预计算成 `g_bsrr` 查表（放 CCMRAM，零等待、避免 Flash 读与分支），`scan()` 热路径逐像素查表合并写 GPIO 端口。
- **脏矩形（④a）**：`dev_display_commit_frame_rect(dev, x, y, w, h)` 与全屏 `dev_display_commit_frame` 并列；未消费前多次提交自动合并包围盒（osKernelLock 保护，矩形钳位、空矩形不提交）。scan_task 消费时经基类 `dirty_rect_x/y/w/h + dirty_rect_valid` 字段传给 `ops->prepare`（虚表签名不变）；prepare 只重排矩形覆盖的逻辑行（prepare 按整行拷贝，行内 x 范围不影响布局）；矩形无效/越界 → 保守回退全量。收益：每步全屏 prepare（量产口径 ±30~50% 亮度抖）→ 只重排滚动行带。
- **渲染互斥（⑤）**：`app_scroll_render_lock/unlock`（`s_render_mutex`）串行「滚动渲染」与「静态渲染」；锁序 render → slot 单向，无死锁（见 §9）。

### 1.2 扫描机制与行同步

- **scan_task**（基类 `dev_display.c`）：Realtime 优先级，启动期创建一次、永不退出；静态化（栈 256，CCM 1124B，不再占 ucHeap）。
- **TIM3 行同步 + 二值信号量 ISR 直投**：TIM3 行事件在 ISR 中 `osSemaphoreRelease(s_scan_sem)` —— 二值信号量在 ISR 走 `xSemaphoreGiveFromISR` 直接唤醒 scan_task，不经任何守护任务。**不能用事件组**：`osEventFlagsSet` 在 ISR 走 `xEventGroupSetBitsFromISR` → 经 FreeRTOS Timer 守护任务（优先级 25）中转，行同步洪流会让守护任务常驻就绪、饿死全部 Normal(24)/EthLink(16) 任务（网络、LDI 全灭，2026-11-24 定级；见 `Device/Display/dev_display.c:24-30`）。
- **TIM3 行周期**：现行 **1.5ms/行**（Prescaler 84-1、Period 1500-1，≈666Hz 行频，8 扫 → ≈83Hz 帧；`Core/Src/tim.c:82-93`，2026-11-24 定级）。原 500µs（2kHz）低于扫描任务单行耗时（384px × 8 通道 × 3 次 GPIO 写 ≈0.9ms）→ scan_task 持续追赶行事件、CPU 逼近 100%、饿死网络/LDI 任务（2026-11-24 网口失联根因）。调整本值须同步评估：刷新率 / 亮度 / 低优先级任务余量。**各模组记录中按 500µs 周期给出的 CPU 占比估算是旧口径，用现行 1.5ms 重算**。
- **TIM4 亮度 PWM**：8 档（`DEV_DISPLAY_BRIGHTNESS_MAX = 8`）；静态扫描模组（22-1665）全额占空。
- **LAT/OE 窗口**：由基类 scan_task 统一处理（锁内核 + 关 TIM4 → OE 置位 → set_row → LAT 脉冲），派生驱动不参与。

### 1.4 关键机制汇总

- **自适应字号**：`FONT_SELF_ADAPT` 由渲染层统一解释（从大到小选最大可容纳字号，无可用回退 `FONT_16`），见 §10。
- **动态滚动**：`app_scroll` 循环滚动引擎（4 槽、2ms 节拍、④a 并集提交、⑤ 渲染互斥、stop=冻结/stop_all=清行），见 §9。
- **TIM3 行同步 + 二值信号量 ISR 直投**：见 §1.2（行周期 1.5ms，2026-11-24 定级）。
- **脏矩形 ④a / 渲染互斥 ⑤**：见 §1.1。
- **prepare/scan 职责分离 + BSRR 查表 + 表驱动**：所有可预计算内容（行基址 `row_dst`、合并写表、落点表）在 init 期算好放 CCMRAM，热路径零计算。
- **dirty_rect 兼容性**：1-263 / 1-969 / 1-543 / 22-1703 的 prepare 均支持行子集重排；22-1665 的 prepare 只用脏矩形判「有无变化」，每次提交整帧重算。

## 2 模组 1-260

### 驱动要点

- 32×32 单模块；HUB75 2 通道（R1G1B1 + R2G2B2）；1/8 扫描；每扫描线每通道 64 时钟。
- 行驱动 **SM5266PH = 移位寄存器型**（不是译码器）：`_1_260_set_row()` 走 `pl_hub75_ShiftRegister_set_row(row, 1)`（`Device/Display/dev_display_1_260.c:150-153`）。正确时序：C 置高进入移位模式 → 8 次移位 → C 置低锁存。
- 当前宏 `_1_260_MODULE_ROWS/COLS = 7/2` → 224×64。

### 已知坑

- **沿用译码器型行选逻辑 → 每帧同时点亮多个像素**：原行选时序按 P5 模组 RUC7258（译码器型，ABC 直接选行）实现，与 SM5266PH 移位寄存器工作方式不匹配。点序测试 `app_test_led_mapping` 每帧多点亮起即此症状。

### 契约

- `set_row()` 的实现必须与硬件芯片类型严格匹配（移位寄存器型 = 移位+锁存；译码器型 = ABC 直通）。
- 点序测试（`app_test_led_mapping`）是验证行驱动正确性的有效手段，修行驱动后必跑。

## 3 模组 1-263

### 驱动要点

- P6 户外全彩 32×32（模块码 1000000263）；1/8 扫描（每扫描线点亮 4 物理行）；HUB75 2 通道；行驱动 16206S（译码器型，A/B/C 直通二进制行址，兼容 1-577 时序）；列驱动 2013EP（16 通道恒流，每数据线 4 颗串联 = 4×16 = 64 通道）。
- **移位链长**：每扫描线每通道 **64 bit = 64 时钟**；6 数据线 × 64 = 384 bit = 4 行 × 32 列 × RGB，逐位对应、无空位。
- **hub75_buff 布局**（单模块直排）：`ch0: line0[64]..line7[64]`（pos 0-511）、`ch1:`（pos 512-1023）；每条 scan line 64 字节 = `[0..31]` Y_high X=0..31、`[32..63]` Y_low X=0..31。行映射：ch0 = 行 L / L+8，ch1 = 行 L+16 / L+24。
- **row_dst**：`row_dst[y] = ch*512 + line*64 + row_type*32`（row_type：1=low → +32，0=high → +0）；init 期预计算入 CCMRAM（`Device/Display/dev_display_1_263.c:80`）。
- **prepare**：32 列整行直排（每行 `memcpy` 32B 到 `row_dst` 指定半区）；支持 dirty_rect 行子集（`dev_display_1_263.c:130-136`）。**scan**：每扫描线 64 时钟循环，BSRR 查表输出。**set_row**：`pl_hub75_Decoder_set_row`（16206S 译码器型）。
- 派生参数：`MODULE_PIXEL_ROW=32`、`SCAN_LINE_PX=64`、`CHANNEL_PIXELS=512`、`BUFFER_SIZE=1024`（CCMRAM×2 双缓冲）。
- 当前宏 1×1 = 32×32（2026-09-14 记录的工作区实态为 7×2 = 224×64，CCM 29568B；两态切换只改 `MODULE_ROWS/COLS`）。

### 已知坑

- **「必须保持 64」是假象**：旧版照抄 1-577 的 64 宽左右半区布局（`SCAN_LINE_PX=128`，每扫描线发 128 时钟），但本模组移位链只有 64 bit → 前 64 时钟被移出链尾丢弃，模组实际保留后 64 bit = 64 宽虚拟画布的**右半**（X=32..63）；右半数据落入 [高行 32][低行 32] 链段、行结构完全正确、字形完整 → 看起来「显示正常」，实为**只显示右半幅**。随后 PIXEL_ROW 改 32 时又沿用 1-577 左右半区 prepare（半宽 16、低行偏移 16 应为 32）→ 显示残缺，反过来强化「必须保持 64」的错觉。
- **CHANNEL_PIXELS 必须除 `CHANNELS_PER_MODULE`（=2）而不是 `TOTAL_CHANNELS`**：误按 8 除得 448 → 整屏映射全错（22-1703 同款陷阱，见 §8）。
- 多模块扩展：`MODULE_ROWS=2` 时 `SCAN_LINE_PX` 自动推导为 128，输出位流 = [左模组高 32][左模组低 32][右模组高 32][右模组低 32]，与旧版 64 布局一致。

### 契约

- 每扫描线每通道时钟数 = 移位链长（64）；每数据线列驱动颗数 = 链长 / 16 = 4。
- 待实机确认：物理屏宽（1 张还是 2 张级联）、示波器链长（R1 对 CLK 计数每扫描线 64 时钟；若 128 = 2 段级联）、全幅显示、行组顺序（若上下 8 行组高低互换，交换 row_dst 中 row_type 偏移 0/32 的语义即可）。

## 4 模组 1-543

### 驱动要点

- P5-8S 320×160mm，64×32，5mm 点距，1/8 扫描，HUB75 2 通道；列驱动 **ICN2037BP**（16 通道恒流，每数据线 8 颗级联 = 每扫描线每线 128 bit）；行驱动 **URC7258D**（8 路行扫描/消隐，3 位行址 ABC，D 恒 0）。
- **与 1-577 的关系**：几何、扫描方式、通道数完全相同；差异**只在链段（16 bit = 1 颗列驱动）到物理区块的排列**。
- **链段表 `_1_543_chain_seg[8]`（as-built，2026-11-10 实机确认）**：数组下标 = 链上顺序，第 0 段最先移入 → 落在链尾：

  ```c
  static const _1_543_seg_t _1_543_chain_seg[8] = {
      {1, 0}, {1, 1}, {1, 2}, {1, 3},   /* 链首 4 段：高行带 X 0..63 */
      {0, 0}, {0, 1}, {0, 2}, {0, 3},   /* 链尾 4 段：低行带 X 0..63 */
  };
  ```

  即「高行带整行 → 低行带整行」。该表是**单一真源**：`_1_543_seg_idx[行带][列块]` 在 `dev_display_1_543_init` 中由表反查生成，`prepare` 只用 `seg_idx`。
- **派生参数**：`SCAN_LINE_PX = 128 × MODULE_ROWS`；`SEGS_PER_MODULE = 8`（每扫描线每模块 8 段 = 128 bit）；`MODULE_BUFF_STRIDE = 128`。改 `_1_543_MODULE_ROWS/COLS` 即切拼屏几何，派生量自动跟随。
- **prepare**：每行 4 个 16 列块各 `memcpy` 16B 到 `seg_idx[行带][列块]` 指定的链段；支持 dirty_rect 行子集。**scan**：每扫描线每模块 128 时钟，BSRR 查表输出 6 数据脚，与 1-577 完全一致。**set_row**：`pl_hub75_Decoder_set_row`（ABC 直通，D 恒 0）。
- **内存**：1×1 = 双缓冲 CCM 4096B + `g_bsrr` 384B + `row_base` 64B + `seg_idx` 8B；当前宏 3×3 = 192×96：CCM 36864B、`g_bsrr` 1152B、`row_base` 192B（三者放普通 SRAM，CPU 独占访问、无 DMA 需求）。
- **对象段尺寸实测**：1×1：`scan` 160B / `prepare` 172B / `init` 476B；3×3：`scan` 160B（与几何无关）/ `prepare` 208B / `init` 360B。单文件 `-Wall -Wextra` 0 告警。

### 已知坑

- **用 1-577 的链段表点本模组 → 整屏碎成 8 块**：1-577 的链段序是「左右半区蛇形」（以 32 列为单位分组），用其表点按「行带整行推进」走线的 1-543，会有 4~8 个 16×8 区块落到错误位置（候选 D，已知不符）。
- **判读方法（一次观察即可定表）**：`_1_543_chain_seg[k]` 的含义是「链段 k 显示逻辑区块 (band, col)」；实机上每物理区块显示的是逻辑哪一块的内容，就把该逻辑区块填到对应段号（观察：段 k 的内容出现在物理区块 P(k) → 令 `chain_seg[k] = P(k)`）。只验证行带是否互换 = 把表前 4 项与后 4 项对调。
- 候选排列裁决：A（现行默认）实机正确；B（低行带整行 → 高行带整行）否证（若为 B 则 A 下整屏上下错 8 行）；C（16 列块列优先）否证（若为 C 则 A 下每 16 列交替错带）。

### 契约

- 8 段必须把「2 行带 × 4 列块」各覆盖一次——重复项会让某个 16×8 区块永不刷新、另一区块被写两遍。
- 接缝形态 = 方块（16 列 × 8 行）；行分组 = `{L, L+8, L+16, L+24}`；R1G1B1 = 上半 16 行、R2G2B2 = 下半 16 行（三者由实机画面正常同时证得）。
- 未验证：多模块拼屏几何（当前 3×3；3×4 未上机）、D（行址 bit3）的消隐语义（1/8 扫不需要 D，出现半屏/全黑再查）。
- EIDE 收录（2026-11-10）：Debug 编入本驱动；`Base` 未排除本文件（与「Base = 基线不含显示驱动」不符），待 GUI 勾选 + Reload。

## 5 模组 1-577

### 驱动要点

- P5-8S 320×160mm，64×32，1/8 扫描，HUB75 2 通道；行驱动 **RUC7258E（译码器型）**，ABC 三线直通选行（无需 CLK+DATA+LAT）；列驱动 ICN2037。
- **hub75_buff 布局**（1×1 口径）：`ch0: line0[128]..line7[128]`（pos 0-1023）、`ch1:`（pos 1024-2047）。每条 scan line 128 字节内部排列（由 `app_test_led_mapping` 实测确认）：

  ```
  [0..31]   = Y_high, X=0..31
  [32..63]  = Y_low,  X=0..31
  [64..95]  = Y_high, X=32..63
  [96..127] = Y_low,  X=32..63
  ```

- **prepare 坐标变换**：`ch = y>>4`；`local_y = y&0x0F`；`line = local_y&7`；`row_type = (local_y<8)?1:0`；`base = ch*1024 + line*128 + row_type*32`；左右半拼接（左半 → base+0..31，右半 → base+64..95）。行映射：ch0 = L / L+8，ch1 = L+16 / L+24。
- **scan**：每扫描线 128 时钟，每时钟 ch0/ch1 各取 1 字节颜色索引查 `g_bsrr` 输出 6 个 GPIO（`pl_hub75_bsrr_flush` + `pl_hub75_clock_pulse`）。
- **g_bsrr**：`TOTAL_CHANNELS × 8 × sizeof(_1_577_bsrr_t)` = 2×8×12 = 192B，CCMRAM。
- **init**：`dev_display_1_577_init()` 由 `hw_dev_initcall` 在 RTOS 启动前执行：绑定 ops 虚表 → `dev_display_register()` → 预计算 `g_bsrr`（2 通道 × 8 颜色 × RGB = 48 个 BSRR 值）。
- 验证：`app_test_led_mapping`（scan 链路）、`app_test_prepare_mapping`（prepare 链路）、`app_test_pixel_scan`（全链路）、`app_test_render_text`（渲染链路）全部通过。

### 已知坑

- **译码器 vs 移位寄存器**：RUC7258E 的 set_row 与 1-260 的 SM5266PH 完全不同（ABC 直通 vs 移位+锁存），两者代码不可互换（对照表见 §1.3）。
- **prepare 复杂度**：左右半拼接（base 与 base+64 两段拷贝），与 1-260 线性拷贝、1-263 整行直排不同——照抄其它模组 prepare 会错位。

### 契约

- 每扫描线每通道 128 时钟 = 8 颗列驱动 × 16 通道；`CHANNEL_PIXELS = 64×32×MODULE_ROWS/2 = 1024×MODULE_ROWS`。

## 6 模组 1-969

### 驱动要点

- 料号 1000000969（兼容 1000001031）；单模块 64×32；1/8 扫描；2 通道/模块（3 列 = 总 6 通道）；R/G/B 分离；当前宏 3×3 = 192×96（`_1_969_SCREEN_COLS = 96` 行）。
- **hub75_buff 以「组」为单位**：16B/组 = 4×4 像素块；组内行偏移基准 `{0, 1, 9, 8}`（行 0/1 镜像、行 2/3 正序交错，由 HUB75 驱动芯片数据输入格式决定）。
- **表驱动结构（现行）**：`g_bsrr[TOTAL_CHANNELS][8]`（CCMRAM 查表）+ `row_dst[SCREEN_COLS]`（合并行基址表，init 预计算入 CCMRAM）；`prepare` 承担全部映射重排，`scan` 只读缓存、只写 GPIO（局部参数缓存 + 指针步进 + 通道展开）。
- **热路径原则**（闪烁优化的沉淀结论）：
  1. `scan()` 必须尽量做到只读缓存、只写 GPIO；
  2. `prepare()` 承担所有复杂映射与重排；
  3. 所有可预计算内容表驱动化；
  4. 对外显示语义不能改变，允许内部缓存布局重构。

### 已知坑

- **低优化等级（-O0）下闪烁**：prepare/scan 热路径中大量运行时计算、重复索引和分支 → 刷新节拍抖动、亮度 PWM 与扫描窗口耦合 → 肉眼可见闪烁；`-O3` 明显优于 `-O0`。**单调调 TIM3/TIM4 周期不能根治**——根因是热路径本身。
- 模组内部映射规则不能放进 `scan()` 热路径；任何可预计算内容留在热路径里都是闪烁放大器。

### 契约

- 表驱动结构保留；继续提速优先从 `scan()` 的循环展开与访问模式入手。
- 支持 dirty_rect 行子集重排（与 1-263 同口径；矩形无效走全量保守回退）。

- **颜色语义**：蓝 4 / 紫 5 / 青 6 / 白 7 → **红+绿都亮**（双色屏无蓝 die 的「非黑即亮」策略，现场已验证）；黄 = 红+绿。策略固化在 `_22_1665_role_bit[2][8]` 唯一一张表（开关 `_22_1665_BLUE_AS_LIT` 已删）。
- **行为开关仅剩 1 个**：`_22_1665_CHAIN_HEAD_IS_MODULE0`（`#ifndef` 守卫、可 `-D`；0 = 链首装组内最后一块（行尾 mx=ROWS-1）；1 = 组内第一块；`ROWS=1` 无影响）。已删除的化石开关 `HUB_WIRING`/`BLUE_AS_LIT`/`DATA_ACTIVE_HIGH` 对现行驱动 `-D` 完全无效。
- **CCMRAM 通式（模型 B）**：`1408×M + 256×COLS`（chain_dst 1024M + pixel_map 256M + frame_state 128M + 合并写表 256·COLS）；1×1 = 1664B、1×2 = 3328B、2×2 = 6144B、8×2 = 23040B、**8×4 = 46080B**。

### 已知坑

- **「红口只上半屏 / 绿口全黑」根因（第二十一轮，已修）**：prepare 原写 `s |= (role_bit[role[i]][c] & s_chain_sel[i])`，`role_bit` 只有 0/1、`s_chain_sel[i]=1<<i` → `1&2 = 1&4 = 1&8 = 0` → 状态字节恒只有 bit0（仅链 0 被驱动），与链表标定无关——「改了链表行为也不变」的机理。修复为 `if (role_bit[role[i]][c] != 0U) s |= s_chain_sel[i]`。教训：宿主自检按**意图语义**建模、未逐字核对 C 表达式 → 58/58 全绿而现场仍黑。

- **几何宏改文件不传 -D**：`-D_22_1665_MODULE_*=…` 只出重定义告警、文件值胜出（静默测错口径）；宿主换口径走 `macro_override.py` 源码替换。

- 上机清单：M2 映射（5 项打点图案：y=0→屏顶第 1 行、y=4→第 5 行、y=8→第 9 行、x=0..7→左 1..8、x=8..15→左 9..16）；M3 链长（R1 对 CLK 每扫描线恰 448 时钟、每行 LAT 1 次、A/B 序列 0→1→2→3、OE 换行窗口为高）；M5 CPU（DWT 实测单行耗时对照 120~156µs，同时观察 LwIP 丢包）；M4 亮度 0~8 全档无鬼影；屏体 RG 双色还是 RGB 全彩（源固件字库标注「双色」但三色引脚齐备，本驱动按全彩处理）；拼装数 7×4 或 10×4（10×4 → CCM 43936B）。
- TIM3 行周期为全局参数（影响所有模组），本驱动落成时未改（保持当时 500µs；现行 1.5ms 见 §1.2）。

## 9 专题：动态滚动显示

### 驱动要点（app_scroll 现行语义）

- **模块**：`Application/Inc/app_scroll.h` + `Application/Src/app_scroll.c`（通用，不含安徽专用语义）；渲染辅助导出 `app_render_draw_glyph_clipped` / `app_render_glyph_width_px`（`Application/Src/app_render.c`）。消费者：安徽费显 0x86~0x89；LDI/VMS 复用前把文本转 GBK 即可。
- **循环滚动语义**：文本按指定方向持续滚动，越过边界后从另一侧重新进入，**永不自动停**，收到停止帧才停。方向映射（安徽运动模式字节 → 枚举，值对齐零转换）：01=LEFT（从右往左）、02=RIGHT、03=UP、04=DOWN；00/全 0 帧 = 冻结该行。
- **停止语义（2026-09-09 裁决）**：`app_scroll_stop(slot)` = **冻结**（置槽位非活跃、**不清行、不提交**——像素停在当前位置；render 锁保证在途渲染完成后才返回，无半帧风险）；`app_scroll_stop_all()` / `app_scroll_stop_all_nolock()` = **保持清行**（0x81 清屏 / 0x85 静态显示依赖它清掉滚动内容）——内部拆 `_scroll_freeze_nolock`（stop 用）与 `_scroll_stop_clear_nolock`（stop_all 用）两条独立路径，stop_all 不继承 freeze。
- **任务与节拍**：scroll_task 惰性创建（栈 256×4=1KB，osPriorityNormal，ucHeap）；全槽空闲 → `osEventFlagsWait(WAKE, forever)` 休眠零 CPU；有活动槽 → 2ms 超时基础节拍；`step_ms = speed×2`（安徽 speed 字节 ×2ms），最小钳制 2ms（speed=0 防御）。
- **位移边界**：LEFT/RIGHT `off ∈ [-(extent_w-1), w-1]`；UP/DOWN `off ∈ [-(font_size-1), h-1]`；回绕目标 = 对侧边缘内 1px（循环视觉连续、无整行黑拍）；初始位移 = 整体不可见位置（LEFT=w / RIGHT=-extent_w / UP=h / DOWN=-font_size），首个推进拍即进入 1px 可见。
- **④a 脏矩形提交**：tick 对当拍推进的活跃槽取矩形**并集包围盒**，整拍仅一次 `dev_display_commit_frame_rect`；无活跃槽推进不提交；并集无效（防御路径）回退全量 `commit_frame`；stop 清行同用矩形。冻结槽不参与 tick 渲染、不进并集矩形 → pixel_map 中冻结内容天然保留、其他槽滚动不触碰冻结槽矩形；同槽重入 start 首拍先 fill 清矩形再画，无旧内容残留。
- **⑤ 渲染互斥**：scroll_task 的「渲染+commit」整段持 `s_render_mutex`（`app_scroll_render_lock/unlock`，与槽位锁 `s_scroll_mutex` 分离）；安徽 0x81/0x85/0x82/0x83 的「stop_all+渲染+commit」整段持同一锁 → 静态渲染与滚动渲染串行，消除混合帧黑条。**锁序固定 render → slot 单向**（start 仅持 slot 不持 render，无反向获取路径 → 无死锁）；stop/stop_all 公共函数自持渲染互斥，锁内调用用无锁变体 `app_scroll_stop_all_nolock`。
- **渲染路径**：`dev_display_fill(rect, BLACK)` 清行 → 逐字形 `app_render_draw_glyph_clipped(gx, gy, rect 裁剪)` → 整拍结束一次 commit。字形绘制复用 app_render 静态内部函数 `_flash_addr`/`_packed_glyph_bytes` 读字模（`dev_storage_read`，W25Qxx SPI 互斥锁保护），逐像素 `dev_display_set_pixel`（屏幕边界 + 裁剪矩形双重判界，越界单点丢弃 = 平滑裁剪）；不提交帧、由调用方整帧后提交。`dev_display_draw_bitmap` 已改为「按屏幕交集裁剪绘制」（`dev_display.c:225-262`），但无裁剪矩形参数、不处理负坐标——滚动字形可整体位于矩形外往返滑动，故仍走本路径。
- **渲染优化**：整行文本在矩形外 → 只清不画；字形整体在矩形左/右缘外 → 跳过（省 W25 读）；后续字形均在右缘外 → 提前结束。
- **字号参数化**：FONT_24 下 GBK 字形 24px / ASCII 12px（`_glyph_width_px`：ASCII=size/2、GBK=size）；垂直回绕边界与初始位移用 `font_size`、水平用 `extent_w`（按实际字形宽累计）；字模 `_packed_glyph_bytes` FONT_24 GBK=72B（≤调用栈 128B 缓冲）。全链路参数化，无硬编码 16。
- **并发**：槽位单写者（协议任务）×单读者（scroll_task）经 `s_scroll_mutex` 串行，渲染在持锁内完成；W25 读互斥（`dev_w25qxx.c` `_read` 入口加锁、`_read_locked` 无锁供 `_write` 读-改-写复用防自锁）；渲染 vs scan_task 与既有 app_render 同模式（pixel_map 写入可被 scan_task 的 prepare 中途抢占，半帧撕裂一帧可接受、无内存安全风险）。
- **内存**：静态 SRAM `s_slots[4]`（4×90B=360B）+ 事件/双互斥/任务句柄 = **376B**；scroll_task 栈 1KB 惰性（未启动滚动时 0 支出）；CCM 增量 0；`dev_display_t` 基类 +12B（dirty_rect 4×uint16 + valid 1B）；文本上限 `SCROLL_TEXT_MAX=64B`（GBK 32 汉字）。
- **屏幕口径**：尺寸无关——行区域矩形由调用方给出 (x,y,w,h)，start 时以 `dev_display_get()` 的 `screen_rows`（=宽，命名反直觉）/`screen_cols`（=高）钳位，不硬编码任何屏宽。

### 已知坑

- **W25 读时延轮询 → 滚动速度失真 ~7×**（已修）：`_dma_recv` 曾以 `while(!s_ok) osDelay(1)` 轮询 → 每字形 ~1ms 轮询粒度；改 `osEventFlagsWait` 事件等待（ISR 置位即刻唤醒 + 启动前 Clear 防残留 + 10ms 超时兜底 + RTOS 未就绪轮询兜底）后，W25 互斥锁也不再在睡眠期间被持有（其他协议渲染排队时延同步下降）。
- **回绕整行黑拍**（已修）：回绕目标原为「文本整体不可见位置」→ 每个滚动循环 1×step_ms 整行黑拍（低速时可达数百毫秒，观察为周期内短暂闪烁）；改「对侧边缘内 1px」后消除。
- 文本 64B 截断可能切开 GBK 尾部（渲染层按非法字节跳过）。
- 32×32 小屏（1-263 单模块）4 行×24=96 > 屏高 32：第 1 行可测、第 2 行经钳位 h=8 部分可见、第 3/4 行起点越界被拒（既有钳位/拒绝行为）；行距与多行同屏需量产口径实机验证。

### 契约

- 待联调（权威文档缺口）：运动模式取值表 1~4 为用户拍板约定（权威 .doc 仅给示例值 01，doc/13 §8 #11）；`stay_ms` 行为待定（字段口径 2B×100ms 大端已确认，v1 忽略，doc/13 §8 #10）；动态行首 Y=00/18/30/48（row×24、h=24）为按字号推导的假设（权威文档仅 16 点阵口径，doc/13 §8 #13）；stop=冻结后 0x85 触发 stop_all 仍清掉其他滚动行（是否符合上位机预期待联调，doc/13 §8 #12 后半）。
- 方向枚举与 mode 映射表不得引入浮点；改动滚动语义须同步核对 ⑤ 锁序（render → slot 单向）。

## 10 专题：自适应字号

### 驱动要点

- **`FONT_SELF_ADAPT` 是 `app_render()` 的标准能力**（`Application/Src/app_render.c` 的 `RENDER_TEXT` 分支）：从大到小尝试候选字号，选能完整放入目标区域的最大字号；无可用字号回退 `FONT_16`。**最终解释权在渲染层**。
- **分层职责收口**：业务层只决定「显示什么、显示在哪个区域」；渲染层负责「用多大字号显示」；设备层只负责像素输出、不关心字号语义。
- **约束**：文本宽度与屏幕尺寸**共同**参与字号选择（避免自适应选到无法完整显示的尺寸）。
- **多行文本**：同屏多行 = **一次性传入完整文本、单次 `app_render()` 渲染**（第二次全屏渲染会清屏，不能用两次全屏居中渲染实现两行）。
- **消费者**：开机 5 秒页（`app_boot.c`：先拼接 `fw_line` 与 `md_line` 两行，单次 `app_render()` + `FONT_SELF_ADAPT`）；工厂测试 `SHOW_CODE`（`app_factory_test.c`：一次性双行 + `FONT_SELF_ADAPT`，保留居中、全屏布局语义）。

### 已知坑

- **`FONT_SELF_ADAPT` 不能直接传给旧版 `app_render()`**：会被当作 `0` 处理并提前返回（历史上业务层各自算字号再传具体值的旧做法的残留陷阱）。
- 自适应逻辑分散在业务层（开机页算字号、SHOW_CODE 固定字号、E6/LDI 先决策后调用）→ 维护成本高、同类场景策略不统一——现行口径为渲染层统一收口，新模板文本页面优先用「单次渲染完整文本 + `FONT_SELF_ADAPT`」模式。

### 契约

- 字号选择不发生在设备驱动层；若未来需要更细粒度策略，在渲染层扩展候选字号与测量规则。
- 测量函数只支持 GBK（见 §11）：传入测量前必须完成编码转换。

## 11 专题：黑屏修复与 UTF8 误用修复

### 驱动要点

**E6 自适应字体黑屏 + 固定字体行号失效**（`Application/Src/LDI/app_ldi_device.c` `display_show`）：

- 两类问题的共同本质 = 显示参数到渲染位置映射不完整。
- 问题 A（自适应黑屏）：`font_size = FONT_SELF_ADAPT` 且 `font_line = 0` 时未把自适应字号转换为有效字号 → 渲染器收到无效参数 → 屏幕清空后无内容绘制。
- 问题 B（固定字体行号不生效）：固定字体模式没有统一处理 `font_line` → 文字总是从第一行开始显示。
- 现行口径：`font_line` 必须参与渲染位置计算；自适应模式必须保证最终字号有效；固定与自适应共享统一的行定位规则；显式区分全屏自适应与按行自适应。可复用参考：`Application/Src/LDI/app_vms_ctrl.c`。
- 排查口诀（同类显示控制问题）：「字体有效性 + 行号定位 + 文本宽度约束」三项。

**UTF-8 编码误用（自适应选号错误）**（`Application/Src/app_render.c` `_render_text` / `_select_adaptive_font` / `_measure_text_box`）：

- 症状：`app_test_render_text()` 用 `FONT_SELF_ADAPT` 渲染「车道」（UTF-8，6 字节），1-577 单模块 64×32 上预期 FONT_32（32×2=64 恰好填满屏宽），实际选 FONT_24。
- 根因：`_select_adaptive_font()`（原第 374 行）先于 `UTF8ToGBK`（原第 383 行）调用 → `_measure_text_box()` 拿 UTF-8 字节流按 GBK 逻辑解析：「车道」的 `E8 BD A5 E9 81 93` → E8 非法跳过、`A5 E9` / `81 93` 被误组成 2 个「GBK 汉字」→ `need_w = 2×size`；32pt 时 `need_w = 64` 恰等于屏宽 64，属**零容差边界匹配**，被误判不可用 → 回退 24pt。
- 现行口径：编码转换**提前**到自适应选择之前（`FONT_ENC_UTF8` → 先 `UTF8ToGBK` 转 GBK，再用 GBK 文本做 `_select_adaptive_font`）。
- 教训：`_measure_text_box()` 只支持 GBK、不支持 UTF-8；调用测量前必须确保文本已转换为目标编码；编码转换应尽早；边界匹配（need_w == w）注意零容差。
- 验证：修复后「车道」在 64×32 正确选 FONT_32；1-969、1-260 等其余模组自适应字号回归正常。

### 已知坑

- `font_size` 长期停留在无效值（0 = FONT_SELF_ADAPT 未解析）→ 清屏后无绘制 = 黑屏：任何自适应入口都必须保证最终字号有效，不得把 `FONT_SELF_ADAPT` 原样传给旧渲染路径。
- UTF-8 字节被 GBK 逻辑误解析时**字符数可能巧合正确**（6 字节 → 2 个「汉字」）——症状不是报错而是选错字号，要靠边界匹配场景（文本宽恰等于区域宽）暴露。

### 契约

- 自适应选号流程的固定顺序：编码转换 → 测量 → 选号 → 绘制；任何重排必须保持该顺序。
- `_measure_text_box()` 的输入契约 = GBK 编码；UTF-8 文本必须先 `UTF8ToGBK`。
