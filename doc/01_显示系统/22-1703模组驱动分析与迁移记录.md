## 2. 位流映射（hub75_buff 布局）

**等价改写**（源固件 `USER/TIMER/timer.c:359-383` 的 `displayDataUpdata`）：

```
ch   = y / 8                          // 通道 = 自然序 ch0..ch7
line = y % 4                          // 扫描行
half = (y % 8) / 4                    // 0=上半行、1=下半行
组号 = (y/8*4 + y%4) * (448/16) + x/8 // 每扫描行 28 组
组内 = (x%8) + half*8                 // 上半行偏移 0..7、下半行偏移 8..15（**顺序**）
```

1 个 16 字节组 = 同一扫描线的 8 个 x（上半行）+ 同 8 个 x（下半行）。

`prepare` 退化为「每逻辑行 28 个 8 字节块拷贝」：

```c
row_dst[y] = ch*1792 + line*448 + half*8;      /* init 期预计算（CCMRAM） */
for (blk = 0; blk < 28; blk++)
    memcpy(hub75_buff + row_dst[row] + blk*16, pixel_map + row*224 + blk*8, 8);
```

- **④a 脏矩形兼容**：每逻辑行独立落入自己的 8 字节半区，行子集重排天然安全（`dirty_rect_valid` 时只重排矩形覆盖的 y 行范围）。
- 全帧 prepare 成本 ≈ 64 行 × 28 块 = 1792 次 8 字节拷贝（远低于扫描开销）。

### 2.1 映射裁决（任务 Q3）：**以 wyh 实机版为准，wyh 版 = 源固件口径**

| 版本 | 通道序 | 下半行位序 |
|---|---|---|
| 源固件 9K23881580 | 自然序 `{R1..R8}`（`ch = y/8`） | 顺序（`x%8 + 8`） |
| **wyh 分支 `dev_P10_32x16_2200001703.c`** | 自然序（`g_hub75_pin_r[ch]`） | 顺序（`pixel_row/4%2*8 + pixel_col%8`） |
| 已删除的旧 STD `Drivers/BSP/Display/scan.c` `convert_pixelmap_p10` | 相邻互换 `{R2,R1,R4,R3,...}` | **逆序**（`15 - x%8`） |

**采纳：wyh 版（= 源固件口径，自然通道序 + 顺序下半行）**。旧 STD 版不采用（其所在工程/DOM 已废弃、屏体批次不可考）。

**证据（宿主穷举比对，2026-09-14）**：以同一 `pixel_map`（伪随机 + 全 0 两组输入）分别跑
①源固件公式 ②wyh 版公式 ③本驱动 `row_dst` 公式，逐字节比对 14336 字节 hub75_buff：

```
几何：224x64, 通道 8, 单通道 1792, 每扫描行 448 时钟, 每行 28 组
位流比对：源固件 vs wyh版 = 一致；源固件 vs 本驱动 = 一致
扫描读取序比对（line/px/ch 读取顺序）：源 vs wyh = 全等；源 vs 本驱动 = 全等
扫描覆盖唯一性：14336/14336 字节，异常项 0
结果：位流全等；扫描序全等；覆盖通过；零值场景全等
```

（wyh 版 `MODULE_ROWS=10`（→320×64）与本文件 `7`（→224×64）仅为**屏体拼装**差异：
其组公式 `GROUP_PER_ROW = MODULE_ROWS*4` 随拼装数自适应，与本文件公式同构。）

## 3. scan 实现（档位 D+：按 GPIO 端口合并写 BSRR）

### 3.1 端口分组（由 `pl_hub75` 引脚表推导，本 PCB 为 5 组）

| 组 | 信号（通道/颜色） | 引脚（`Core/Inc/main.h:74-193`） | key 表达式（热路径） | 表项数 |
|---|---|---|---|---|
| G | ch0(R,G,B) + ch1(R) | PG9/PG10/PG12/PG15 | `c0 \| (c1<<3)` | 64 |
| B | ch1(G,B) + ch2(R,G) | PB7/PB6/PB8/PB9 | `c1 \| (c2<<3)` | 64 |
| E | ch2(B) + ch3(R,G,B) + ch4(R,G,B) | PE0/PE1..PE3/PE4..PE6 | `c2 \| (c3<<3) \| (c4<<6)` | 512 |
| C | ch5(R,G,B) | PC13/14/15 | `c5` | 8 |
| F | ch6(R,G,B) + ch7(R,G,B) | PF0..PF5 | `c6 \| (c7<<3)` | 64 |

- 每时钟（每像素）**只写 5 次 BSRR**（同端口多通道合并为一次 32 位写），替代档位 A 的 8 通道 × 3 = 24 次写引脚；数据脚全在 G/B/E/C/F，与行址/CLK/LAT/OE（全部 PDx）**物理不相交**。
- 表在 `hw_dev_initcall` 由 `g_hub75_pin_r/g/b` 生成，并**校验同组信号确在同一 GPIO 端口**；校验失败 → `s_22_1703_merged_ok = false` → 自动回退通用逐通道路径（`pl_hub75_set_rgb`），不静默出错。
- 颜色字节取自 `hub75_buff`（值域 0~7，由 `pixel_map` 写入侧保证），故 key 表达式无需再掩码。

### 3.2 等价性证据（宿主穷举 8^8 = 16,777,216 组合）

```
信号覆盖：24 个数据脚 唯一覆盖
穷举 16777216 个颜色组合：失配 0 → 全部等价（合并写 == 逐通道写）
```

> 该穷举在开发中**实际抓到过一次分组位序错误**（grp1/grp2 的 key 位号与热路径表达式不一致），
> 已修正并复验——此类错误在实机上表现为通道错位，肉眼难以定位。

### 3.3 指令数与 CPU 估算（`-Og` 反汇编实测）

| 驱动 | 每时钟指令数 | 每行（448 时钟） | 通道-时钟数 | 每通道-时钟 |
|---|---|---|---|---|
| `_1_263_scan`（现行 7×2，2 通道，含 3 次写引脚/通道） | 58（22×2 + 14） | **25,984** | 896 | 29 |
| `_22_1703_scan`（本模组，8 通道，合并写） | **45** | **20,160** | 3,584 | 5.6 |

> 本模组每行位输出是 1-263 的 4 倍，而指令数反而少 22%（合并写把 24 次引脚写压到 5 次端口写）。

**估算耗时**（沿用分析报告 §4.4 的 1.0~1.3 周期/指令折算，168MHz）：

- 每行 ≈ 20.2k~26.2k 周期 ≈ **120~156 µs**；
- 占 TIM3 行周期（现行 `Core/Src/tim.c:82-84` = 500µs）的 **24~31%**；若 TIM3 改 1ms → **12~16%**。

**档位对比**（分析报告 §4.4）：档位 A（朴素）339~440µs/行（68~88%@500µs）→ 档位 D 133~173µs → 本实现（D+）120~156µs。

⚠ **TIM3 行周期为全局参数（影响所有模组），本次未改**——`Core/Src/tim.c` 保持 500µs。
是否需要放宽到 1ms（刷新 250Hz，仍是源固件 71.4Hz 的 3.5 倍）属**待用户裁决项**，
见 `.analysis/9k23881580/integration_report.md` §5；上机后须用 DWT 实测复核（M5）。

## 7. 待硬件实测确认项（上机清单）

1. **映射正确性（M2）**：用点阵打点图案逐项确认——① y=0 整行亮 → 屏顶第 1 行；
   ② y=4 整行亮 → 第 5 行（判上半/下半行语义）；③ y=8 整行亮 → 第 9 行（判通道序）；
   ④ x=0..7 亮 → 屏左起 1..8（判组内位序）；⑤ x=8..15 亮 → 左起 9..16（判块序）。
2. **移位链长度（M3）**：`R1` 对 `CLK` 计数，每扫描线应恰为 **448** 个时钟；每行 LAT 脉冲 1 次；
   `A/B` 电平序列 0→1→2→3；OE 在换行窗口为高。
3. **CPU 实测（M5）**：DWT 计时 `_22_1703_scan` 单行耗时，对照 §3.3 的 120~156µs 估算；
   同时观察 LwIP（ping/IAP 升级/UDP 业务）有无丢包或明显变慢。
   若实测占空比过高 → 裁决 TIM3 周期（1ms）或进一步优化（分析报告 §4.4 档位 C）。
4. **亮度/消隐（M4）**：`dev_display_set_brightness` 0~8 全档目视；换行无鬼影/残影。
5. **屏体颜色**：屏体实际为 RG 双色还是 RGB 全彩（源固件字库文件名标注"双色"，但三色引脚齐备）
   → 影响协议侧颜色可选范围（本驱动按全彩处理）。
6. **拼装数复核**：整机实际为 7×4 = 224×64（本配置）还是其它（wyh 口径 10×4 = 320×64）；
   改 `MODULE_ROWS/COLS` 即可，CCM 随动（10×4 → 31648+12288 = 43936B）。
