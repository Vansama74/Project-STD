# GZ_OL `0x40` 端口不生效 —— 端到端追踪与性质判定（2026-09-14）

> **【修订 2026-09-15 · 用户裁决（现行口径，优先于本报告）】** 端口字段线上编码改为**高字节在前（BE16）**，
> **有意不参考协议文档/源固件**：写 10028 发 `27 2C`（改后即生效），`2C 27` 解析为 11303。本报告内
> 「小端 `2C 27`=10028」的表述为当时的实现口径（历史），现行口径见 `doc/14_贵州治超屏协议/README.md`
> §13.5.1 与 `port_10028_diagnosis.md` §8.8。

**现场事实**：实机用贵州治超屏协议（"TCLY" 帧族）`0x40` 改 IP → 重启后 **IP 生效**；
同一命令里的 **端口不生效**（用户按同一套流程验证，端口没有变化）。

**结论（先说答案）**：**不是写入 bug，是端口字段语义不匹配**——
① `0x40` 的端口值与 IP 在同一记录、同一次擦写事务中落盘（**IP 生效即证明端口字段已落盘**）；
② 该值被应用到 **STD `net_cfg.port` = TCP 业务口（9528）**，而 GZ_OL 自身的 UDP 服务口是
**编译期常量 10011**（`LDI_DISCOVERY_PORT`，源码注释明写「设计原则禁止修改接口」），
Sector1 里没有任何字段能让它变化；
③ 源固件语义里该端口 = **设备自身 UDP 口**（`#define UDP_LOCAL_PORT F407_PORT` →
`udp_bind(upcb, IP_ADDR_ANY, UDP_LOCAL_PORT)`），所以上位机按「改设备端口」理解时，
现象必然表现为「端口不生效」。
④ 附带发现（当前映射的副作用）：`0x40` 的端口值会**悄悄把 LDI/IAP 生态的 TCP 业务口
（9528）改成设定值**，这是跨协议副作用，建议一并裁决（见 §4）。

**本报告不含任何代码改动**（按任务要求：语义不匹配分支不擅自改字段语义，交用户裁决）。

## 1. 端到端追踪 `0x40`（含证据行号）

### 1.1 链路总览

```
上位机 0x40 帧（UDP 10011 / RS485 / RS232 任一通道）
  └─ probe（首字节 0x54 快拒 + 4B 引导串）→ 入 gz_ol 队列
      └─ gz_ol_parse_frame()            app_gz_ol_proto_parse.c:154-166
          ├─ data_len < 14 → ERR_PARAM（整帧丢弃）        :157-159
          └─ port = LE16(payload[12..13])                :164
      └─ gz_ol_execute_cmd() → _gz_ol_exec_set_ip()      app_gz_ol_proto_cmd.c:266-287
          ├─ udp_port = (记录有效 ? cur.udp_port : 20103) :271
          ├─ app_board_net_cfg_update(ip,mask,gw,port,udp_port)  :272（返回值被 (void) 忽略）
          ├─ 应答 0x50 帧（**回显请求字段**，非读回记录）  :275-281
          ├─ osDelay(100)                                 :285
          └─ NVIC_SystemReset()                           :286
      └─ 重启后 app_net_boot_apply()                       app_net_boot.c:66-69
          ├─ pl_net_set_ip(cfg.ip,cfg.mask,cfg.gw)         → netif_set_addr（pl_net.c:104-116）
          └─ app_tcp_server_set_port(cfg.port)             → TCP Server 监听口
                                                             （app_tcp_server.c:45-48 → :91 bind）
```

### 1.3 关键推论：IP 生效 ⇒ 端口字段已落盘（排除「没写进去」）

`app_board_net_cfg_update()` 把 `ip/mask/gw/port/udp_port` 全部写进**同一个 `info.net_cfg`**，
再**一次擦除 + 一次 72B 写**（`app_board_net_cfg.c:155-156`、`:166-170`）。字段之间没有独立写路径：

- 擦除失败 / 写失败 → `return ret;`（`:167-168`、`:170`）→ **整条记录都不变**（IP 与端口同时保持原值）；
- 同值跳过（`:160`）→ 要求 `net_cfg` **全字段（含 ip 与 port）与旧快照逐字节相同** → 若端口/ IP 有变化必走写路径；
- 因此「IP 变成新值」这一现场事实，**等价于「整条记录（含 `port` 字段）已成功写入 Sector1」**。

→ 「端口根本没写进去」在本实现里**不成立**（除非端口值与旧值相同，而用户明确说是「改了但没变」）。
→ 也**不存在「别处把它覆盖回默认值」**：Sector1 的写方只有 5 处（`app_board_net_cfg_update` 调用点），
启动路径上仅两处可能触发，且都以「记录无效/非法」为前提：
- `app_net_boot.c:37-62` accept_write（仅当 `app_board_net_cfg_get` 失败 或 IP 全 0 或 port∉[1,65535]）→ 会同时写默认 IP（dev：192.168.114.200），与「IP 生效」矛盾；
- `app_ldi.c:190-199` 分支 2 自愈回写（仅当 Sector1 空/损坏/**net_cfg 非法**）→ 同样会回滚 IP；
- 分支 1（`app_ldi.c:107-154`，本次记录必然走这条）**只写 W25 镜像**（`:145`/`:154`），**不写 Sector1**。

### 1.4 「端口字段确实生效了，只是生效到了 TCP 业务口」

- 唯一消费者：`app_net_boot.c:69` → `app_tcp_server_set_port(cfg.port)`；`app_tcp_server.c:43`
  （`static uint16_t g_port = 9528;`，`:19` `#define TCP_SERVER_PORT 9528`）→ `:91`
  `netconn_bind(conn, IP_ADDR_ANY, g_port)`。
- 静态证明（默认口径 elf，`build/Debug/Project_STD.elf` md5 `81f114b8…`）：
  - `app_tcp_server_set_port` 反汇编 = `strh r0,[0x200003cc]`（写 `g_port`，符号 `200003cc d g_port`）；
  - `tcp_server_task` 首部 = `ldrh r2,[r3=0x200003cc]` → `bl netconn_bind`（绑定时读 `g_port`）。
- 调用点唯一性：全仓 `app_tcp_server_set_port` 只有 `app_net_boot.c:61/69` 两处（无别处覆盖回 9528）。
- 结论：`0x40` 设 `port=X` 后重启，**TCP 监听口确实变成 X**（9528 不再监听），
  但 **GZ_OL 的 UDP 服务仍在 10011**，与用户期望的「设备端口」无关。

### 1.5 源固件语义（端口 = 设备自身 UDP 口，有源码证据）

| 证据 | 位置 | 内容 |
|---|---|---|
| 端口宏 | `9K23881580/.../USER/LWIP_APP/UDP_SERVER.h:11` | `#define UDP_LOCAL_PORT F407_PORT` |
| 端口绑定 | `UDP_SERVER.C:418` | `udp_bind(upcb, IP_ADDR_ANY, UDP_LOCAL_PORT)` ← **就是设备自己的 UDP 监听口** |
| `0x40` 解析/落库 | `UDP_SERVER.C:233`、`:235-240` | `F407_PORT = inbuf[12] + (inbuf[13] << 8)`（小端与本实现一致）；写 W25 `"setip"` 记录 |
| 应答 | `UDP_SERVER.C:257-258`（0x50）/ `:285-286`（0x70） | 回显 `F407_PORT` 小端 |
| 默认值 | `UDP_SERVER.C:305-355`（`:353`） | 无记录 → `F407_PORT = 10028` |
| 源固件自身缺陷（**本实现未复制**） | `UDP_SERVER.C:336` | 上电读回用大端 `(t[17]<<8)+t[18]`，与写入小端不自洽 |

→ 协议字段语义 = 「设备自身 UDP 服务口」**成立**；本实现把它接到了 TCP 业务口，
GZ_OL 的 UDP 服务口保持 10011 恒定 → **语义不匹配**。

## 2. IP 生效 / 端口不生效 的差异机理

| 维度 | IP（生效） | 端口（不生效） |
|---|---|---|
| 应用对象 | **netif 全局属性**（`pl_net_set_ip` → `tcpip_callback(netif_set_addr)`，`pl_net.c:104-116`）→ 影响**所有** socket（UDP 10011 / CQ 20103 / TCP / ICMP） | 只作用于 `net_cfg.port` 的**唯一消费者**：TCP Server 监听口（`app_net_boot.c:69`） |
| GZ_OL 服务口是否随之改变 | 是（GZ_OL 走 UDP 10011，IP 换了以后发往新 IP:10011 即可通信） | **否**：GZ_OL UDP 服务口 = `LDI_DISCOVERY_PORT` 编译期常量（`app_udp.c:18-19`、`app_ldi.h:13`），Sector1 中无字段可改它 |
| 上位机视角 | 改 IP 后照旧用 10011 通信 → 「IP 生效」 | 改端口后按新端口发帧 → 无应答（只有 10011 应答）→ 「端口不生效」 |
| 是否跨协议副作用 | 无（IP 本为共享） | **有**：LDI/IAP 生态的 TCP 业务口（9528）被悄悄改成设定值 |

**一句话**：IP 落在一个「全局共享、所有服务都听」的属性上；端口落在一个「跟 GZ_OL 无关的
服务（TCP 业务口）」上，而 GZ_OL 自己的服务口是编译期写死的 10011。

## 3. 性质判定

| 判定 | 结论 |
|---|---|
| 端口是否写进 Sector1 | **是**（与 IP 同一记录同一次擦写；IP 生效即证明） |
| 端口写入是否被拒绝/跳过 | **否**（中间态不拒；同值跳过要求全 `net_cfg` 相等；返回值未检查但不影响本结论） |
| 端口是否被启动路径覆盖回默认 | **否**（仅记录无效/非法时才会写默认，且会连 IP 一起回滚） |
| 端口字段的消费者 | 仅 `app_tcp_server_set_port` = **TCP 业务口** |
| GZ_OL 自身 UDP 服务口 | **编译期常量 10011**，不可由配置改变 |
| **最终定性** | **语义不匹配（字段落到了错误的服务端口上）**，不是写入/落盘 bug；另含一处**跨协议副作用**（改 TCP 业务口） |

## 4. 处置方案（决策选项表，交用户裁决）

> 前置：按纪律**本轮不改任何代码**；下列代价均为代码级估算（含内存/文档面）。

| 选项 | 做法 | 代价 | 风险/副作用 | 推荐度 |
|---|---|---|---|---|
| **① 忠实复现（改 GZ_OL 自己的 UDP 口）** | `0x40` 改写 `net_cfg.udp_port`（保留 `port`）；新增 GZ_OL 专用 UDP 通道实例（仿 `_udp_cq_*`：新 `CH_ID_UDP_GZOL` + `app_udp_gz_ol_start()` + `_udp_gz_ol_read_port()` 读 Sector1 `udp_port`），GZ_OL 绑定该通道；`0x70` 应答改报实际服务口 | +1 netconn（`MEMP_NUM_NETCONN`/`MEMP_NUM_UDP_PCB` 各 8，dev baseline 已用 4——须按 doc/06 记账）；+1KB 任务栈（ucHeap 36KB，需查水位）；`CH_ID_MAX 8→9` 影响 `ch_proto_map[]/channels[]` 数组（~几十 B bss）；新增通道 RB/绑定/互斥核对（doc/08-03）；文档与宿主推演更新 | `udp_port` 是 **CQ 专有字段**：PROTO=ALL/dev 口径下 CQ 实例（固定 20103）与本实例可能同口 → 需**构建口径互斥**（GZ_OL 量产口径 vs CQ 口径）或另立字段；**另立字段会破坏 Sector1 72B 布局**（Bootloader/Recovery 必须同步重烧，方案 B 纪律加重） | ★★☆ 仅当产品要求「上位机可改设备端口」时必须做 |
| **② 维持 `port`（TCP）语义 + 文档明确** | 不改代码；文档（doc/14 §13、CLAUDE.md）写明「设备 UDP 口固定 10011；本字段只改 TCP 业务口 9528→X」 | 0 | ①跨协议副作用保留（LDI/IAP 的 TCP 口被 GZ_OL 命令改动）；②上位机若依赖该字段则永远不生效 | ★★☆ 最小成本，但需用户接受「字段无效」 |
| **②b 只改 IP，端口保留现值（消除副作用）** | `app_board_net_cfg_update(ip,mask,gw, cur.port, udp_port)`——`0x40` 不再改任何服务端口；文档明确「本字段在 STD 上不改变任何端口」 | 极小（1 行传参变化 + 文档） | 端口字段彻底沦为无效字段（比 ② 更诚实，代价是上位机改端口的诉求完全无实现路径）；`0x70` 回显端口仍报 `net_cfg.port`（9528），与「设备端口」也不一致 | ★★★ 若短期不做 ①，建议选此（消除跨协议副作用） |
| **③ 同时写 `port` 与 `udp_port`（同值）** | `app_board_net_cfg_update(..., port, port)` | 0（1 个实参） | **单独做无收益**：GZ_OL UDP 服务口仍 10011；若将来做 ① 则记录已就位；PROTO_CHONGQING 口径下会把 CQ UDP 业务口一起改掉（跨协议副作用） | ★☆☆ 仅作为 ① 的铺垫，不单独实施 |

**推荐组合**：
1. **本周（不改代码路径）**：选 **②b** + 文档（把「10011 固定」写进联调说明与上位机配置说明）；
2. **若产品要求「上位机改端口即生效」**：做 **①**，并同时裁决 `udp_port` 的字段归属与构建口径互斥（GZ_OL 量产口径不编 CQ，或为 GZ_OL 增设独立字段并接受三固件同步重烧）。

## 5. 现场复测步骤（发什么帧 / 看什么现象 / 如何判定）

**统一前提**：DIP1 = OFF（9600）；GZ_OL 网口只应答 **10011**；`0x50` 修改应答是**回显请求**
（**不能**作为落盘证据）；读 Sector1 的只有**搜索触发 `0x50`/`0x60` → 应答 `0x70`**。

### 5.1 落盘核验（证明「端口字段确实写进去了」）

1. 发 0x40 把 IP 改成 `192.168.1.100`、端口改成 `10028`（0x272C 小端 = `2C 27`）：
   ```
   54 43 4C 59 00 00 00 00 1F 00 00 00 40 00 00 00 C0 A8 01 64 FF FF FF 00 C0 A8 01 01 2C 27 00
   ```
   （31B；旧帧例端口 9528 即 `38 25`）
2. 约 100ms 后设备自复位。重启后把上位机目标改到 **新 IP + 10011**，发 `0x60`（或 `0x50`）搜索帧：
   ```
   54 43 4C 59 00 00 00 00 11 00 00 00 60 00 00 00 00
   ```
3. **判定**：0x70 应答载荷 `[0..3]`=新 IP、`[12..13]`=`2C 27`（10028 小端）
   → **落盘成功**（与「IP 生效」互相印证；若这里仍是旧端口，才需要查写入路径）。
4. **预期现象**：应答里端口已是 10028 —— 说明「写进去了」。**但这不等于 GZ_OL 在 10028 上服务。**

### 5.2 应用域核验（证明「端口只生效到 TCP 上」）

5. 用 TCP 工具连新 IP 的 **10028** → 应能建立连接（TCP Server 已迁到 10028）；
   连 **9528** → 应连不上（旧 LDI 上位机此时会连不上 9528 → 这就是跨协议副作用）。
6. 用 UDP 工具发 0x60 到新 IP 的 **10028** → **无应答**；发到 **10011** → 有应答。
   → 与「①设备 UDP 口固定 10011；②0x40 端口只改 TCP 业务口」两条结论完全一致。

### 5.3 判定矩阵

| 5.1 的 0x70 端口 | 5.2 的 TCP 10028 | 5.2 的 UDP 10028 | 结论 |
|---|---|---|---|
| 10028（新值） | 通 | 无应答 | **语义不匹配（本报告结论）** |
| 旧值 | 不通 | 无应答 | 写入/落盘失败 → 需抓 RTT + 查 Sector1 记录（当前无此现象） |
| 10028 | 通 | 有应答 | 说明已实现选项 ①（当前未实现） |

## 7. 遗留项

1. **`udp_port` 字段归属未决**：CQ 专有（`app_udp.c:316-332`）；若做选项 ①，必须先定「GZ_OL 与 CQ 是否同编」以及字段共享方式（同编即需口径互斥或新字段 + 三固件同步重烧）。
2. **上位机（`CD_GuiZhou_QBB.dll`）是否依赖 `0x50/0x70` 回显端口**：若上位机把回显端口写回自己的目标端口配置，则选项 ②b 会带来「回显 9528 / 实际服务 10011」的二次不一致，需一并确认。
3. **0x50 应答不可作为落盘证据**（回显请求）——已写入本报告 §5 与 doc/14 §13；后续若做 RTT 诊断，建议在 `_gz_ol_exec_set_ip` 内加一行「update 返回值 + 落盘后 read-back」日志（当前 `(void)` 吞掉返回值）。
4. **`0x70` 回显端口口径**：当前报 `net_cfg.port`（TCP 业务口）；若最终裁决「设备端口 = 10011」，回显是否改报 10011 需用户裁决（涉及上位机兼容）。
5. **本轮未做的验证**：无硬件，未做实机复测（§5 步骤待现场执行）；TCP 端口迁移为静态代码 + 反汇编证明，未实测。
