### 2.1 帧格式

| 偏移 | 长度 | 字段 | 取值/语义 | 证据 |
|---|---|---|---|---|
| 0..3 | 4 B | **引导串** | `54 43 4C 59`（固定） | D「引导串：4字节, 54,43,4C,59」；S `UDP_SERVER.C:78-79` |
| 4..7 | 4 B | 包序号 | 文档规定 `00 00 00 00`；源固件**不读不校验** | D「包序号：4字节，00 00 00 00」；S `UDP_SERVER.C:76`（仅偏移跳到 8） |
| 8..9 | 2 B | **数据包长度** | **小端**；= **整帧总长（含引导串与结束符）** | D「数据包长度：2字节，先低字节后高字节(整个通信协议里包含的数据总数)」；S `UDP_SERVER.C:80` `tempLen = ringBuf[head+8] + (ringBuf[head+9]<<8)` |
| 10..11 | 2 B | 保留位 | 文档规定 `00 00`；源固件**不读不校验** | D「保留位：2字节（暂时填00 00 16进制）」 |
| 12..15 | 4 B | **命令字** | 4 字节容器；文档「不足四个字节后面补 0x00」→ **仅 byte[12] 有效** | D「命令字：4字节（详细参考命令字说明16进制）」；S `UDP_SERVER.C:83` `getCmdNo(&ringBuf[head+12])` 只读单字节 |
| 16..16+N-1 | N B | **基本数据包** | 变长，含义随命令字（见 §2.3） | D「基本数据包：长度变长，包含显示内容、设置参数及扩展码」 |
| 16+N | 1 B | **结束符** | `0x00` | D「结束符：1字节，00（16进制）」；S `UDP_SERVER.C:81` `ringBuf[head + tempLen - 1] == 0x00` |

## 3. 与既有协议的冲突矩阵与快拒策略

### 3.1 既有协议首字节占用（STD 现状）

| 槽 | 首字节占用 | 协议（证据：`doc/05_协议模块多协议兼容优化/01_architecture.md` §3.3、各协议源文件 probe） |
|---|---|---|
| RS485 / RS232 | `0xFF` | 四川治超（`app_sc_ol_proto.c` probe：首字节非 `0xFF` → FAKE；第二字节 = 长度 `[7,255]` 且**排除 0xFE**） |
| RS485 | `0xFF 0xFE` | RLS（`app_rls.c:89-98`：首字节非 `0xFF` → FAKE，第二字节非 `0xFE` → FAKE） |
| RS485 / RS232 | `0x7B`（`'{'`） | 青海 / 山东 / 贵州（常规费显）/ 云南 / 四川 MTC |
| RS485 / RS232 | `0x0A` | 四川 ETC |
| RS485 / RS232 | `0x5A` | 安徽（`app_anhui_proto.c`） |
| RJ45（UDP/TCP） | `0x5A5A5A5A` | IAP |
| RJ45 | `0xFF 0xFF` | LDI |
| RJ45 | `'{'` 或 `FF FF`+12B | 重庆 CQ |

### 3.2 贵州治超（新）与各协议冲突矩阵

| 组合 | 同物理槽 | 判定 | 依据 |
|---|---|---|---|
| **贵州治超 + 四川治超** | RS485/RS232 | ✅ **允许（双向首字节快拒成立）** | 新协议首字节 `0x54` ≠ `0xFF` → 四川治超 probe 立即 FAKE；四川治超首字节 `0xFF` ≠ `0x54` → 新 probe 立即 FAKE。**第二字节无需参与判别**（`0x43` vs 长度域，且 0x43=67 落在治超合法长度区间 [7,255] 内 — 但首字节已互斥，不进第二字节比较） |
| **贵州治超 + RLS** | RS485 | ✅ **允许** | RLS 要求首字节 `0xFF` 且第二字节 `0xFE`；新协议首字节 `0x54` → RLS FAKE；RLS 首字节 `0xFF` → 新 probe FAKE |
| **贵州治超 + 青海/山东/贵州常规/云南/四川MTC** | RS485/RS232 | ✅ **允许** | 上述协议首字节 `0x7B`（`'{'`）；新协议 `0x54` → 互斥快拒 |
| **贵州治超 + 四川 ETC** | RS485/RS232 | ✅ **允许** | ETC 首字节 `0x0A`；互斥 |
| **贵州治超 + 安徽** | RS485/RS232 | ✅ **允许** | 安徽首字节 `0x5A`；互斥（`0x54` ≠ `0x5A`） |
| **贵州治超 + IAP / LDI / CQ** | **不同槽**（RS485/RS232 vs RJ45） | ✅ **允许**（若不绑定 UDP，则物理不相交） | 若**额外绑定 `CH_ID_UDP`**（RJ45 槽）：IAP 首字节 `0x5A` → FAKE；LDI 首字节 `0xFF` → FAKE；CQ 首字节 `{`/`FF` → FAKE。**仍无冲突** |
| **贵州治超 + `CH_ID_RS232_1`** | — | ⛔ **禁止**（USART6 语音 TX 专用，无 RX 通道） | `doc/05-01` §6、`doc/08-04` Step 8 |
| **贵州治超 + `g_brace_proto_guard`** | — | **不适用**（非 `'{'` 帧族，**不定义**该守卫符号） | 守卫仅约束 QH/SD/GZ/SC_MTC/YN 五个 `'{'` 族 |

### 3.3 结论

> **✅ 贵州治超协议在 STD 全协议架构下与现有任何协议零帧头冲突：**
> 1. **不需要 EIDE 目录互斥排除**（不像山东/贵州/云南/青海/四川MTC 那样必须二选一）；
> 2. **不需要 `g_brace_proto_guard` 编译期守卫**；
> 3. **probe 首字节快拒（`0x54`）即为充分判别**，无需第二字节参与；建议额外做 4 字节引导串全匹配（`54 43 4C 59`）以进一步降低误认领概率（几乎零成本，且 `0x54 0x43` 组合在既有协议数据段中出现的概率被压到极低）。

### 3.4 probe 快拒策略（建议）

```
探测顺序（链式，注册序决定）：
  ① avail == 0                     → FAKE          （禁止盲 WAIT 阻塞链式）
  ② peek[0] != 0x54                → FAKE          （首字节快拒，挡住 ~99.6% 无关数据）
  ③ avail < 4                      → WAIT          （引导串未到齐）
  ④ peek[1..3] != 43 4C 59         → FAKE          （4 字节引导串全匹配）
  ⑤ avail < 10                     → WAIT          （长度字段未到齐）
  ⑥ len = peek[8] | peek[9]<<8
     len < 17                       → FAKE          （结构性下界 = 16 帧头 + 0 载荷 + 1 尾）
     len > 本模块帧长上限            → FAKE          （见 §4.3；防止"永不满足的 WAIT"卡死链式）
  ⑦ avail < len                    → WAIT          （整帧未到齐）
  ⑧ peek[len-1] != 0x00            → FAKE          （尾字节定界校验）
  ⑨ READY，写 *total_len = len
```

> **硬约束（务必遵守）**：第 ⑥ 步的长度上界**必须**≤ RB 可用容量（`RB_SIZE_RS485-1 = 767`）。若允许 `len` 超过 RB 容量，probe 会返回 `WAIT` 而 `avail` 永不可能达到 `len` → **链式探测在该槽上永久停等**（`doc/05-01` 记有四川治超因长度上限放宽到 `0xFF` 后必须显式排除 `0xFE` 的同类教训）。
>
> **命令字不在 probe 中校验**（保持 probe 纯粹为"帧结构"判定，与 SC_OL/Anhui 一致）；命令合法性在 `parse` 层判定 → `GZ_OL_PARSE_ERR_CMD` 静默丢弃。

### 4.3 队列深度与 payload 上限

**长度上界推导**：

| 约束 | 值 |
|---|---|
| 0x20 显示命令的**实际最大帧长** | FONT16 / 224×64 屏：14 GBK 字/行 × 4 行 = 56 字 = **112 B 文本** → 帧 = 17 + 17 + 112 = **146 B** |
| 源固件 FONT16 文本缓冲硬上限 | 124 B → 帧 = 17 + 17 + 124 = **158 B** |
| RB 可用容量 | `RB_SIZE_RS485 - 1 = 767`（`RB_SIZE_RS232` 同 768） |
| dispatch 全局帧上限 | `FRAME_DATA_MAX_LEN = 1044`（`app_dispatch.h:24`） |
| `osMessageQueue` 消息体 | `sizeof(frame_msg_t) + payload = 8 + payload`（`app_dispatch.h` 柔性数组，`sizeof(frame_msg_t)==8`） |

**建议**：

```c
#define GZ_OL_FRAME_LEN_MIN   (17U)   /* 16 帧头 + 0 载荷 + 1 尾（0x10/0x30/0x60 最小帧） */
#define GZ_OL_FRAME_LEN_MAX   (256U)  /* 解析/入队上限：实测最大 158B，256 留 1.6× 余量 */
#define GZ_OL_PAYLOAD_MAX     (GZ_OL_FRAME_LEN_MAX) /* 256 */
#define GZ_OL_MSG_SIZE        (sizeof(frame_msg_t) + GZ_OL_PAYLOAD_MAX) /* 264 */
#define GZ_OL_QUEUE_DEPTH     (3U)    /* 与青海/贵州/云南/四川/安徽一致 */
_Static_assert(GZ_OL_PAYLOAD_MAX <= RB_SIZE_RS485, "GZ_OL frame must fit RS485 RB");
_Static_assert(GZ_OL_PAYLOAD_MAX <= RB_SIZE_RS232, "GZ_OL frame must fit RS232 RB");
```

**长于 `GZ_OL_FRAME_LEN_MAX` 但结构合法的帧怎么办？** 两种方案（**推荐 B**）：

- **A（简单）**：probe 对 `len > 256` 直接 FAKE → 逐字节重同步。风险：帧内数据段若含 `0x54 43 4C 59` 可能被重新认领（概率极低且自愈），但会产生逐字节抖动。
- **B（推荐）**：probe 对 `17 ≤ len ≤ 767` 一律判"结构合法"；`len > 256` 时返回 **`PROTO_PROBE_SKIP`** 并写 `*total_len = len`（框架 `rb_skip` 整帧消费、不入队、不处理）。这样超长帧被**干净消费**，不污染重同步路径，也不占队列。

> 队列深度取 **3** 的理由：文档明确要求"缓存 + 先到先处理"；本协议 0x20 显示帧为**单向无应答**，上位机会连续下发多帧（换行/多行刷新），深度 3 与既有地区协议一致，单槽 264B 属小体量。

```
其他     → COLOR_RED         ← 0x20 默认；0x80 时源固件"不动屏幕"（Q7 一并裁决）
```

**字号映射**：`16/16→FONT_16`、`24/24→FONT_24`、`32/32→FONT_32`，**其余回退 `FONT_16` 并整帧忽略**（源固件此处为未定义行为，**必须比源固件更严格**，不可复制缺陷）。

**字体映射**：`"宋体"→FONT_ST`、`"仿宋"→FONT_FS`、`"楷体"→FONT_KT`、`"黑体"→FONT_HT`、未命中 → `FONT_ST`（与源固件一致）。

> **实现前置检查**：字库可用性。STD 的 `app_render` 按当前激活字库芯片配置取用三元组 —— `FONT_CHIP_W25Q64` 支持 16/24/32（**与源固件字库档位完全对齐**）；`FONT_CHIP_MX25L256` 为 14/16/20/24/32。若运行在 MX25L256 配置上，`FONT_32` 不存在 → `_find_region` 回退首项（渲染结果与预期不符）。**建议在模块头注释中标注该依赖**，并在实机联调时确认 DIP2 档位。

### 4.5 任务栈与绑定通道

| 项 | 建议 | 理由 |
|---|---|---|
| 处理任务 | `gz_ol_handle_task`，`stack_size = 256 * 4`（1 KB），`osPriorityNormal`，帧缓冲 **`static`** | 与青海/贵州/云南/四川/安徽完全一致（`doc/08-04` Step 3/8）；栈从 `ucHeap` 支出，**不计入 `.bss`** |

## 8. 待用户裁决的问题清单（14 条）

> 格式：**问题 / 选项 / 推荐及理由**

### Q1 — 帧长上限（入队 payload 上限）
- **选项**：A) 256 B（余量 1.6×）；B) 512 B（余量 3.2×，静态 +768 B）；C) 128 B（贴实测上限，无余量）。
- **推荐：A（256 B）**。理由：实测合法最大帧 158 B（FONT16 + 124 B 文本上限），256 已有 1.6× 余量；B 多付 768 B 静态 SRAM 无收益且 SRAM 本就紧张；C 会拒绝正常长帧。配 **SKIP 消费 >256 的结构合法帧**（§4.3 方案 B）。

### Q2 — `0x10` 故障查询是否应答
- **选项**：A) 应答 2 B `0x00 0x00`（无故障）；B) 完全静默（复现源固件）；C) 应答真实硬件状态位。
- **推荐：A**。理由：文档要求应答且明确"无此故障硬件的位补 0"，STD 硬件无对应故障采集点 → `0x0000` 是**合规且诚实**的答案；源固件的静默会让上位机故障轮询超时（源侧缺陷，不应复制）。C 需要新增硬件故障采集，超出本次范围。

### Q3 — `0x50` 是否作为入站命令接受
- **选项**：A) 严格按文档：`0x50` 仅作**出站**应答命令字，入站忽略；B) 兼容源固件：入站 `0x50` 触发搜索应答（回 `0x70`）；C) 入站 `0x50` 与 `0x60` 都触发搜索应答。
- **推荐：C**。理由：文档定义 `0x60` 为搜索命令、`0x50` 为应答帧命令字；源固件把 `0x50` 当搜索触发。上位机版本不明（测试软件中**未找到"搜索设备"UI 字符串**，仅见"修改IP地址"）→ 同时接受 `0x60` 与 `0x50` 可覆盖文档版与固件版上位机，**零额外成本、无副作用**（真正的 `0x50` 应答帧不可能被主机回发给设备）。

### Q4 — 搜索应答 `0x70` 的发送方式
- **选项**：A) 单播回源（STD `channel_send` 语义）；B) 广播（复现源固件 `myUdpSendDtatBroadcast`，仅 UDP 通道可行）；C) 串口通道单播回源 + UDP 通道广播。
- **推荐：A（先），C（若联调证明上位机依赖广播）**。理由：STD 的 UDP 通道 `udp_ch_send` 回源 IP:PORT（`app_udp.c:96-108`），这也是标准做法；源固件固定发往对端 10028 口并广播属于其私有约定。**建议以 A 起步，联调时用真实上位机验证**；如需广播需显式调用 `app_udp_broadcast`（须先绑定 `CH_ID_UDP`）。

### Q5 — `0x40` 修改 IP 的落库对象与重启策略
- **选项**：落库 A) `app_board_net_cfg_update()`（STD 中立配置，Sector1）；B) 自建 W25Qxx 私有记录（复现源固件）。重启 C) 应答后 `NVIC_SystemReset()`（复现源固件）；D) 仅应答、不主动复位（STD LDI 0AH 约定，重启后生效）。
- **推荐：A + C**。理由：A —— STD 已有唯一网络配置真源（Sector1 `net_cfg`）与统一应用路径（`app_net_boot_apply`），自建 W25 记录会造成**双配置源冲突**（源固件的 `"setip"` 幻数记录正是 STD 已淘汰的旧模式）。C —— 源固件明确"应答后软复位"，且 STD 约定改 IP 统一"重启生效"，主动复位最贴近现场行为。**注意端口字段语义**：STD `NetConfig` 有 `port`（TCP 业务口，默认 9528）与 `udp_port`（CQ UDP 专有，默认 20103）两个字段，而本协议的 port 语义是"设备自身 UDP 口"→ **需用户明确写哪个字段**（建议写 `port`，不触碰 `udp_port`）。

### Q6 — `0x80` 全屏显示的"关自动调光 + 亮度 8"副作用
- **选项**：A) 完整复现（关光敏任务 + 亮度 8）；B) 只填充颜色，不动亮度；C) 复现但限制为"仅亮度 8、不挂起光敏任务"。
- **推荐：A**。理由：这是现场设备**可观察行为**（全屏显示时强制最亮，便于治超屏在强光下可读），且与协议"立即显示"意图一致；实现成本仅两行（`osThreadSuspend` + `dev_display_set_brightness`），STD 已有 SC_OL 的先进先例（`app_sc_ol_proto_cmd.c` 亮度处理）。同时建议**保留"收到任何数据即恢复自动调光"**的源语义（`osThreadResume`）。

### Q7 — 颜色映射（`00 00 FF` → 黄 还是 蓝？其余颜色如何处理？）
- **选项**：A) 复现源固件：`FF0000→红`、`00FF00→绿`、`0000FF→黄`、其余→红（`0x80` 时其余→不改屏）；B) 按文档语义：`0000FF→蓝`，其余→黑/不改；C) 完整 24 位 → 8 色最近邻映射。
- **推荐：A**。理由：**"功能等效于源固件"是本任务的首要验收标准**；现场操作员看到的"蓝=黄"是既有事实，改成蓝反而与现场不一致。**注意**：STD 的 `display_color_t` 与源 `hub75_color` 枚举**完全同构**（`black=0,red=1,green=2,yellow=3,blue=4,purple=5,cyan=6,white=7`），因此映射表可直接 1:1 书写。若用户希望"未来切换到全彩"再考虑 C（需要色域映射策略，本次不建议）。

### Q8 — 换行符识别范围（`0x5C 0x6E` 字面量 `\n` 与 `_` 下划线）
- **选项**：A) 只认 `0x0A`（并跳过 `0x0D`）—— 交给 `app_render` 原生行为；B) 复现源固件：额外把 `0x5C 0x6E`（`\n` 两个字面量）与 `_`(0x5F) 预翻译为 `0x0A`；C) 预翻译开关做成宏，默认关。
- **推荐：A（先）/ C（若联调证明上位机发字面量 `\n`）**。理由：STD 渲染引擎已原生支持 `0x0A` 换行、`0x0D` 跳过（四川 MTC/贵州既有裁决），`0x0A 0x0D` 对自然覆盖；而把 `_` 当下划线文本字符误当换行符，**会破坏含下划线的正常文本**（风险大于收益）。建议联调时用真实上位机抓帧决定。

### Q9 — 屏宽/屏高字段是否采纳
- **选项**：A) 忽略（复现源固件，始终用 `dev_display_get()` 实际几何）；B) 采纳包内值作为渲染区域。
- **推荐：A**。理由：源固件忽略；STD 全协议既有裁决一致（"坐标上限以模组驱动实际屏幕尺寸为准，协议文档不作为标准"）。采纳包内值会导致上位机发错尺寸时显示区域被裁剪成一块，且与其它协议不一致。

### Q10 — 通道绑定范围（是否绑 UDP）
- **选项**：A) Phase 1 仅 `CH_ID_RS485` + `CH_ID_RS232`；B) 直接三通道（+ `CH_ID_UDP`）。
- **推荐：A（先）**。理由：串口双通道即覆盖源固件串口三路行为；UDP 绑定会把 IP 配置/搜索/广播语义引入 RJ45 共享槽（与 IAP/LDI/CQ 同槽，虽然首字节不冲突，但会多一份 `0x40` 写网络配置的入口，与 Q5 强耦合）。**建议以 A 交付，Q4/Q5 结论明确后再评估 B**。

### Q11 — 是否实现上电默认画面
- **选项**：A) 实现（3 行绿字「贵州省 / 高速公路 / 欢迎您!」，FONT16）；B) 不实现（使用固件默认欢迎画面）；C) 实现但内容改为「贵州省治超屏」等新文案。
- **推荐：A**。理由：源固件有该行为，属"功能等效"组成部分。**但必须提示副作用**：`app_default_display_register` 是**单槽、首个注册生效**，全协议 dev 构建下会与山东（`app_sd_proto_default.c`）等注册者竞争（归属由 initcall 链接序决定）；量产单协议无竞争。若用户不接受该副作用 → 选 B。

### Q12 — 内存放置策略（SRAM 还是 CCMRAM）
- **选项**：A) 队列体+cb+帧缓冲置 **SRAM**（+1156 B，与青海/贵州/云南/安徽一致）；B) 置 **`.ccmram`**（+0 B SRAM，CQ 先例）；C) 先腾挪 SRAM 再走 A。
- **推荐：B**。理由：**关键新事实** —— `doc/06-04`/`CLAUDE.md` 按 1-263 = 224×128 记账（CCM 65516 满），但**当前 `dev_display_1_263.c:35-38` 实为 224×64**，CCM 实际仅用 29568 B、**空闲 ≈ 35.9 KB**；而 Makefile PROTO=ALL 的 SRAM 余量按文档仅 ~536 B（**不足以容纳 1156 B**）。因此 B 是**唯一零风险**选项，且 CCM 对协议队列（CPU 独占访问、无 DMA）完全适用。若用户坚持"与青海/贵州/云南同 SRAM"原则 → 选 C，但需先明确腾挪来源（另开裁决）。**⚠️ 若 `dev_display_22_1703` 显存占用 > 34 KB，B 的可行性需重估**（§6.3）。

### Q13 — 与安徽动态滚动的同屏共存渲染互斥
- **选项**：A) 本模块静态渲染**不参与** `app_scroll_render_lock`（当前默认）；B) 本模块 0x20/0x30/0x80 的"清屏+渲染+commit"整段持 `app_scroll_render_lock`（与安徽 0x81/0x85 同纪律）。
- **推荐：B（若两协议可能同编同屏）**。理由：安徽为 `0x5A` 帧族、贵州治超为 `0x54` 帧族，**二者不互斥、可同编共存**；若同一物理屏上两种协议都有流量，滚动渲染与静态全屏渲染并发会产生黑条（doc/13 ⑤ 记录的现象）。若用户确认量产只跑单协议 → A 亦可（零成本）。**代价**：B 需 include `app_scroll.h` 并引入一次锁开销。

### Q14 — 命令字非法时的行为
- **选项**：A) 静默丢弃（`GZ_OL_PARSE_ERR_CMD`，与四川治超一致）；B) 记录 RTT 日志便于联调；C) 回"不支持"应答（协议未定义该应答格式）。
- **推荐：A + 联调期临时 B**。理由：协议未定义错误应答格式（C 会造成上位机解析混乱）；A 与既有协议一致。联调期可临时加 RTT dump 并在验收前删除（`doc/08-04` Step 7 纪律）。
