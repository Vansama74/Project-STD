## 3. 「10028 无响应、10011 正常」的全部可能状态 + 判别签名

| 状态 | 机理 | 唯一可观察签名（RTT / 网络） |
|---|---|---|
| **A. 板上镜像无专用实例**（旧构建，如 16:02 EIDE 产物） | 端口只迁 TCP 业务口；UDP 由固定的 10011 承载 → 10028 上根本没有 socket | **RTT 完全没有 `[diag]` 横幅**（旧镜像无该设施）；`0x70` 回显 = **10028（记录写成功了）**；TCP 连 10028 **通**、TCP 连 9528 不通；UDP 10028 无应答 |
| **B. 记录在启动时被判非法 → `accept_write` 把 port 改回默认** | ① `0x40` 帧 IP 字段写成 `0.0.0.0`（只想改端口）→ 记录 magic/CRC 有效但 IP 全 0 → 重启判非法；② 记录 CRC 坏；③ port 写成 0 | **`[diag] netcfg INVALID at boot (record ok but net invalid): ip=0.0.0.0 port=… port=… -> accept_write defaults`**（本轮新增，`app_net_boot.c`）；`[gz_ol] 0x40` 的 `requested` / `readback` 行显示 0x40 时确实写进了 10028；`0x70` 回显 **9528**（被覆盖）；UDP 9528 有应答、10028 无 |
| **C. 端口值落进设计分支**（10011/20103 → `SKIPPED`；0/非法 → `FALLBACK(9528)`） | 与常驻 UDP 口同号 → 跳过绑定（10011 场景 GZ_OL 仍由 `CH_ID_UDP` 承载，功能不受损） | `[diag] chan gzol=… port=… bind=SKIPPED(...)/FALLBACK(...)`；`[gz_ol] UDP service port … busy … -> skip bind` |
| **D. 绑定了但网络/测试侧不通**（IP 被同帧改到别的网段、测错 IP；或 10028 被上位机防火墙/路由挡） | 记录与绑定都正确 | `[diag] chan gzol=UP port=10028 bind=OK` **且** `netcfg readback port=10028`；**此时对 10011 也是「能通」的**（说明 IP 可达）→ 若两者同一 IP 而 10028 不通，则排除 D |
| **E. 端口字段字节序不匹配**（2026-09-14 定案＝当时根因，见 §8；**2026-09-15 用户裁决后转为设计口径：固件改高字节在前 BE16，见 §8.8**） | 当时固件按小端 LE16 解析，上位机发 `27 2C`（10028 高字节在前）→ 解析为 **11303** → 记录/绑定都是 11303；发 10028 无响应；10011 是常量口不受影响。**裁决后相反对齐**：`27 2C` 即 10028（生效），`2C 27` 才是 11303 | **裁决前**：`[gz_ol] port field payload[12..13]=27 2C -> 11303 (LE16)`；**裁决后**：同一帧打 `…=27 2C -> 10028 (BE16)` |
| **F. 核心代码缺陷**（本报告 §2 已逐段排除） | — | 若 A~E 全部排除后再回到代码（用 `[gz_ol]`/`[diag]` 行定位到具体层） |

**优先级**：A（镜像陈旧，最可能：症状与修复前**完全一致**）> B > C > D > **E（2026-09-14 实机定案＝本例根因）** > F。
（**2026-09-14 修订单**：原表 E 为「核心代码缺陷」，因实机定案新增 E 类，原 E 顺延为 F，原优先级链同步顺延；
