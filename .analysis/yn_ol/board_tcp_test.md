| 09:34:55.169-170 | B 立即收到 **5 帧** `7B 31 01 00 7D`（+1.2~2.0ms） | **恢复，无需重启板子**；此后 B 每次查询均 +0.4ms 正常 |

**小结（分叉结论 2）**：
- 半开期间 **30s 内 6 次查询全部零应答**，板子对这 30s 的孤儿连接**没有任何自愈手段**（无 keepalive、`netconn_recv` 无超时、TCP 通道不注册链路监听——与上一轮只读排查报告一致，本轮为实机实证）。
- 但只要**任何一个能证明连接已死的报文送达**（本例 = 我方内核的重传 FIN），服务循环立刻释放并补发积压应答。⇒ **「只有半开连接才需重启」的准确表述是：只有当对端从此永不发包（拔线/断电/进程消失且无重传到达）时，串行循环才会被永久占住、且板子自身无任何超时能救它**；普通上位机的 FIN/RST（含重传）最终都会送达→自愈。**「任何送达的关闭都能让循环恢复」成立。**

## 6. 【本轮新增·更重要】板子自身周期性整体死机（~30s 后看门狗复位）

实测过程中捕获到 **4 次**「板子 TCP + ICMP 全死 → 约 30s 后自愈」事件。第 3 次有**报文级重启实证**：

**watch 实验（09:42:07 起，单条长连接 + 每 10s 查询 + 每 2s ping，全程抓包）**
```
板子自身 1Hz ARP 心跳（who-has 192.168.114.1）：
    ...连续... 09:43:05.804     ← 最后一次心跳
    ===== 空窗 32.0s（板子完全静默） =====
    09:43:37.723  ARP who-has 192.168.114.200 tell 192.168.114.200  ← 自身/重复地址 ARP = 刚启动的栈
    09:43:37.814  ARP who-has 192.168.114.1   tell 192.168.114.200  ← 心跳恢复
    09:43:38.782  ARP who-has 192.168.114.17  tell 192.168.114.200  ← 回头解析我方地址（ARP 表已空）
    09:43:38.783  ICMP echo reply 恢复（ping 中断 30.0s）
期间：我方 ping 请求、我方对该 IP 的 ARP 请求（09:43:13.8/14.8/15.8）均无任何回应
```
**解读**：板子自身的 ARP 心跳停 32.0s + 恢复时 ARP 表为空 + 自问自身 IP ⇒ **板子发生了复位/重启**；32.0s 与 IWDG 配置（prescaler 256 × reload 4095 ÷ ~32kHz ≈ **32.8s**，`Core/Src/iwdg.c:41-42`）吻合 ⇒ 典型「死机 → 看门狗复位」。重启后旧 TCP 连接全部失效（我方旧 socket 收到 RST / 报 `EPIPE`）。

**四次事件与触发规律**

| # | 实验 | 事件时刻 | 死机时长 | 证据强度 |
|---|---|---|---|---|
| 1 | 步骤 4 半开（恢复爆发后） | ~09:34:56 | ~44s | TCP 三次 connect 超时（09:34:59.6、09:35:02.6）+ 一次 EHOSTUNREACH + 09:35:40 恢复 |
| 2 | burst（积压 6 条集中应答后） | ~09:38:30 | ~30s | ping 09:38:32.3 起 FAIL、10028 在 09:39:00.79 回 RST（新栈无监听）、09:39:02.8 全恢复 |
| 3 | **watch（长连接持续查询）** | 09:43:05.8 | **32.0s** | **抓包实证：心跳断 32.0s + 启动签名 ARP + ARP 表空** |
| 4 | **hold（长连接 + 每 10s 查询）** | 09:55:14.8（连接建立后 **+42.2s**） | **30.0s** | ping 死亡/恢复、旧连接被毁 |

**4 次事件全都出现在「一条被 accept 的 TCP 连接存活较久（约 40~60s）且其上有点查询/应答流」的场景**；以下对照实验**均未**触发：

| 对照实验 | 连接寿命 | 单连接应答数 | 结果 |
|---|---|---|---|
| 无 TCP 流量（liveness 300s，板子 1Hz ARP 心跳连续 309 包无空窗） | 无 | 0 | **不崩** |
| 静默长连接 hold2（**150s 一个字节不发**） | 150s | 0 | **不崩** |
| quick5（同一新连接快速连发 5 次查询，寿命 4s） | 4s | 5 | **不崩** |
| churn（20 轮 connect→1 次查询→close） | 每条 ~2s | 1 | **不崩** |
| repro（6 条连接共 11 次查询） | 最长 13s | ≤3 | **不崩** |
| 步骤 4 半开（A/B 存活 53~55s，B 收到 5 帧集中应答） | 53~55s | 5 | **崩（#1）** |
| burst（A/B 存活 35~41s，B 收 5 帧集中 + 2） | 41s | 7 | **崩（#2）** |

⇒ 经验触发条件（待靶上定位根因）：**连接被服务且存活约 40s 以上时，其上的查询/应答流会触发整体死机**；单纯「连接存在」（哪怕 150s 静默）或「短寿命连接上的应答」都不触发。**根因未能在板外定位**（见 §8 局限）。

## 7. 背景观察：板子 1Hz「连不上的 TCP Client」ARP 风暴（旁证/风险）

- 抓包显示板子**持续以 1Hz 向网关 `192.168.114.1` 发 ARP 请求且永不应答**（watch 240s 内 209 次、liveness 300s 内 309 次 ≈ 1/s）。
- 代码对上：`Application/Src/Channel/app_tcp_client.c:87-88` 默认目标 `192.168.2.17:9529`（跨网段、本网络无网关 ⇒ 不可达），`:136-204` 为「非阻塞 connect → 失败 → `netconn_delete` → `osDelay(1000)`」的 **1Hz 重试循环**，每次重试都要解析网关 ⇒ 与 1Hz ARP 风暴一致。
- 相关风险点（**未在本轮直接触发，列为待查**）：`Platform/Inc/lwipopts.h` 未覆盖 `MEMP_NUM_TCP_PCB` ⇒ 取 LwIP 默认 **5**（`opt.h:436`），而 `MEMP_NUM_NETCONN=8`（`lwipopts.h:134`）；LwIP 2.1.2 有 TIME_WAIT（2×TCP_MSL=120s，`tcp.c:1438`）会占用 pcb。频繁 connect/断开场景下 pcb 池耗尽是现实风险（现场若出现「connect 超时但 ping 正常」应优先查这里）。

## 9. 最终判定（对现场问题）

1. **头号机理（串行单客户端服务循环被占位）已实机证实**：新连接握手成功（0.3ms）但应用层零应答；被占位连接照常工作；被占位期间的数据积压在板子 LwIP recvmbox，循环一旦释放即成批补发。
2. **恢复条件**：「任何送达的 FIN/RST 都能让服务循环恢复」——**成立**（FIN、RST 两变体均实测通过）。**需要重启板子的唯一天花板条件是「对端从此永不发包」的孤儿/半开连接**：此时无 keepalive、无 recv 超时、无链路监听，30s 实测零自愈，逻辑上永久占位。
3. **现场问题更可能是「第二机理」主导**：板子自身在被服务的长连接（≥~40s）+ 查询流下会**整体死机 ~30s 后由看门狗复位**（4/4 复现、报文级重启实证）。死机期间：新连接**根本建不起来**（connect 超时）；已有的连接全部作废（重启后对旧连接的数据会被 RST）。上位机若不在重启后**重新 connect**，界面仍显示「已连接」而任何数据都无响应——与现场「连上没反应，重启板子再重连才行」完全吻合（用户手动重启=恰好完成了一次新会话）。
4. **建议动作**：
   - P1（最高）：带 RTT 复跑最小复现（hold：连上后每 10s 发一次 `'1'`；或 burst：A 占位、B 积压 6 条后关 A），抓死机前的 `[err]`/断言/堆水位与重启后的 `[diag]` 横幅，定位 §6 根因；必要时同时排查 `app_tcp_client.c` 1Hz 重试循环与 pcb/netconn 池（`MEMP_NUM_TCP_PCB=5`）。
   - P2：TCP Server 服务循环加固（keepalive 或 recv 超时或 link-down 监听），否则孤儿连接仍会永久占位（上一轮报告 §6 的 P1 清单结论不变）。
   - P3：上位机侧核查——断线（RST）后是否真的会**重新 connect**；否则任何板子重启都会表现为「连上但没反应」。
