## 1. 协议摘要（逐节提取 + 原文依据）

### 1.1 帧格式

| 项 | 结论 | 原文依据 |
|---|---|---|
| 帧头 | `0xFF 0xDC`（2 字节，所有命令统一） | §2.1~§2.10 各表「Message start 信息开始 0xFF 0xDC」 |
| 长度字段 | **1 字节 = 整帧总长**（含 2 字节帧头与末尾 BCC），大小端无关 | §2.2/2.3/2.4/2.5/2.7/2.10 均 `Length=5`，而各帧字节数恰为 2(头)+1(len)+1(cmd)+1(BCC)=5；§2.1 `Length = 10+N*16` = 9 字节头 + N*16 内容 + 1 BCC；§2.11 示例 `FF DC 05 44 → BCC=0x62` 亦为 5 字节整帧 |
| 命令字 | 1 字节（ASCII 字母） | §2.1~§2.10 表「Type of command」 |
| 载荷 | 变长（按命令） | 同上 |
| 校验 | **BCC = 除 BCC 字节外所有字节逐个 XOR**（覆盖帧头、长度、命令、载荷） | §2.11「BCC 是每个消息字节的 XOR」+ 示例 `0xFF^0xDC^0x05^0x44=0x62`（实测该式成立） |
| 定长/变长 | 头部定长（4 字节：FF DC Len Cmd），帧长由 Len 字段定界 | §2.1~§2.10 |
| 帧长上下限 | **5 字节**（无载荷命令：`FF DC 05 xx BCC`）~ **74 字节**（文本 4 行：`10 + 4×16`） | §2.1/§2.2 |
| 转义/特殊字节 | 无转义、无字节填充；BCC 允许 0x00~0xFF（即可能出现 0x00，不能以 0x00 作定界） | §2.11「BCC 0x00 ~ 0xFF」 |

> **长度语义的推导（重要，probe 判据依据）**：三种解读里只有「Len = 整帧总长」能让全部命令自洽——心跳 `05` ↔ 5 字节；文本 `10+N*16` ↔ 9 字节头 + N×16 内容 + 1 BCC；预设语音（若语音编号为 1 字节）`08` ↔ 8 字节。**该结论也是探针唯一的长度判据来源。**

### 3.2 常量与 probe 判据（草案）

```c
#define XJ_STX0 (0xFFU)              /* 帧头 1 */
#define XJ_STX1 (0xDCU)              /* 帧头 2 */
#define XJ_LEN_OFFSET (2U)           /* 长度字段 = 整帧总长 */
#define XJ_CMD_OFFSET (3U)
#define XJ_FRAME_LEN_MIN (5U)        /* 无载荷命令 */
#define XJ_FRAME_LEN_MAX (74U)       /* 文本 4 行 = 10 + 4*16 */
#define XJ_QUEUE_DEPTH (3U)
#define XJ_PAYLOAD_MAX XJ_FRAME_LEN_MAX
#define XJ_MSG_SIZE (sizeof(frame_msg_t) + XJ_PAYLOAD_MAX)
_Static_assert(XJ_FRAME_LEN_MAX <= RB_SIZE_RS232, "XJ frame must fit RS232 RB");
_Static_assert(XJ_FRAME_LEN_MAX <= RB_SIZE_RS485, "XJ frame must fit RS485 RB"); /* 若绑 RS485 */
```

probe 判定链（**PURE、只 peek**；顺序即隔离策略，见 §4 Q2）：

1. `avail == 0` → **FAKE**
2. `[0] != 0xFF` → **FAKE**
3. `avail < 3` → **WAIT**
4. `[1] != 0xDC` → **FAKE**（← 与 RLS `FF FE`、MM `FF E0` 在此分道）
5. `len = [2]`；`len < 5 || len > 74` → **FAKE**（← 四川治超 `FF DC…` 若把 0xDC 当长度会落在 220 > 74，此处一次性排除）
6. `avail < 4` → **WAIT**；`[3]` 不在 ASCII 命令白名单 `{'T','O','E','F','J','K','V','S','C'}` → **FAKE**（← 四川治超命令字 `0x80~0xB9` 在此排除）
7. `avail < len` → **WAIT**
8. `XOR([0..len-2]) != [len-1]` → **FAKE**（← 第三重保险；IAP/LDI 已有「校验和放 probe」先例）
9. → **READY**，写 `*total_len = len`

> 说明：第 5/6 步刻意放在「等齐整帧」之前，保证见到四川治超的长帧（长度字段 0xDC、需 220B）时**立刻 FAKE 而不 WAIT**，不把任何等待预算摊到别的协议头上；广东治超（GZ_OL，0x54）与 `{` 族、ETC、安徽等按首字节早已 FAKE。
> 残余误判概率：理论最大值 ≈ 治超帧恰以 `FF DC` 开头且第 4 字节恰为 9 个 ASCII 白名单字母之一且 BCC 恰好吻合 ≈ `9/256 × 1/256 ≈ 1.4e-4`，且要求该治超帧的第 2 字节（长度）**恰为 0xDC 且 ≤ 74**——与「长度=0xDC=220」互斥，实际为 0（治超命令字集合内无 ASCII 字母）。

### 3.3 通道绑定、队列与内存放置

## 4. 帧头冲突分析（逐槽）

既有首字节集合（`doc/05-01` §3.3 + 兼容矩阵；仅列实际可能出现在该槽的协议）：

| 槽 | 既有协议 → 首 1~4 字节特征 | 与 `FF DC` 的关系 | 隔离手段 |
|---|---|---|---|
| **RS232**（USART3） | ETC `0A…0D`；安徽 `5A 01 …A5`；`{` 族（QH/SD/GZ/YN/SC_MTC/YN_OL）`7B…7D`；**四川治超** `FF + 长度(07~FF，排除 FE) + 命令 + … + BCC + FF`；**缅甸 MM** `FF E0…`（定长 20B） | ETC/安徽/`{` 族：首字节不同 → **FAKE，零风险**；MM：第二字节 `0xE0 ≠ 0xDC` → **FAKE，零风险**；**四川治超：唯一重叠**（`0xDC` 是其合法长度值） | ① 治超对 `FF DC` 判 **WAIT**（链式契约继续试下一协议，不消费）；② 新疆以 `len>74` 或命令字白名单（治超命令 `0x80~0xB9` 无 ASCII 字母）**FAKE**；③ BCC 第三重校验；④ 若新疆优先注册则直接 READY 消费 |
| **RS485**（USART1） | 同上 + **RLS** `FF FE …` + **GZ_OL** `54 43 4C 59` | RLS：第二字节 `0xFE ≠ 0xDC` → **FAKE**；GZ_OL：首字节 `0x54` → **FAKE**；治超：同上 | 同 RS232 行 |
| **网口**（RJ45 共享槽，若绑） | IAP `5A5A5A5A`；LDI `FF FF`；CQ JSON `7B` / 12B `FF FF`；GZ_OL `54…`；YN_OL `7B…` | LDI 第二字节 `FF ≠ DC` → FAKE；CQ 12B 需 `FF FF` → FAKE；其余首字节不同 → FAKE | 建议**不绑网口**（文档为 RS232；且网口槽另有 netconn/RB 语义成本） |

**结论**：`0xFF 0xDC` 作为「两字节前缀」在同槽协议中是唯一的（只有四川治超把 `0xDC` 当长度值造成一字节层面的重叠），且存在三重独立隔离（长度范围 >74、命令字白名单、BCC）。**无需 EIDE 目录互斥**；但 `doc/05-01 §6` 兼容矩阵仍应新增一行（「新疆 + 四川治超（`FF` 重叠）：允许，判据 = 第二字节 `0xDC` + 长度 ≤74 + 命令字白名单 + BCC」）。

## 5. 问题与裁决清单（按重要性排序）

> 标 ★ = 动工前必须拍板；其余可在实现中按推荐值先做、后续调整。

### ★Q1【阻断级】注册掩码槽位已满：`PROTO=ALL` 32/32

**事实（代码核对）**：`app_proto_register()` 在 `registered_mask`（`uint32_t`，`PROTO_MAX_COUNT=32`）满位时**返回 0**；各模块 `init` 见 0 即 `return`，**无任何日志**。全仓 `app_proto_register` 调用点：

| 模块 | mask 数 | | 模块 | mask 数 |
|---|---|---|---|---|
| IAP | 1 | | SC_OL | 2 |
| LDI | 3 | | SD | 2 |
| CQ | 2 | | GZ | 2 |
| QH | 2 | | YN | 2 |
| SC_ETC | 2 | | ANHUI | 2 |
| SC_MTC | 2 | | GZ_OL | 4 |
| RLS | 1 | | YN_OL | 4 |
| MM | 1 | | **合计** | **32** |

（AH_MQTT 的 1 处已注释停用。）⇒ `PROTO=ALL` 口径下新疆模块**无法注册**；`PROTO=CQ` 口径因剔除 LDI 只剩 29 个，尚有 3 槽。

- 选项 A：**框架扩容 32 → 64**（`proto_mask_t`/`registered_mask`/`ch_proto_map[]` 改 64 位 + 新增 `bit_ctz64` + `1ULL<<i` + `PROTO_MAX_COUNT 64`）。改动集中在 `app_dispatch.h/.c` + `bit_utils.h`，协议模块代码零改动；代价 ≈ 数十字节 bss。
- 选项 B：**收敛既有 mask 数**（腾 1~3 槽）：如 YN_OL 的 TCP_S/TCP_C 两 mask 合并为「1 mask 绑 2 通道」（同一 RJ45 RB、同一 probe、同一队列，返回值靠 `msg->ch` 回源，机制上可行）；GZ_OL 的 UDP/GZ_OL 同理。**注意**：doc/08 明确记「每逻辑通道独立 mask（LDI 先例），禁止单 mask 绑多通道」，属惯例而非硬约束，需用户裁决并同步改文档。
- 选项 C：**维持现状**——新疆只在 `PROTO=CQ` / EIDE 口径编入，`PROTO=ALL` 开发构建里不注册（= 该构建下无法联调）。
- **推荐：A**。理由：32 槽已用满，任何后续新协议都会撞同一堵墙；扩容是干净的一次性投入，且不动任何已验证模块。若用户不愿动框架，退而求其次选 B 中代价最小的一处（YN_OL 两 TCP mask 合一，腾 1 槽）。

### ★Q2 通道绑定集合

- 选项 A：**仅 RS232（1 mask）**；B：RS232 + RS485（2 mask）；C：+TCP Server/Client（4 mask，网口）。
- **推荐：A（起步）**，现场确有 RS485 需求再补一个 bind。理由：文档明示 RS232；mask 槽位紧张（Q1）；`FF DC` 在三个槽上都有完整隔离（§4），后续扩展零返工。**请用户确认现场接线（费显侧是 RS232 还是 RS485）。**

### ★Q3 文本显示的行拆分与「显示行」字段

- 选项 A：**严格按 16 字节/行切行**（最多 4 行，逐行渲染，行高 = 字号），`[5]` 显示行字段**忽略**；GBK 双字节跨 16B 边界时把边界后移 1 字节。
- 选项 B：整段内容交渲染引擎 `word_wrap=true` 自动按屏宽换行（忽略 16B 规则与 `[5]`）。
- 选项 C：把 `[5]` 当起始行号（0 = 顶部）。
- **推荐：A**，并把「`[5]` 恒为 0」当既定事实（若厂商确认有其他取值再改 C）。理由：16B/行 = 8 个汉字，配 FONT_16 在 224 与 128 两种屏宽上刚好整行，是最忠实的复刻；B 会在宽屏上把上位机想要的两行拼成一行。**字号/字型建议 FONT_16 / FONT_ST。**
- 附带：`'T'` 帧到达时**先清屏再按行渲染**（推荐，避免残影；`'C'` 才是协议意义上的全清）；行内容尾部 0x00/0x20 填充按「去尾后为空则该行不画」处理。

### ★Q4 颜色与亮度映射

- **颜色**：推荐**位掩码映射**——`R≥128 → bit0`、`G≥128 → bit1`、`B≥128 → bit2`，与 `display_color_t` 枚举天然同构（1 红 / 2 绿 / 3 黄 / 4 蓝 / 5 紫 / 6 青 / 7 白）；三通道全 0 = 黑（不画/擦除）。阈值 128 可否决（可选「>0 即算」）。
- **亮度**：推荐 **0 = 恢复光敏自动调光；1~255 均匀映射为 8 档**（`level = 1 + (v-1)*7/254`，v=255 → 8 最亮）；每次收到 `'T'` 帧都按该帧取值设置（非 0 时挂起光敏任务）。备选：恒等线性映射 0~7（v=0 → 关屏，风险高）或忽略该字段。
- **推荐理由**：与本项目已裁决的同类语义（安徽 0x92「0=自动、1~999→8 档」、YN/YN_OL「0=自动、1~8 手动」）保持一致，现场行为可预期。

### ★Q5 心跳超时故障屏

- 选项：实现与否 / 阈值 / 文案 / 恢复条件 / 是否编译开关。
- **推荐**：实现；阈值 **15s**（= 文档 5s 的 3 倍，容忍上位机节拍抖动；文档「超过 5 秒」按严格值会在 5s 边缘闪烁）；文案默认 **红字「系统维护中」居中**（编译期宏可改，对应文档「可由出厂软件设定」——本设备用宏近似）；**收到任意有效帧即清除**；编译开关 `XJ_FAULT_SCREEN` 默认 **1**（车道协议，故障屏是文档硬要求），与 `CQ_FAULT_SCREEN` 同款语义（共存构建若出现互相踩屏，可在 EIDE 侧关掉本开关）。
- **需用户确认**：15s 是否可接受；文案是否就是「系统维护中」四个字（维语？本项目语音/显示字库为 GBK，维文字库不存在 → 显示只能用中文）。

### ★Q6 语音能力边界（文档要求 vs 硬件）

- 事实：`dev_rs232_voice` 只有「自由文本 TTS（GBK）+ 音量」两个接口，**没有**男声/女声、汉语/维语/双语、语音编号（段号）接口；且设备无维文字库/维语 TTS。
- 选项 A：**`'V'` 全实现**（文本透传语音板，忽略男/女声字段；音量 0x30~0x37 映射到板载档位），**`'S'` 用「编 号→中文文案」固定表近似**（0x31 您好 / 0x32 祝您一路平安 / 0x33 ETC 车辆，请通行 / 0x34 ETC 写卡失败，请领取通行卡 / 0x35 ETC 交易失败，请转人工处理；未知编号忽略）；B：只做 `'V'`；C：语音全不实现。
- **推荐：A**（但须用户确认「维语/双语」不要求，或现场有别的语音板）；若确认现场必须出维语，则本板硬件无法满足，需要升级语音板——**这属于项目级风险，越早暴露越好**。
- 附带待确认：音量字节两处（`'V'`/`'S'`）都是 `0x30~0x37` ASCII，板载音量档位映射表（现有先例：贵州 1~5 → {1,3,5,7,9}）需现场校准。

### Q7 上电默认画面

- 选项 A：**不注册**专用画面（走 STD 现有默认显示链路，同 YN/YN_OL）；B：上电即渲染红色「系统维护中」直到收到首帧（与 Q5 语义自洽：上电必无心跳）；C：注册地区欢迎画面（文案待定）。
- **推荐：B（若 Q5 = 实现）/ A（若 Q5 = 不实现）**。理由：文档只说超时要显示维护中，上电到首帧之间本质就是「超时」，B 零额外代码且现场表现最合理。

### ★Q8 文档缺口与版本确认（影响实现范围，需厂商/用户答复）

需确认：① 是否存在「彩色行显示协议」章节与命令（M1）；② 2.6 缺失的命令（M2）；③ BCC 示例中的 `'D'`(0x44) 是否为真实命令（M3）；④ `'T'` 的内容区是「N×16 变长」还是「固定 64 字节」（M4）；⑤ `'V'` 帧是 71 还是 72 字节、内容 64 还是 65 字节（M5）；⑥ `'S'` 的语音编号是 1 字节还是 2 字节、取值基准 0x30 还是 0x31、0x36 是什么（M6/M7）；⑦ 显示行字段的其它取值（M8）；⑧ 心跳超时的严格阈值（5s？）与「系统维护中」的可配置范围（M9/§2.2）。
- **推荐**：先按本报告的「已确定项 + 推荐值」实现最小可用集（T/O/E/F/J/K/V/S/C 九个命令 + 推荐映射），把 `'D'` 与「彩色行」列为待确认扩展；**但如果 M1 的命令现场在用，probe 白名单与实现范围都要改**，所以 Q8 应在写码前问清。

### Q9 构建收录与目标

- 建议：Makefile `INC_DIRS` + `SRC_APPLICATION`（**追加末尾**，保持既有 probe 优先级）；EIDE `files` 收录 + 各 target `incList` 加 `-I`；**是否新建 `targets.XinJiang`**（仿 `targets.Myanmar` 无显示口径）或仅编入现有 Debug 由用户裁决。
- **推荐**：先编入 Makefile（`PROTO=ALL` 用于桌面/台架联调，前提是 Q1 落地）+ EIDE Debug/Release 的 `incList`；量产目标等协议冻结后再建，避免反复改 yml（改完必须 `EIDE: Reload Project`）。

### Q10 队列深度与内存放置

- **推荐**：深度 3、payload 74、队列体+cb+帧缓冲+任务栈全部 CCMRAM（≈1532B），SRAM 仅 ≈20B。理由：与 CQ/GZ_OL/YN_OL/MM 同款裁决，SRAM 余 2088B 不宜再压。若用户希望「协议少时省 CCM」，可改为 SRAM（−408B CCM、+408B SRAM）——**不推荐**。

### Q11 `'T'` 帧的显示语义细节

- 推荐：清屏后按行渲染（见 Q3 附带）；空内容（去尾 0x00/0x20 后为空）→ 仅清屏；同一帧里 N 行全部渲染。
- 需确认：上位机会不会「只发一行、期望保留其它行」（若会，则改为逐行覆盖不清屏）。

### Q12 联调前置

- 需用户提供：现场波特率（DIP1 OFF=9600 / ON=115200，**推荐 OFF**）、接线口（RS232/RS485）、上位机发帧样本（至少 T/O/E/F/C 各一帧的十六进制，含 BCC）。
- 建议实现时同步写宿主推演脚本 `.analysis/xinjiang/xj_frame_sim.py`（仿 `mm_frame_sim.py`）：覆盖半帧/粘包/伪头/超长/BCC 错/治超共存等边界，作为验收证据（doc/08 §4 Step 2 惯例）。
