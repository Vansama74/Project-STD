# 第二十五轮：1×2（16×32）「两块模组都不显示」取证与现场测试矩阵

**日期**：2026-09-17
**现场报告（用户原话）**：「我设置 `_22_1665_MODULE_ROWS` 1，`_22_1665_MODULE_COLS` 2，默认显示"1"换行"2"，
模组连接第一个 HUB75 口，屏幕没有显示，第二个 HUB75 口，屏幕也没有显示。接在第一个 HUB75 时，
按下一次测试，屏幕能显示 MD。接在第一个 HUB75 时，按下测试，屏幕始终没有显示。」
**结论一句话**：**不是 1×2 派生出错，而是「单块模组只收得到帧内最后 128 位（= 驱动内部「模块 1」= 屏体下半 16 行）」
＋「口 2 的数据脚从未被驱动」两条同时成立**；默认画面的内容又只落在上半 16 行（且实际只画出 1 个字），
所以「默认全黑 / TEST 出 MD」完全可预测。驱动内唯一的缺陷是**注释与代码对「链首模块是谁」自相矛盾**（已修），
另新增一个现场 A/B 开关用于核实级联顺序。

## 1. Q1：1×2 驱动**逐字输出**什么（机器级，宿主直跑编译产物）

脚本：`.analysis/22_1665/round25_two_modules.py`（17/17 通过；日志 `round25_two_modules.log`）。
方法：用 `.analysis/22_1665/host/` 的桩 + harness 把**现行驱动**编成 x86-64 程序，喂进指定 `pixel_map`，
打印 `frame_state` / 每时钟 BSRR 写序 / CLK 数，再用**单模块落点模型**把每个 128 位块解回 16×16 图像。

| 项 | 1×2 实测 |
|---|---|
| 基类字段 | `screen=16x32`（宽 16 / 高 32）、`buffer_size=512`、`scan_line_pixels=256`、`modules=1x2` |
| 每帧 CLK | **256**（= 128 × 2 模块） |
| 每帧 BSRR 写序 | 512 项（256 时钟 × 2 端口 G/B） |
| 帧内块 0 = `state[0..127]` | **最后移入 ⇒ 停在链首**（贴着数据脚那一块）；解出内容 = **模块 1**（图案「模块0=红/模块1=绿」下解出全绿） |
| 帧内块 1 = `state[128..255]` | **最先移入 ⇒ 推到链尾**；解出内容 = **模块 0**（全红） |

⇒ **单块模组接在任意一个口上时，它是「链首」，拿到的是块 0 = 驱动内部「模块 1」的位流 = 屏体逻辑 y=16..31 的内容。**
（这条与 doc 里的散文「末 128 位落在链首模块 m=0」**相反**，是文件头/§0.3/§0.9 与代码公式 `[(M-1-m)·128, …)`
自相矛盾之处；本轮已修注释并加开关，见 §5。）

## 2. Q2/Q3：三种接线模型下每块屏显示什么 + 与现场观测对照

「SEPARATE」= 两级独立线（每列模块各占一组数据线；本文件只写第一组）；
「CHAIN-0/1」= 同线级联（一块的 SDO 接另一块的 SDI），板端那块是链首。
图案：逻辑上半 16 行（= 模块 0 区域）红、下半 16 行（= 模块 1 区域）绿。

| 接线模型 | 板端口 1 那块显示 | 口 2 那块显示 | 与观测①（默认全黑） | 与观测②（TEST 出 MD） | 与观测③（口 2 全黑） |
|---|---|---|---|---|---|
| **SEPARATE（每列一口）** | 块 0 = 模块 1 = 绿（下半内容） | **全黑**（4 根脚从未被写） | ✅ 自洽（默认内容只在上半） | ✅ 自洽（MD 在下半） | ✅ 自洽 |
| CHAIN（同线级联，链首 = 板端那块） | 块 0 = 模块 1（下半） | 另一块 = 模块 0（上半，红） | ⚠️ 远端那块**应显示上半内容**（「一」/FW），现场说没有 | ✅（近端显示 MD） | ✅（口 2 若为另一组脚） |
| CHAIN-FLIP（`…IS_MODULE0=1`） | 块 0 = 模块 0（上半，红） | 另一块 = 模块 1（下半） | ⚠️ 同上（有一块应显示内容） | ❌（近端会显示 **FW** 而不是 MD） |

**观测②是判链首归属的关键实验**：现在实际看到的是 **MD（下半内容）**，说明「板端/链首那块 = 驱动内部的模块 1」。
如果现场把 `-D_22_1665_CHAIN_HEAD_IS_MODULE0=1` 重编后同一实验变成显示 **FW**，则反向结论成立、
可用该开关把「链首 = 模块 0」固定下来。

**「口 2 全黑」的解读**：驱动只写 4 根脚——现场定标过的 R1(PG9)/G1(PG10)/R2(PG15)/G2(PB6)，
它们属于**第一组数据线**（第一块 HUB75 口的 ch0/ch1）。口 2 若走的是另一组脚（兄弟驱动语义下
`MODULE_COLS` 每 +1 就要多用一组：第二组按通道序 = `R3(PB8)/G3(PB9)/R4(PE1)/G4(PE2)`），
则无论按多少次 TEST 都不会有反应——**这与观测③一致**；反之若口 2 与口 1 并联，则 TEST 全屏红时
口 2 那块也必然亮红——**现场已否证并联**。

## 4. 为什么可以判定「1×2 派生路径本身没有 bug」

| 检查 | 结果 |
|---|---|
| 长度/上界派生 | `frame_state[128·M]`、`pixel_map[256·M]`、`chain_dst[4M][128]`、CCM `1408M+384` 全部按 M 派生；1×2 实测 `.ccmram=11868B`（本模组 3200B = 1408·2+384 ✔），无越界/无写死 128 |
| `scan` 循环 | `for (p = FRAME_BITS; p-- > 0;)` = 256 次；实测 CLK 256、BSRR 512 项（= 2 端口 × 256） |
| 基类字段 | `screen=16x32 / buffer=512 / scan_line_pixels=256 / modules=1x2`，`prepare` 只按 `FRAME_BITS` 访问 |
| 与独立规格模型对拍 | `check_host_differential.py` 40/40（1×1/2×1/1×2/2×2 + 开关变体，逐字节） |
| 几何自检 | `check_driver.py --geom` 1×1/2×1/2×2 各 50/50；编译矩阵 19/19；EIDE 原命令 11/11 |
| 链接 | `PROTO=ALL` `DISP=22_1665` 1×1 / 1×2 / flip 三口径全部链接通过（`.ccmram` 10460 / 11868 / 11868） |
| 结论 | **1×2 的位流生成与输出正确**；「两块都不显示」由「接线/模组归属」解释，见 §2 |

> 唯一被证实的**驱动内缺陷**：文件头与 doc/01 §0.3/§0.9 的散文「末 128 位（p 最小）落在链首模块（m = 0）」
> 与代码公式 `[(M-1-m)·128, (M-m)·128)` **互相矛盾**（按公式，链首那块装的是模块 M-1）。已按代码实态修文并
> 新增开关（§5）——**行为零变化**。

## 6. 「多模块到底怎么接」待确认问题清单（信息到位前不要改驱动）

1. **两个 HUB75 口各有哪些信号脚**：给口 2 的丝印/原理图/照片（尤其 `R3/G3/B3/R4/G4/B4` 是否引出到口 2）。

   4 根数据脚应为 `R3(PB8)/G3(PB9)/R4(PE1)/G4(PE2)`。**这是假设，必须现场核对**。
2. **两块模组是「面板自带级联」还是「各自一口」**：面板背面有没有第二个 16P 座？模组之间有没有短排线？

3. **级联方向**：若为级联，排线从哪一块进（上还是下）——决定 §5 开关取值。
4. （可选）**口 2 的脚位实测**：可取回归档探针驱动
   `.analysis/22_1665/archive/prev_round/dev_display_22_1665_round23_pre_refactor.c`

5. **面板供电与电平**：口 2 那块是否独立供电/共地（`MBI5034B` VIH≈3.5V 的老问题，doc/01 §1.3）。
