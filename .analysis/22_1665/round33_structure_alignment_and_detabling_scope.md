## 0. 用户问题（原话意图）

1. 22_1665 驱动「实测显示已无任何问题」，但**文件结构没有对齐兄弟驱动**（`dev_display_1_263.c` /
   `dev_display_22_1703.c`）；其中 `_22_1665_line_t` 这个类型**别的模组驱动里没有**。
2. **之前提的「去表方案」是不是就是用映射关系来替代这张表？**

**一句话结论**：不是。「去表」自始至终指的是 **`_22_1665_chain_dst`**（`[4M][128]` = `1024·M` 字节的
全量落点预计算表）降级为「按需计算 + 小块常量表」；与 `_22_1665_line_t` / `_22_1665_lines`（20 项 /
240 B 的**硬件接线描述**）是两张完全不同的表。「用映射关系替代行表」是**另一件独立的事**，
而且它在语义上等价、代价很小，但它**不解决 CCM 占用**，也**不是** round31/32 提出的那个方案。

### 2.2 推导式与逐项核对

驱动现行写法（`dev_display_22_1665.c:170-185`）与推导式：

```
group g（= 模块列 g）占用通道对 (2g, 2g+1)
j = 0 → &g_hub75_pin_r[2g]   role = RED    half = 0（上半屏）
j = 1 → &g_hub75_pin_g[2g]   role = GREEN  half = 0
j = 2 → &g_hub75_pin_r[2g+1] role = RED    half = 1（下半屏）
j = 3 → &g_hub75_pin_g[2g+1] role = GREEN  half = 1
通式：line = (j & 1) ? &g_hub75_pin_g[2g + (j >> 1)] : &g_hub75_pin_r[2g + (j >> 1)]
      role = (j & 1) ? GREEN : RED        half = (j >> 1)
```

逐项核对（5 组 × 4 行 = 20 项，全部命中；物理脚来自 `main.h`）：

| g | j=0 | j=1 | j=2 | j=3 |
|---|---|---|---|---|
| 0 | R1 = `pin_r[0]` = PG9 | G1 = `pin_g[0]` = PG10 | R2 = `pin_r[1]` = PG15 | G2 = `pin_g[1]` = PB6 |
| 1 | R3 = `pin_r[2]` = PB8 | G3 = `pin_g[2]` = PB9 | R4 = `pin_r[3]` = PE1 | G4 = `pin_g[3]` = PE2 |
| 2 | R5 = `pin_r[4]` = PE4 | G5 = `pin_g[4]` = PE5 | R6 = `pin_r[5]` = PC13 | G6 = `pin_g[5]` = PC14 |
| 3 | R7 = `pin_r[6]` = PF0 | G7 = `pin_g[6]` = PF1 | R8 = `pin_r[7]` = PF3 | G8 = `pin_g[7]` = PF4 |
| 4 | R9 = `pin_r[8]` = PF6 | G9 = `pin_g[8]` = PF7 | R10 = `pin_r[9]` = PF9 | G10 = `pin_g[9]` = PF10 |

**独立佐证**：宿主脚本 `.analysis/22_1665/check_driver.py:122-131` **早就用同一公式**（`EXPECT_ROWS`
按 `g` 生成 20 项）去校验源码里的表——即「表内容 = 公式」这一点已被自动化断言固化。

### 2.3 两个字段的性质

| 字段 | 可否由公共表推导 | 语义归属 |
|---|---|---|
| `line`（数据脚） | **完全可推导**（上表 20/20） | 公共层事实（`main.h` → `g_hub75_pin_*`） |
| `role`（红/绿 die） | 取值由行号 `j` 决定（`j&1`）；但「哪根线对应哪种 die」是 22_1665 独有语义 | 22_1665 独有（公共层无 die 概念） |
| `half`（上/下半屏） | 取值由行号 `j` 决定（`j>>1`）；「线覆盖哪半屏」是 22_1665 独有语义 | 22_1665 独有（公共层无半屏概念） |
| `name` | 不可推导（就是给人看的字面量） | 纯文档；**逻辑 0 次读取** |

**现场标定的真实内容**（probe 8 逐脚定标，doc/01 §0.10）其实只有两句话：① 组 g 用通道对
`2g/2g+1`；② 组内 4 行的次序 = 上半 R / 上半 G / 下半 R / 下半 G。这两句话（而不是 20 项数据）
是"不可推导"的部分。

## 3. 「去表」的边界（核心问题）

### 3.1 round31 / round32 原文中的「去表」指什么（逐条出处）

| 出处 | 原文（摘要） |
|---|---|
| `round31_8x2_budget_analysis.md` §5 方案 C 第 3 条 | 「另一个不改上限的做法是**改驱动实现**——`chain_dst` 的 1024·M 可以从「全量预计算表」降级为「按需计算 + 小块常量表」…去掉该表后本模组只剩 6656 B」 |
| `round32_ccm_limit_removed.md` §5「若 8×2 实测超标，可选方向 ②」 | 「后续按需把 `chain_dst` 全量预计算表（1024·M，M=16 时为 16384B）降级为「按需计算 + 小块常量表」（省 CCM、代价 = prepare 热路径加算 —— 本轮不做…）」 |
| `doc/01_.../22-1665模组驱动分析与迁移记录.md:330`、`:1264` | 同上措辞，均点名 `chain_dst` |
| `.analysis/22_1665/README.md:91` | 「**未改 TIM3/TIM4 参数、未做去表重构**」（承接 round32 的边界声明） |

**全文没有任何一处**把「去表」指向 `_22_1665_lines` / `_22_1665_line_t`。

### 3.2 两张表不是一回事

| 维度 | `_22_1665_chain_dst`（去表对象） | `_22_1665_lines`（用户以为的对象） |
|---|---|---|
| 信息性质 | **几何派生的查找表**（`_22_1665_region_offset()` 是纯函数，`dev_display_22_1665.c:357-365`） | **硬件接线描述**（哪根脚接在哪个链段；现场标定结果） |
| 尺寸（实测） | 1024·M 字节：8×2 = 16384 / 8×4 = **32768** | **240 B**（20 项 × 12 B） |
| 段 / 时机 | `.ccmram` / init 建表（`_22_1665_build_chain_dst`，:370-385） | `.rodata` / 编译期常量 |
| 消费者 | `prepare` 热路径（每 (m, j, p) 一次查表，:280） | init 建表（`bsrr_table` 的脚/端口、`chain_dst` 的半屏、prepare 的角色） |
| 去掉后的代价 | prepare 每次访问 +1~2 条指令（用「常量相对模式 + 运行时基址」形式），或每元素 +10 余条（全量重算） | 现场换线从「改一行表」变成「改公式或加特例」 |
| 去掉后的收益 | **省 1024·M 字节 CCM**（8×4：−32768） | 省 240 B `.rodata` + ~63 B 字符串 |

**量级比**：8×4 口径下 `chain_dst` 是行表的 **137 倍**（32768 / 240）。

### 3.3 若真把行表改用映射关系（用户所指的那件事）

- **可行性**：完全可行且**内容等价**（§2.2 的公式已被 `check_driver.py` 当作期望值）。
- **代价**：
  - `.rodata` **−240 B**（表）**−约 63 B**（线名字符串）；`.text` 基本不变（公式内联 1~2 条 `LDR`+`AND`）。
  - `init` 侧无变化（`build_bsrr_table` / `build_chain_dst` 改为调用推导函数）。
  - 可读性：从「20 项表，改线改表」变为「4 行公式 + 注释 + 断言」；现场换线的自由度收窄。
  - **一个实际收益（当前设计的隐患）**：`half` 列 20 项中**只有组 0 的 4 项被读**
    （`dev_display_22_1665.c:378` 写死 `_22_1665_lines[0][j].half`），即表**看起来**每组都能
    单独配半屏，**实际上组 ≥1 的 half 全被忽略**；`role` 则每组都读（:286）。改用公式后这层
    「幻觉可配置性」消失，语义与实现一致（配合一条 `_Static_assert` 或注释固定行序约定）。
- **另外**：`name` 字段是表里唯一**没有兄弟对应物、且逻辑从不读取**的东西——即使不做公式化，
  它也是「结构对齐」里最没有争议的删除对象（删后 12 B → 8 B/项，表 240 → 160 B）。

### 3.4 「结构对齐」与「去表」的关系

| | 结构对齐 | 去表（chain_dst） |
|---|---|---|
| 解决什么 | 可读性 / 三驱动形状一致 / 消除名不副实的数据（`name`、只读 1/4 的 `half`） | **CCM 占用**（1024·M → ~256 B 常量） |
| 不解决什么 | CCM 占用一点不省 | 与「像不像兄弟驱动」无关；反而让 prepare 结构离兄弟更远（兄弟 prepare 是 memcpy，1665 已是逐位重建） |
| 触碰现场已验证路径？ | 否（可做到零行为变化，宿主逐位可证） | 是（落点计算进 prepare 热路径，须机器级 A/B + 上机复核） |
| 是否同一件事 | **不是**——两件独立的事，可以各做各的，也可以都不做 | |

## 5. 方案对比（只列分析，不动手）

### 5.0 前置事实：工作区几何宏值 = **8×4 = 128×64**（与提问时的 8×2 不同）

- 源码：`dev_display_22_1665.c:31-32` = `(8U)` / **(4U)**；文件 mtime `2026-09-18 17:37`
  （晚于 round32 末次构建 17:17），与 `archive/round32/pre_round32.c` 的非注释差异**只有
  `MODULE_COLS 2 → 4`**。
- 今日 08:47 的 `build/Debug/Project_STD.elf` 实测：`_22_1665_chain_dst` = 32768（= 1024×32）、
  `pixel_map` 8192、`frame_state` 4096、`bsrr_tab` 1024、`bsrr_slot_cnt` 4 ⇒ **M=32 = 8×4**；
  整个 `.ccmram` = **57484 B**（= 本模组 46080 + 非模组 11404，EIDE Debug 子集），余 8052 B。
- **算术提示（本轮未构建，仅按 round31/32 实测数推算）**：`PROTO=ALL` 口径非模组部分实测
  35836 B ⇒ 8×4 整片会是 `46080 + 35836 = 81916 B > 65536 B`，**链接期会溢出**；
  EIDE Debug（CQ 子集）口径则余 8 KB 左右，与今日 elf 相符。
- 另：8×4 的 `prepare` 估算 ≈2.0~2.4 ms/次提交（按 round31 §4 的 M=16 ≈1.0~1.2 ms 线性外推），
  仅发生在"有提交"的帧；静态画面只跑 `scan`（≈0.36~0.48 ms × 4 组并行？不随 M 放大，仅随
  `128 × ROWS` 放大 → 8 行时 ≈0.36~0.48 ms，占 TIM3 500 µs 的 72~96%）。

### 5.2 关于 C 的实现形式（供将来立项参考，本轮不做）

- 省内存的高效形式不是"每元素全量重算"，而是**常量相对模式 + 运行时基址**：
  `offset(m,j,p) = (y0 + half_j·HALF_COLS)·SCREEN_ROWS + x0 + pat(p)`，其中 `pat[128]` 是
  单模块的相对偏移常量（**~256 B `.rodata`**，与 M 无关），基址每 (m, j) 算一次。
  `prepare` 每次访问只多 1 条 `ADD` —— 比 round31/32 措辞里的"十余条指令"便宜得多，
  但同时**会改变 `chain_dst` 这一「prepare ↔ 宿主脚本的对照面」**：`check_equivalence.py`
  目前直接比对落点表内容（:352-361），需改为比对 `prepare` 输出的帧状态数组。
- 若走这条路，`_22_1665_lines` 的映射化（方案 B）基本是顺带完成的。

## 6. 结论

1. **「去表方案」≠ 用映射关系替换 `_22_1665_line_t`**。round31 §5(C)、round32 §5②、doc/01
   §0.7/§6 三处原文点名的都是 **`_22_1665_chain_dst`**（1024·M 字节的全量落点预计算表 →
   「按需计算 + 小块常量表」），因为它是**纯几何派生**的；`_22_1665_lines` 是**硬件接线描述**，
   两者在信息性质上无关、在尺寸上差 137 倍（8×4）。
2. **`_22_1665_line_t` 并非孤例**：22_1703 也有同类「驱动内手写接线描述表」（`_22_1703_sig_t`
   ×5 张 + `_22_1703_grps[]`）；真正只有 1665 才有的，是 `name` 字段（逻辑 0 次读取）与
   「role/half 写成数据列」。且 `line` 字段**完全可由 `g_hub75_pin_*` 推导**（20/20 命中，
   公式与 `check_driver.py` 的期望值一致）。
3. **最小、最安全的落点（若目标是"结构对齐"）**，按性价比排序：
   - 0 改动：把「行表 ↔ 兄弟驱动对应物」的对照写进 `doc/01` §0.3（本文 §1 可直接用）；
   - 小改动：删 `name`（逻辑零读取，`.rodata` −240 → 160 B，行为零变化）；
   - 再进一步：`line` 用 §2.2 公式、`role/half` 固定为行序约定 + 一条断言（等价性由宿主逐位证明）。
4. **不要为了"对齐"去动 `chain_dst`**；反过来，也不要因为"结构对齐"而误以为 `chain_dst`
   的问题被解决——它是：`.ccmram 32768 B`（8×4，占本模组 71%）、以及 `PROTO=ALL` 口径下
   `46080 + 35836 > 64 KB` 的唯一根因。
