## 1. 问题①：`.analysis/22_1665/` 下的 `.py` / `.sh` 到底有什么用？

### 1.1 它们是什么（三个事实）

| 事实 | 说明 |
|---|---|
| **跑在电脑上** | `python3 .analysis/22_1665/xxx.py`（只用 Python 标准库，不需要装任何包）；`.sh` 是 Bash + 交叉编译器 |
| **不进固件** | 它们不在 Makefile 的源列表里，`make` 永远不会碰它们；板子上跑的还是 `build/Debug/Project_STD.hex` |
| **不影响板子** | 它们只做两件事：读源码文本、算数（或调 `arm-none-eabi-gcc -fsyntax-only` 试编），产物是 `.md` 报告或一行行的通过/失败 |

### 1.2 为什么要这么麻烦（核心动机）

这个模组（2200001665）到现在都没标定完：**哪根脚管哪块屏、哪种颜色、什么朝向，全都不确定**。
现场调试的成本很高（改一行代码就要重新编译 + 烧录 + 人跑到屏前看 + 手抄点亮的坐标），
所以采用的办法是：

```
        现场（只能烧几次）                        电脑（想跑多少次跑多少次）
   ┌──────────────────────────┐          ┌──────────────────────────────────┐
   │ 烧一次固件 → 看屏 → 手抄   │  ──────▶ │ 把「代码按现有表应该出什么」算出来 │
   │ 现象（比如 23 个亮点坐标）│          │ （ASCII 图 + 点集）              │
   └──────────────────────────┘          └──────────────────────────────────┘
                    ▲                                  │
                    └──────── 逐点比对 ────────────────┘
             一致 ⇒ 代码逻辑没问题 ⇒ 问题在接线/硬件
             不一致 ⇒ 代码（或我们对表的理解）有问题 ⇒ 先在电脑上改对再烧
```

具体例子（就是上一轮真实发生的）：用户在屏上看到红色「口」只亮 23 个点。
`check_round17.py` 在电脑上把「口」的 16 点阵字模从字库 bin 里 dump 出来，
按第十六轮那张链表（链 0=R1 / 1=G1 / 2=B1 / 3=R2）逐位算出「驱动应该给 R1 发 23 点、给 B1 发 29 点」，
再把「只有 R1 导通」代进去 → 算出的可见点集**与用户手抄的 23 个坐标逐点相同**。
这一步同时证明了两件事：① 驱动算得没错；② B1/G1/R2 那三根脚现场没接链。
如果不先算这一遍，就无法区分「代码算错」和「接线不对」，很可能白改一轮代码。

- 平时开发/跑协议功能：完全无关（它们不参与构建）。

## 2. 问题②：`_22_1665_CHAIN_PROBE` 探针有什么用？

### 2.1 它是什么

`dev_display_22_1665.c:375` 处的编译期宏：

```c
#ifndef _22_1665_CHAIN_PROBE
#define _22_1665_CHAIN_PROBE (0U)   /* 0 = 关（默认） */
#endif
```

把 `0U` 改成别的值 → 重新 `make -j8 DISP=22_1665` → 烧录 → **驱动忽略正常显示内容，
改画这一种自检图案**。它是「标定/排障设施」，与多链/兼容模式无关，两种模式下都能用。

### 2.2 为什么需要它（它解决的问题）

- 这个模组的接线还没有标定：**4 条链（每条 128 位 = 8 片 MBI5034B）里只有 1 条（R1）确认能工作**，
  另外 3 条的数据入口未知。
- 屏上没有丝印、没有说明书，且**去现场烧一次的成本很高**。
- 于是把「可能需要的信息」设计成几种图案，一种图案回答一个问题：
  「这条链有多长 / 每片输出落在哪几个灯 / 这根脚有没有真的驱动屏幕 / 哪根脚管哪块屏、什么颜色、什么朝向」。

### 2.3 模式总表（当前已有 0..9）

| 值 | 名字 | 屏上画什么 | 怎么判读（判据） |
|---|---|---|---|
| **0** | 关（默认） | 正常显示内容 | — |
| 1 | 走点 | 每过 N 帧把 1 位沿链移动（`HOLD` 控制速度，×500µs） | 亮点在屏上的移动路径 = 链位在屏面上的排列顺序（慢，一般不用） |
| 2 | 区间全亮 | 链位 `POS` 起 `SPAN` 位（默认一整片 16 位）全亮 | 判断「一片的 16 个输出落在屏上哪 16 个灯」→ 看出一片的块形状 |
| 3 | 前半链全亮 | 链位 0..63 全亮 | 快速看**边界**落在屏面什么位置（链长/块形状是否单调） |
| 4 | 片锚点 | 每片的第 `POS` 级（默认 3）亮 → 屏上 8 个点 | 8 个点的位置 = 8 片在屏面上的块栅格排布 |
| 5 | 全链点亮 | 128 位全 1（= 该脚**恒定高**） | 不亮的位置 = 未接/坏灯；也用来「确认这根脚到底通不通向屏幕」 |
| 6 | 全链点亮（同 5） | 同上（历史编号） | 同上 |
| **7** | 逐脚标识 | **每根候选脚各自的重复图案**（以一片 16 链位为周期），每块 4×4 亮的点数 = `k+1`（k = 脚序号 0..9 → 1,2,3,4,5,6,7,8,12,16 点） | **数每块亮几个点 − 1 = k** → 该区域的数据脚。点数判据对链内位序置换不变，所以位序不同也能认脚；出补色图案读 `16 − 点数` |
| **8** | 逐脚闪烁 + 纹理 | 每根候选脚停留 **3s**：前 1.5s「全 1 帧 ↔ 全 0 帧」2Hz 闪烁；后 1.5s 静态 `1010…` 纹理。**R1 区域全程显示被测脚的序号数字**（5×7 点阵） | **闪 + 细密规则纹理 = 该脚真被驱动**（链在这根脚上、位流被正确接收）；**只闪没有纹理 = 只是「电平跟随」（悬空/弱耦合）**；全程无反应 = 这根脚与任何链都无关 |
| **9** | 逐链 × 逐脚内容扫描 | 一轮 = 链数 × 脚数：每次**只驱动一根候选脚**并送**某条链自己的内容**（非黑即亮）；R1 区域显示**两位数字**（左 = 链号、右 = 脚号 k）；每 1.5s 换一组，默认 4×4 = **24s 循环** | 看到**某块屏出现形状正确的内容** → 该链的脚 = 右数字（6=A / 7=B / 8=C / 9=D）；颜色 = 该链 die 的颜色（红 → ROLE_RED / 绿 → ROLE_GREEN）；出现的位置 = 该链 `region`；内容上下颠倒/左右相反 → 该链要加 `flags`（最常见 `_22_1665_XF_ROT180`） |

补充：

- **上电引脚回读自检**（`_22_1665_PIN_SELFTEST` 默认开，与 `_22_1665_RTT_DIAG` 同时为 1 才编入）：
  开机时对参与输出的脚逐根「写 1 → 读回 → 写 0 → 读回」，RTT 打
  `[22_1665] pin=R1 (PG9) write1/read=1 write0/read=0 PASS`。
  **PASS = MCU 侧这根脚确实被驱动**（GPIO 模式对、端口位号对、没被外部拉死）——用来先排除「软件根本没驱动这根脚」这一类病因。
- 探针 8/9 里，**序号数字显示在「链 0 的区域」**、但由 **R1 脚**承载（默认链表里链 0 就是 R1，所以数字出现在上半屏）。
  如果以后把链 0 改成别的脚，数字仍出现在 R1 那片屏上——这是显示设施的约定，不影响判读（读数以数字为准）。
- 探针 8 的候选脚集合 = `_22_1665_DATA_LINES`（默认 `0x3FF` 十根全开）；探针 9 的扫描脚集合 = `_22_1665_PROBE9_PINS`（默认 `0x3C0` = 四个地址脚 A/B/C/D，**且不允许含 R1**，因为 R1 专职显示数字）。
- 探针 1..7 的候选脚也是 `_22_1665_DATA_LINES`；**多链正常显示（探针 0）不用这个掩码**（每条链用自己表里的脚）。

### 2.4 手把手：怎么用（以探针 9 为例）

**准备**：只需要改一个数字、编译、烧录，别的不动。

```bash
# 1) 改宏（文件里只有一个地方，第 375~381 行那一段）
#    Device/Display/dev_display_22_1665.c:   _22_1665_CHAIN_PROBE (0U)  →  (9U)
#    （若要缩小/扩大扫描的脚，再改 _22_1665_PROBE9_PINS，见 §4）

# 2) 编译（DISP 必须显式给，默认口径是 1_263）
make -j8 DISP=22_1665          # 全协议 PROTO=ALL 默认；EIDE 侧也编 22_1665

# 3) 烧录（二选一）
bash tool/flash_all.sh         # J-Link：Bootloader + Recovery + 主固件一次烧完，默认烧后擦 Sector1
# 或
openocd -f ./Compiler/stm32f407zg.cfg -c "init; halt; program ./build/Debug/Project_STD.hex verify reset exit"
#   注意：任何烧录器烧完主固件后都要「擦除 Sector1（0x08004000~0x08007FFF）」恢复出厂态，
#         否则 Bootloader 的条件 D 可能判「App 损坏」把设备锁在 Recovery。
```

**上电后看两处**：

1. **RTT**（J-Link RTT Viewer / IDE 的 RTT 窗口）：开机先有横幅与链表自检行，然后每 1.5s 一行
   ```
   [22_1665] multichain=1 chains=4 screen=16x16 frame_bits=128
   [22_1665] chain0 C0  lines=0x001 role=RED   region=(0,0,16,8) xf=0x0 dst=default
   [22_1665] chain1 C1  lines=0x040 role=GREEN region=(0,0,16,8) xf=0x0 dst=default
   [22_1665] chain2 C2  lines=0x080 role=RED   region=(0,8,16,8) xf=0x0 dst=default
   [22_1665] chain3 C3  lines=0x100 role=GREEN region=(0,8,16,8) xf=0x0 dst=default
   [22_1665] out_lines=0x1C1 ports=2 states=4
   [22_1665] pin=R1 (PG9) write1/read=1 write0/read=0 PASS      ← 逐脚自检（行数 = 参与脚数：
   ...                                                             探针 9 默认 4 行 R1/A/B/C；探针 0 默认 4 行；探针 8 默认 10 行）
   [22_1665] probe9: chain=0 C0 role=RED pin=A (PD4) k=6        ← 每 1.5s 一行，随组合刷新
   ```
   **这几行同时是「板上跑的是哪份镜像」的证据**：`chain1 lines=0x040`（= A）说明板上是第十七轮默认口径；
   若看到 `0x002`（G1）那就是第十六轮的旧镜像。
2. **屏**：上半屏（R1 区域）出现**两个数字**，左边是链号、右边是脚号；左上角是「当前扫描的那根脚 + 那条链的内容」。

**盯一轮（默认 24s）**：每次数字变化时看**屏幕上有没有哪块区域出现形状正确的内容**：

| 屏上看到 | 结论 | 填表动作 |
|---|---|---|
| 某块屏出现**形状正确**的内容 | 该链的数据脚 = 右数字（6=A / 7=B / 8=C / 9=D） | 该行 `line_mask = _22_1665_LINE_x` |
| 内容是**红**色 | 该链的 die 是红的 | `role = _22_1665_ROLE_RED` |
| 内容是**绿**色 | 该链的 die 是绿的 | `role = _22_1665_ROLE_GREEN` |
| 内容出现在**上半屏** | 该链覆盖上半屏 | `region = (0,0,16,8)` |
| 内容出现在**下半屏** | 该链覆盖下半屏 | `region = (0,8,16,8)`（左/右半同理 `(0,0,8,16)` / `(8,0,8,16)`） |
| 内容**上下颠倒或左右相反** | 该链片内位序/块栅格是镜像的 | 把该行 `_22_1665_ROW` 换成 `_22_1665_ROW_XF(..., _22_1665_XF_ROT180)`（或相应镜像旗标） |
| 扫完所有脚**什么都不出** | 该链的数据入口不在这几根脚上 | 改 `_22_1665_PROBE9_PINS` 再烧一次，或退回探针 8（扫全部候选脚） |

**收尾**：把 `_22_1665_CHAIN_PROBE` 改回 `0U` → 重新编译烧录 → 复验（TEST 全屏红 →
红链覆盖区域全亮；全屏绿 → 绿链区域全亮；上电默认画面 = 完整的「口」）。

### 2.5 探针 8 的手把手（什么时候先烧它）

- 场景：怀疑「这根脚其实连着一条链，只是链跟不上快的位流（悬空/弱耦合，只对恒定电平有反应）」。
  探针 9 送的是**内容**（快速位流），这种情况会「什么都不出」，容易误判为「没接线」；
  探针 8 的分段设计正好把这两种情况分开：**先闪（电平跟得上）→ 再给静态纹理（真被驱动的链才能出细密纹理）**。
- 步骤同上：`_22_1665_CHAIN_PROBE` 改 `8U`（可配合 `_22_1665_DATA_LINES` 缩到几根脚，见 §4）→ `make -j8 DISP=22_1665` → 烧录。
- 屏上：每根脚 3s（默认 10 根 = 30s 一轮）；R1 区域显示**当前被测脚的序号数字**（0..9 = R1/G1/B1/R2/G2/B2/A/B/C/D），
  RTT 同步打 `[22_1665] probe8 dwell: pin=A (PD4) k=6`。
- 判读：**数字在变 + 某块屏在闪 + 闪完出现细密规则纹理** ⇒ 那根脚真驱动了一条链（记下数字）；
  **只闪、没有纹理** ⇒ 只跟电平（弱耦合/悬空）；**全程无反应** ⇒ 那根脚与任何链都无关。

## 3. 两条新现场观测的解读

### 3.1 先确认「板上跑的是哪份镜像」（很重要）

两条观测的解读**强依赖当前链表**，所以先用 RTT 核对（0 成本）：

- 有 `[diag] fw=… built=… tree=cf5ad3d1 …` 横幅 + `[22_1665] chain1 C1 lines=0x040 … chain2 C2 lines=0x080 … chain3 C3 lines=0x100`
  ⇒ **板上是第十七轮默认口径**（链表 = R1 / A / B / C），下面的解读成立。
- 如果看到 `lines=0x002/0x004/0x008`（G1/B1/R2），那是第十六轮的旧镜像 → 结论要按第十六轮的表重新推。
- 如果**没有 `[diag]` 行**：镜像太旧（诊断设施是 2026-09-14 之后才有的），先重烧。

### 3.2 观测③「全屏点亮只有上半屏（0-7 行）」

**先把「全屏点亮」翻译成电信号**：TEST 键的全屏纯色 = 屏上所有像素同色 ⇒ **每条链 128 位全部相同**
（红链取像素 R 位、绿链取 G 位）⇒ bit = 1 的那条链，把**它的数据脚持续拉高整整一帧**（不是位流，是恒定高）。

当前链表（链 0 = R1 / 链 1 = A / 链 2 = B / 链 3 = C）下，8 种纯色把脚拉高的结果
（宿主 `check_round18.py` 复算，矩阵见 `round18_color_matrix.md`）：

| 全屏颜色 | R1(链0) | A(链1) | B(链2) | C(链3) | 恒高脚 |
|---|---|---|---|---|---|
| 红 | 高 | 低 | **高** | 低 | R1, B |
| 绿 | 低 | **高** | 低 | **高** | A, C |
| 黄 / 蓝 / 紫 / 青 / 白 | 高 | **高** | **高** | **高** | R1, A, B, C |
| 黑 | 低 | 低 | 低 | 低 | （无） |

- 现场只看到**上半屏（R1 那条链，0-7 行）**亮 ⇒ **B 被持续拉高却什么都没点亮**（红/黄/白都试过则 A、C 也一样）
  ⇒ **B 上没有链**（不管是红 die 还是绿 die 的链：恒定高会让任何一条挂在那里的链的输出全部点亮，一定会看见一块亮区）。
- **与既有结论的关系**：这正是第十七轮「只有链 0（R1）真在工作」的**再次印证**，并且**更强**：
  第十七轮说的是「送内容时没反应」，这次是「**恒定电平也没反应**」——排除了「链在 B 上但跟不上位流」这类解释。

### 3.3 观测④「按键测试全屏绿色，绿色灯珠不亮」

- 全屏绿 ⇒ 只有两条**绿链**（链 1 = A、链 3 = C）被持续拉高；链 0（R1）取 R 位 = 0 ⇒ **上半屏理应正确地变黑**。
- 现场：绿色一颗不亮 ⇒ **A 上没有链、C 上没有链**（同上：恒定高会让任何挂着的链整块点亮）。
- 这条同时**再次验证了取色逻辑自洽**：绿内容下连 R1 那条链都黑了（如果取色写错，比如红链也吃 G 位，就会出现「绿字显示成红字」的现象——没有出现）。
- 关于「绿色灯珠到底存不存在」：第十六轮曾报过「绿灯亮」（当时的构建是十脚全驱的口径 B），
  所以绿 die 物理上存在；问题在**把内容送到绿链的那根脚**。

### 3.4 与第十五轮「全 1 十脚同流 → 整屏 16×16 全亮」的对比（本轮最关键的机理）

这是用户最容易困惑的一点：**为什么那次整屏能亮，现在只亮上半屏？**

| | 第十五轮那次（整屏全亮） | 现在（第十七轮默认口径） |
|---|---|---|
| 构建 | 兼容口径（16×8 单链）+ `_22_1665_DATA_LINES = 0x3FF` | 多链口径，链 0..3 = R1 / A / B / C |
| 一帧里被驱动的脚 | **十根全开**（R1/G1/B1/R2/G2/B2/A/B/C/D 全部，且数据是「恒定全 1」） | **只有四根**（R1/A/B/C）；其余六根（**G1/B1/R2/G2/B2/D**）**一个位都不写**，由 CubeMX 初始化成推挽输出**低电平**后一直保持不变 |
| 结论 | 四条链全部点亮（说明「其余三条链确实存在、而且能被点亮」） | 只有链 0 亮 |

⇒ **差异不是「内容」而是「哪几根脚被驱动」**：把「R1+A+B+C 恒定高」这一组（= 现在能做到的最强激励）
与「十根全高」相比，**差的正是 G1/B1/R2/G2/B2/D 这六根**。既然「四根高」点不亮其余三链，
那么**「整屏全亮」必然依赖这六根里的至少一根**。

再把历轮「哪些脚被驱动 / 其它区域有没有亮过」排成表（宿主脚本已复算）：

| 口径 | 被驱动的脚 | 其它区域亮过？ |
|---|---|---|
| A：0x3F 同流（第十三/十四轮） | R1, G1, B1, R2, G2, B2 | 否（回报：无新亮区域） |
| B：0x3FF 同流（第十四~十六轮） | **全部十根** | **是**（全 1 恒定 → 整屏全亮；另报「绿灯亮」「口被切成两半」） |
| C：多链 R1/G1/B1/R2（第十六轮构建） | R1, G1, B1, R2 | 否 |
| D：多链 R1/A/B/C（第十七轮构建 = 现在） | R1, A, B, C | 否 |

**一个很干净的发现**：唯一「在阳性口径 B 里被驱动、在 A/C/D 三个阴性口径里都保持低」的脚 = **D**
（其余九根都至少在一个阴性口径里被驱动过）。另外用集合代数也能算出：三条阴性口径各自要求
「需要的脚集」含有 {A,B,C,D} 之一、{D,G1,B1,R2,G2,B2} 之一、{G2,B2,D,A,B,C} 之一
⇒ **单脚解唯一 = D**（两脚解例如 {A, G2} 也自洽——一根数据 + 一根使能/选通）。

### 3.5 收窄后的候选脚集合

三重排除（每一重都是「**把这些脚驱动起来、屏上其它区域无任何反应**」的现场事实）：

1. **G1 / B1 / R2**（第十六轮构建驱动、第十七轮观测否定）；
2. **A / B / C**（本轮新观测：恒定拉高也无反应）；
3. R1 已被链 0 占用。

⇒ 剩下的候选 = **{G2, B2, D}**（恰好三根 ↔ 三条未标定链），其中 **D 是唯一与「其它区域亮过」
完全同步的那根脚**。

### 3.6 与既有结论是否一致？（诚实清单）

| 问题 | 回答 |
|---|---|
| 观测③ 是否与第十七轮矛盾？ | **不矛盾**，是加强：第十七轮靠「内容无反应」推断 B1 无链；这次靠「恒定电平无反应」推断 B 无链。 |
| 观测④ 是否与第十五轮的「绿从未亮」矛盾？ | 不矛盾：绿 die 存在（第十六轮报过绿灯亮），本轮说明「当前口径下没有一根脚把内容送到绿链」。 |
| 有没有和历史上某次回报冲突？ | **有**：口径 A（0x3F 六脚同流）与口径 C（R1/G1/B1/R2）都报过「其它区域没亮」，但按上面推论 G2/B2（口径 A 里被驱动）本该出内容。两种可能：① 那两次是「以已知区域为参照的粗略回报」，漏看了别的区域；② 其余链只对**恒定电平**有反应（那第十五轮的整屏全亮正是恒定电平），而对位流没反应。**探针 8 就是为区分这两者设计的**。 |
| 有没有新信息能反推「下半屏是哪几根脚」？ | 只到「**在 {G2,B2,D} 里**」这一级；要定到单根（或确定是「数据脚 + 使能脚」的两脚组合）必须再做 §4 的实验。 |
| 本轮结论成立的前提 | ① 板上确实是第十七轮默认口径（§3.1 核对）；② 观测③测的是「含红」的全屏纯色（若那一次是**绿色**全屏，则上半屏本不该亮，观察就另有含义——见 §6 问题 1）。 |

## 4. 下一步动作（具体、可执行、可判读）

### 4.0 通用纪律

- 每次只改一个宏 → `make -j8 DISP=22_1665` → 烧录 → **擦 Sector1**（`tool/flash_all.sh` 默认做了）→ 看 RTT + 看屏。
- 每次烧完记三样：**RTT 里的 `[22_1665]` 行**（链表/自检/探针行）、**屏上的现象**（哪块亮/闪/出内容）、
  **当前的宏值**（`CHAIN_PROBE` / `DATA_LINES` / `PROBE9_PINS`）。
- 探针 8/9 的数字显示在**上半屏**（链 0 区域）；数字是「左 = 链号、右 = 脚号 k（0..5 = R1/G1/B1/R2/G2/B2，6..9 = A/B/C/D）」。

### 4.1 第 1 步（最省事、最先做）：确认「除上半屏外还能不能亮」

**改 2 个宏**：

```c
#define _22_1665_CHAIN_PROBE (5U)        /* 探针 5 = 全链点亮（恒定全 1，忽略显示内容） */
#define _22_1665_DATA_LINES  (0x231U)    /* 参与脚 = R1(0x001) + G2(0x010) + B2(0x020) + D(0x200) */
```

（`0x231 = R1 | G2 | B2 | D`；保留 R1 是为了上半屏仍然亮着当参照。）

**预期与判读**：

| 屏上看到 | 结论 | 下一步 |
|---|---|---|
| 上半屏亮 **+ 另外还有 1~3 块区域整块亮**（可能是绿/红） | G2/B2/D 里至少一根通向其余链（或 D 是使能脚） | 走 4.2（二分到单脚），再走 4.4（读全表） |
| 上半屏亮，其它**全黑** | 这三根脚（恒定电平）也不通 | 走 4.3（探针 8）确认「只跟电平」存不存在；否则转 4.5（硬件侧） |
| 连上半屏都不亮 / 屏全黑 | 镜像不对或驱动异常 | 先做 §3.1 的镜像核对 |

**顺带的对照组（可选，同一次烧录做不到）**：`DATA_LINES = 0x3FF` + 探针 5 = 第十五轮那次的条件，
应当能复现「整屏 16×16 全亮」。如果**复现不了**，说明板子/接线/镜像与当时不同，后面的推论都要重来。

### 4.2 第 2 步：二分到单脚（定位那根脚）

| 子步 | 宏 | 看到什么 ⇒ 结论 |
|---|---|---|
| 2a | `CHAIN_PROBE=5`，`DATA_LINES=0x201`（R1 + D） | **有别的区域整块亮** ⇒ **D 单独就够**（它是某条链的数据脚，或它是使能脚且其余链的输入恰好被拉高）；**仍只上半屏** ⇒ D 单独不够（可能是「使能 + 数据」两脚组合） |
| 2b | `CHAIN_PROBE=5`，`DATA_LINES=0x211`（R1 + G2） | 有别的区域亮 ⇒ G2 是某条链的数据脚 |
| 2c | `CHAIN_PROBE=5`，`DATA_LINES=0x221`（R1 + B2） | 有别的区域亮 ⇒ B2 是某条链的数据脚 |
| 2d | 若 2a/2b/2c 全为否、而 4.1 的 `0x231` 为是 | ⇒ **需要两脚同时**（典型：一根使能 + 一根数据）→ 见 4.6 的「探针 10」建议，并把现象回报 |

### 4.3 第 3 步：区分「真被驱动」和「只跟电平」（探针 8）

```
_22_1665_CHAIN_PROBE = 8U
_22_1665_DATA_LINES  = 0x230U     /* 只扫 G2/B2/D → 一轮 3×3s = 9s；想全覆盖用 0x3FE（9 根，27s） */
```

判读（R1 区域的数字 = 当前被测脚 k：4=G2、5=B2、9=D）：

| 现象 | 结论 |
|---|---|
| 数字在变 + 某块屏**闪（2Hz）+ 闪完出现细密规则纹理** | 那根脚**真驱动**了一条链 → 走 4.4 读内容/颜色/区域 |
| 数字在变 + 某块屏**只闪、纹理段什么都没有** | 「电平跟随」（悬空/弱耦合）→ 内容送不进去；按 4.5 走硬件排查，或考虑「只做电平填充」的非常规用法（不推荐做正式显示） |
| 全程只有 R1 区域在变数字，别处没反应 | 这三根脚也无链 → 4.5 |

### 4.4 第 4 步：读全表（脚 / 颜色 / 区域 / 朝向）—— 探针 9

```
_22_1665_CHAIN_PROBE = 9U
_22_1665_PROBE9_PINS = 0x230U     /* 只扫 G2/B2/D → 一轮 4 链 × 3 脚 × 1.5s = 18s；全覆盖 0x3FE → 54s */
```

- 屏上：上半屏显示两位数字（左 = 链号、右 = 脚号），每 1.5s 换一组；
- 看到**形状正确的内容** → 照 §2.4 的判读表填 `_22_1665_chains[]` 的对应行；
- 填完把 `CHAIN_PROBE` 改回 `0U`、`DATA_LINES` 改回默认（`0x3FF`）→ 重编重烧 → 复验（红「口」整幅、TEST 全屏红/绿）。

### 4.5 若「{G2,B2,D} + 全部十根」都没反应 —— 转硬件侧

- 需要你提供（这几轮一直在清单里，但还没有）：**排线/连接器的信号线数量与丝印**、
  **模组背面照片**（除了 MBI5034B 还有没有 74HC245 之类缓冲/译码芯片）、以及**屏上亮/灭区域的照片**。
- 另外可扩候选到板卡上其余 HUB75 通道（`main.h` 里有 R3..R10 / G3..G10 / B3..B10），
  但那要改 `pl_hub75.c` 的引脚表（超出「只改本驱动」的范围，属于下一轮的工作）。
- 兜底交付口径：按「单链 16×8 可用」收敛（`_22_1665_MULTI_CHAIN=0`，兼容口径，行为与第十五轮逐点一致）。

### 4.6 若 2d 指向「使能 + 数据」两脚组合（下一轮的代码建议，本轮未改）

本轮探针 8/9 都是「一次只驱动一根脚」的设计，**结构上无法测「A 常高 + B 送内容」的组合**。
如果 4.2 的结果指向两脚组合，建议下一轮加一个「扫描期间常高的脚掩码」参数（**建议 diff，未落地**）：

```c
/* 探针 9 新增（示意）：扫描期间把该掩码内的脚**恒定拉高**（当作使能/选通线用），

#ifndef _22_1665_PROBE9_ENABLE_PINS
#define _22_1665_PROBE9_ENABLE_PINS (0x200U)   /* 例：D 常高 */
#endif
/* `_calc_out_lines()`（探针 9 分支）：PROBE9_PINS | PROBE9_ENABLE_PINS | R1

```

## 6. 需要你回答/提供的问题

1. **观测③ 的那次「全屏点亮」是哪种颜色？**（TEST 键第几次按键）
   如果是**绿色**全屏而看到上半屏亮，那与当前代码的逻辑相反（绿内容下 R1 那条链应当变黑），
   说明我们漏了别的东西 —— 请务必确认颜色。若是红/黄/白/蓝/紫/青任意一种，本报告结论成立。
2. **观测④ 的「绿色灯珠不亮」，是「整屏全黑」还是「有别的颜色亮着、只是没有绿色」？**（一句话即可）
3. **RTT 开机那几行**（`[diag]` 横幅 + `[22_1665] chain0..3` + 逐脚自检行 —— 探针 0 口径下自检是
   4 行 R1/A/B/C）——用来确认板上镜像与脚的自检结果。
4. 如果方便：**模组背面 / 排线的照片**（有没有缓冲芯片、排线引出几根信号线、丝印是什么）。
   —— 这是「其余三条链的数据入口到底在哪」最硬的一条外部证据，前面几轮清单里一直缺这一项。
5. 做完 §4.1（探针 5 + `DATA_LINES=0x231`）之后：**除上半屏外有没有别的区域整块亮？亮的是哪几块、什么颜色？**
