# 第二十六轮：双 HUB 口现场现象判定（HUB1 显「2」/ HUB2 全黑）

**日期**：2026-09-17 傍晚
**现场报告（用户原话）**：「我现在接了两张模组，一张接第一个 hub 一张接第二个 hub，
默认显示 "1\n2" 16 点阵，应该第一模组显示 1，第二张模组显示 2。
实际第一张模组显示 2，第二张模组没有显示。」
**结论一句话**：现象与 **H2（两个 HUB 口各占一组独立数据脚，硬件 = 模型 B）** 完全一致——
`R1/G1/R2/G2` 那一组只有一块模组（它是链首），它留下的正是**帧末 128 位 = 驱动内部「模块 1」
= 屏体逻辑下半 16 行 = 默认画面第 2 行「2」**；HUB2 的第二组数据脚**从未被驱动**（全帧 512 项
BSRR 写序里一次都没出现）⇒ 那块全黑。**本轮不改代码**（达成「HUB1 出 1 / HUB2 出 2」必须先知道
第二组脚的真实脚位，禁止猜脚位）。

## 1. 判定链第一环：默认画面 `"1\n2"` 在 16×32 上的**真实落点**

**必须核实的点**：第二行会不会在 16 点阵 + 16 行高屏上被裁掉？——**不会**，因为 1×2 口径下
逻辑屏是 **16 宽 × 32 高**（两块 16×16 上下叠的语义），两行 16 点阵恰好放满。

| 环节 | 口径（源码事实） | 结果 |
|---|---|---|
| 区域 | `w = screen_rows = 16`、`h = screen_cols = 32` | 两行各 16px，`text_h = 2 × 16 = 32 = h` → **恰好放得下** |
| 字宽 | ASCII `_glyph_width_px(FONT_16, ASCII) = 16/2 = 8` | 每行 1 个字（8px） |
| 水平 | `h_align = ALIGN_CENTER` → `x = (16 - 8) / 2 = 4` | 两行均 x = 4..11 |
| 垂直 | `v_align = ALIGN_LEFT_UP`（不加偏移）+ `'\n'` → `cur_y += line_h` | 第 1 行 y 0..15、第 2 行 y 16..31 |
| 裁剪 | `word_wrap` 未设（=关）⇒ **没有** `cur_y >= h` 早退分支；`draw_bitmap` 的 `vis_h = 16`（16+16 = 32 ≤ 32） | **第二行完整落屏，不被裁、不被丢** |

**独立复写布局模型输出**：字形框 `[(4,0,8,16), (4,16,8,16)]`，文本高 32（= `cfg.h`）。
⇒ **模块 0 区域装「1」、模块 1 区域装「2」，两行都非空**（这就是判定链的地基：
「HUB1 显示 2」不可能是「第二行被裁掉后剩下的第一行」造成的）。

> **现场观测本身就是这条落点模型的实证**：链首模块只可能拿到**帧末 128 位 = 模块 1 区域**的内容
> （§2 机器级证明），而用户看到的是「**2**」——反过来说明「第 2 行」确实被渲染进了模块 1 区域
> （若落点相反，链首那块会显示「1」）。即：**渲染落点、帧归属、现场观测三者互相印证**，
> 不存在「第二行被裁掉、链首看到的是第一行」这种替代解释（那种情况下链首应显示「1」）。

> 对照第二十五轮：当时文本是 `"一/n二"`（`/n` 不是换行、且 4 个汉字 64px > 屏宽 16px），
> 实际只画出「一」且只在上半屏 ⇒ 单块（链首 = 模块 1 区域）看默认画面**全黑**。
> 本轮文本修正后，同一块屏显示「2」——两条现场观测同源、互为印证。

**宿主脚本对应断言**（`round26_two_hubs.py` §1，7 项源码事实 + 5 项布局推演，全通过）：
文本转义 / FONT_16 / 对齐 / `w,h` 取法 / ASCII 字宽 / `'\n'` 换行动作 / 早退只在 word_wrap 分支；
字形框 = `[(4,0,8,16),(4,16,8,16)]`；两条框分别落在模块 0 / 模块 1 区域；`text_h == 32`。

## 2. 机器级位流归属（现行 1×2 驱动实际输出）

用宿主 x86-64 直跑**驱动编译产物**（`.analysis/22_1665/host/` 桩 + harness），喂进按 §1 落点
生成的 pixel_map（上半「1」= 红、下半「2」= 绿，8×16 合成字形，MSB-first 与真字库同布局）：

| 项 | 实测 |
|---|---|
| 每帧 CLK | **256**（= 128 × 2），`frame_state` 长 256B |
| 每帧 BSRR 写序 | **512** 项（256 时钟 × 2 端口 G/B） |
| 扫描序 | 第 k 个时钟发出的 = `state[255-k]` ⇒ **先移入 `state[255]`、最后移入 `state[0]`**（逐项比对 512 项，全部一致） |
| 帧内块 0 = `state[0..127]` | **最后移入 → 停在链首**（贴着数据脚那一块 = 单块单独接时的那一块） |
| 帧内块 1 = `state[128..255]` | **最先移入 → 被推到链尾**（真级联时第二块的位置） |

把两块各用**单模块落点模型**解回 16×16 像素（`R`=红 `G`=绿 `.`=灭）：

```
[链首模块（贴数据脚那块）= 块 0 解出]        [链尾模块（真级联时的第二块）= 块 1 解出]
    ................                            ................
    ......GGGG......                            .......R........
    .....G....G.....                            ......RR........
    ..........G.....                            .......R........
    ..........G.....                            .......R........
    .........G......                            .......R........
    ........G.......                            .......R........
    .......G........                            .......R........
    ......G.........                            .......R........
    .....G..........                            .......R........
    ....G...........                            .......R........
    ....G...........                            .......R........
    ....G...........                            .......R........
    ....G.....G.....                            .......R........
    ....GGGGGGG.....                            .....RRRRR......
    ................                            ................
```

- 链首块 = **模块 1 区域（第 2 行 =「2」）**（逐像素相等，绿色）；
- 链尾块 = **模块 0 区域（第 1 行 =「1」）**（逐像素相等，红色）。

⇒ **单块模组插在任一「第一组数据脚」的口上时，它看到的是「2」。**
这与用户观测「第一张模组显示 2」逐字吻合（也解释了为什么不是「1」）。

## 3. 三种接线假设 vs 现场两条观测

| 假设 | 接线 | HUB1 那块预测 | HUB2 那块预测 | 与现场 |
|---|---|---|---|---|
| **H1** | 两口 4 根数据脚**并联**（同一组 MCU 脚） | 末 128 位 = 「2」 | 也是链首、同样收「2」 | ❌ **否证**（HUB2 应亮「2」） |
| **H2** | **两口各占一组独立数据脚**（硬件 = 模型 B：每列一口） | 末 128 位 = 「2」 | 该组脚从未被驱动 → **全黑** | ✅ **完全自洽（同时解释两条观测）** |
| **H3** | 模组 A(口 1) → 模组 B(口 2) **物理级联** | 末 128 位 = 「2」 | 首 128 位 = 「1」 | ❌ **否证**（HUB2 应亮「1」） |

补充说明（判据的强度与边界）：

- **H1 的否证**只排除「数据脚并联」这一种共用方式；若 HUB2 与 HUB1 **共用数据脚但 CLK/LAT/OE 另走一路且未接**，
  现象也会是全黑——但那种板级设计不常见，用 §6 的 **E4（示波器）** 一次即可分辨
  （看 HUB2 的 CLK/LAT/OE 有没有动作：有动作 = 只缺数据 ⇒ H2；无动作 ⇒ HUB2 整口未驱动）。
- **H3 的否证**：真级联时链尾那块必然保留**最先移入**的 128 位 = 模块 0 = 「1」。
  现场看到的是「黑」而不是「1」，所以要么级联线根本没接（用户已明确是「各插一个口」），
  要么第二块没有任何数据源——无论哪种，**修复路径都与 H2 相同**（补接成真级联，或补驱动第二组脚）。
- **假阴性风险**：H2 成立的前提是「HUB2 的 4 根数据脚确实来自另一组 MCU 脚」。若 HUB2 是硬件故障
  （虚焊/未装配/排线断），现象与 H2 完全相同。**§6 的 E1（互换两块）与 E4（示波器）就是为分辨这一点设计的。**

## 4. 「第二组数据脚从未被驱动」的机器级证据

从全帧 **512 项 BSRR 写序**里提取所有被置位或复位过的引脚：

```
出现过的引脚 = PG9 / PG10 / PG15 / PB6     ← 恰为 _22_1665_lines[4]（R1/G1/R2/G2）
候选第二组 = PB8 / PB9 / PE1 / PE2         ← 一次都没出现
```

源码侧同样成立：`_22_1665_lines[]` 只引用 `g_hub75_pin_r[0] / g_hub75_pin_g[0] /
g_hub75_pin_r[1] / g_hub75_pin_g[1]`（通道 0/1），**没有任何** `[2]`/`[3]` 引用。

引脚对照（`Platform/Src/pl_hub75.c` → `Core/Inc/main.h`）：

| 组 | 驱动线名 | MCU 脚 | 现行状态 |
|---|---|---|---|
| 第一组（通道 0/1） | R1 / G1 / R2 / G2 | **PG9 / PG10 / PG15 / PB6** | ✅ 现场第二十轮逐脚定标，每帧都在写 |
| 第二组（通道 2/3，**假设**） | R3 / G3 / R4 / G4 | PB8 / PB9 / PE1 / PE2（另有 B3=PE0 / B4=PE3） | ❌ 从未被写（HUB2 若走这组脚 ⇒ 必然全黑） |

> ⚠ 「第二组 = 通道 2/3」是**按兄弟驱动（1_263 / 22_1703 的 2 通道/模块）通道序推的假设**，
> 不是实测结论。**必须现场用通断档核到 HUB2 座的数据 pin**（§6 的 E5），不要照搬。

## 5. 现场 A/B 开关 `_22_1665_CHAIN_HEAD_IS_MODULE0` 的效果

机器级验证（`round26_two_hubs.py` §4）：开关只把「帧内哪 128 位归哪个模块」**对调**——
`=1` 时块 0（链首块）装**模块 0** = 第 1 行「1」、块 1 装模块 1「2」。

| 口径 | 单块接 HUB1（或真级联的链首） | HUB2 那块 |
|---|---|---|
| 默认（`=0`，现行） | 显示「2」 | **全黑** |
| `-D_22_1665_CHAIN_HEAD_IS_MODULE0=1` | 显示「1」（**对上"第一块显示 1"的期望**） | **仍全黑** |

⇒ flip 是「先让第一块内容对」的**现场开关**，**不是**双口问题的修复（它不增加任何被驱动的引脚）。
编译：`make -j8 DISP=22_1665` 时加 `-D_22_1665_CHAIN_HEAD_IS_MODULE0=1`；
EIDE 侧给 `defineList` 加同名宏（改完 `.eide/eide.yml` 需 `EIDE: Reload Project`）。

## 6. 最小修复方案（两条路径）与现场实验清单

### 6.1 达成「HUB1 出 1 / HUB2 出 2」的两条路径

| 路径 | 需要什么 | 固件改动 | 说明 |
|---|---|---|---|
| **P1 真级联**（推荐先试，零代码） | 两块模组能**串起来**（第一块有 OUT 座 / 面板自带级联线），第二块接到第一块的 OUT | **不需要**（只把 flip 开关置 1 让链首 = 模块 0） | 链首 = HUB1 那块 → 显「1」，链尾 = 第二块 → 显「2」，正好符合期望 |
| **P2 模型 B（每列一口）** | **HUB2 那 4 根数据脚的真实 MCU 脚位**（原理图 / 丝印 / 万用表通断实测） | 需要：`_22_1665_lines` 扩为「列 × 4 行」（8 行）、每帧时钟 = `128 × MODULE_ROWS`、每时钟把「列 c 的模块内容」写到第 c 组脚；`_22_1665_STATES` 变 256、`g_bsrr_tab` 增到 3 端口 × 256 态（CCM 预算另算） | 信息到位前**不改代码、不猜脚位** |

> 若 HUB2 与 HUB1 **并联改线**（跳线把两组脚接一起）：两块内容永远相同（都显「2」或都显「1」），
> **不能**达成「一块 1、一块 2」⇒ 并联不是可行路径。

### 6.2 现场实验清单（每次只改一件事，判读唯一）

前置：RTT 可见时先看开机横幅有没有 `[diag] display screen=16x32 code=2200001665 modules=1x2`
（有 = 板上是 1×2 镜像；无 = 旧镜像，先重烧）。

| # | 操作 | 预期 | 说明什么 |
|---|---|---|---|
| **E1** | 两块模组**互换 HUB 口**（原本黑的那块插到 HUB1） | 黑的那块在 HUB1 上显示「2」，原来出「2」的换到 HUB2 后变黑 | ⇒ 问题在**口/通路**，模组本身是好的。若黑的那块换到 HUB1 **依旧黑** ⇒ 模组/排线/供电问题，先查硬件 |
| **E2** | 单块接 **HUB2**，烧 1×1 口径（`MODULE_ROWS=1 / MODULE_COLS=1`） | 全黑 ⇒ HUB2 不是并联、也没有可用数据脚（H2 成立）；显示「1」 ⇒ 两口共用数据 | **一次判定两块口是不是同一组脚** |

| **E5** | 万用表通断档：从候选 MCU 脚（PB8/PB9/PE1/PE2，必要时加 PE0/PE3）量到 **HUB2 座的数据 pin** | 找出第二组 4 根脚的真实归属 | **这是 P2 唯一必需的硬件信息**（禁止照搬通道序假设） |

| **E7** | 1×1 口径 + 单块 HUB1，把默认文本临时改成「2」 | 显示「2」 | 排除「第二块模组/第二个数字本身有问题」 |
