**日期**：2026-09-17 晚
**本轮对象**：`Device/Display/dev_display_22_1665.c`（22-1665 16×16 红绿双色 / 静态单扫 / MBI5034B）
**用户输入**：① 第二组数据线的「引脚定义与 HUB75 顺序」**按兄弟模组驱动口径**取（不必回填 HUB2 实测脚位）；
② 现场 ETC 实测：`MODULE_ROWS=1 / MODULE_COLS=2`、单块模组接第一个 HUB 口、四川 ETC 逐行发
`"1234567890"` ⇒ **发第一行→「34」、第二行→空、第三行→「12」、第四~七行→空**。

**结论一句话**：
1. **ETC 七行现象已完全解释**（零剩余观测）：现行固件下，单块模组（链首 = 只留末 128 位）看到的是
   **逻辑屏下半（模块 1 区域 y16..31）**；七条观测的**唯一自洽组合 = 工具 0-based 行号**（「第一行」= 行号 0 = 全屏）

   （单行命令在 16px 宽屏上只可能出「12」或空，已证）。
2. **模型 B 已实现为默认**（`_22_1665_HUB_WIRING=2`）：每列模块（= 一个 HUB 口）各占一组 4 根数据脚，
   组 g 取**兄弟驱动通道序 2g / 2g+1** ⇒ 组 0 = R1/G1/R2/G2（PG9/PG10/PG15/PB6，现行那 4 根）、
   **组 1 = R3/G3/R4/G4（PB8/PB9/PE1/PE2）**；各组并行、每帧 **128 × MODULE_ROWS** 时钟。
   烧新固件后：**HUB1 显逻辑上半（默认画面「1」）、HUB2 显逻辑下半（「2」）**。
3. 模型 A（同线级联）保留为可编译开关（`-D_22_1665_HUB_WIRING=1`，= 第二十四/二十五轮现场取证形态，
   代码路径逐字节保留）；1×1 行为与旧驱动**逐字节一致**（宿主编译产物机器级对拍）。

## 1. §A 四川 ETC 七行现象逐行解释（位级 / 模拟证据）

### 1.1 源码事实（直接读源码，不猜）

| 项 | 源码口径 | 出处 |
|---|---|---|
| 单行行号 → 行索引 | `_sc_etc_render_line((uint8_t)(p->row - 1U), ...)` ⇒ **行号 r → y = (r-1)×16** | `app_sc_etc_proto_cmd.c` |
| 单行渲染参数 | 先 `dev_display_fill(0, row×16, screen_rows, 16, BLACK)` 清本行；再 `.y = row×16`、`.w = screen_rows`（= 16）、`.h = FONT_16`（= 16）、`word_wrap = false`、`h_align/v_align = ALIGN_LEFT_UP`、`FONT_16` | 同上 |
| 行号 0（全屏） | 先 `_sc_etc_clear_screen()`（整屏清黑）再 `word_wrap = true`、`.w = screen_rows`（16）、`.h = screen_cols`（32） | 同上 |
| 清屏语义 | 数据首字节 `0x20`（空格）⇒ 行号 0 清全屏 / 行号 n 清第 n 行，**不再渲染文本** | 同上 |
| 行号 7 | probe：`row > 6` → `PROTO_PROBE_FAKE`（不认领、不显示，帧被重同步跳过） | `app_sc_etc_proto.c` |
| 屏体几何 | 用户宏值 1×2 ⇒ 逻辑屏 **16 宽 × 32 高**（两块 16×16 上下叠放） | driver「一」节 |

**渲染层算术（`app_render.c::_render_text`）**：FONT_16 ASCII 字宽 = 16/2 = **8px** ⇒ 16px 宽屏
**每行最多 2 个字**；`word_wrap=false` 时超宽字形直接「跳过」（`char_pos++; continue;`）——
不会换行、也不会左移；`word_wrap=true` 时按 `w` 折行，且 `cur_y >= h` 即终止（不再画后续行）。

### 1.3 与现场七条观测的对照（哪种假设能复现？）

现场观测序列（发第一~七行）：`34 / 空 / 12 / 空 / 空 / 空 / 空`。
**可见区域固定 = 模块 1 区域（y16..31）**——旧固件（模型 A、1×2）单块模组是链首、只保留末 128 位，
由 round26 已现场判定（HUB1 显默认画面第 2 行「2」）。

| 假设 | 预测（七次观测的可见内容） | 命中 |
|---|---|---|
| H1 1-based 行号 + 不清屏（累积） | 空 / 12 / 12 / 12 / 12 / 12 / 12 | 1/7 |
| H2 1-based 行号 + 每次观测前清屏 | 空 / 12 / 空 / 空 / 空 / 空 / 空 | 4/7 |
| H3 0-based 行号 + 不清屏（累积） | 34 / 34 / 12 / 12 / 12 / 12 / 12 | 2/7 |
| **H4 0-based 行号 + 每次观测前清屏** | **34 / 空 / 12 / 空 / 空 / 空 / 空** | **7/7 ✔** |

**唯一自洽 = H4**：工具把「第一行」当 **行号 0**（协议里 0 = 全屏）发，且每次观测之间屏幕被清空
（工具连发清屏帧 / 人工清屏 / 复位）。逐条对应：

- 「第一行」→ 行号 0（全屏）：清屏 + 折行「12」「34」⇒ 单块（下半区域）显示 **「34」** ✔
- 「第二行」→ 行号 1（y 0..15，在上半区域）⇒ 单块（只看得见下半）**无显示** ✔
- 「第三行」→ 行号 2（y16..31，正在下半区域）⇒ **「12」** ✔
- 「第四~七行」→ 行号 3..6（y ≥ 32，整行在 32 行屏之外）⇒ **均无显示** ✔

**不可能性证明（机器级）**：行号 1~6 的单行命令在 16px 宽屏上**只可能出现「12」或空**
（`word_wrap=false` + `w=16` + 8px/字 ⇒ 只画前 2 字；行号 ≥3 整行越界 ⇒ 空）。
⇒ **任何观测到的「34」都不可能是行号 1~6 的单行帧**，必然来自行号 0（全屏）或滚屏帧。

> **与屏幕几何无关的既有口径问题（只记录、本轮不改 ETC 模块）**：ETC 单行行高硬编码
> `FONT_16`（16px），协议 6 行隐含屏高 ≥ 96px；16×32 台架上只有行 1~2 落在屏内，行 3~6 的
> fill/draw 全部越界（`dev_display_fill` 起点越界丢弃、`draw_bitmap` 交集裁剪），表现为
> 「发出去没反应」——属**几何上限**而非缺陷；16px 宽屏上「行」的可观测性天然只有 2 字窗口。
> 若要在该台架逐行验证：用**行号 0（全屏）**发「每行一段」的文本（换行按 16px 折行），
> 或换 ≥96px 高的屏。ETC 是测试工具，本轮**未改**（改动会影响其它屏）。

**复现**：`python3 .analysis/22_1665/round27_wiring_b_and_etc.py`（§A 段；32/32 全通过）。

### 2.2 引脚口径（指示 1 的取证结论）

| 组（HUB 口 / 模块列） | 线 0 上半红 | 线 1 上半绿 | 线 2 下半红 | 线 3 下半绿 | 说明 |
|---|---|---|---|---|---|
| **组 0**（HUB1） | R1 = **PG9** | G1 = **PG10** | R2 = **PG15** | G2 = **PB6** | 与现行第一组**逐脚一致**（现场第二十轮定标） |
| **组 1**（HUB2） | R3 = **PB8** | G3 = **PB9** | R4 = **PE1** | G4 = **PE2** | 兄弟驱动（1_263 / 22_1703）通道序 **2g / 2g+1** 的通道 2/3 R/G 脚 |

取证链（**不照抄假设，逐条从代码实证**）：

1. `Platform/Src/pl_hub75.c` 的 `g_hub75_pin_r[2]/g[2]/r[3]/g[3]` → `Core/Inc/main.h`：
   `HUB75_R3_Pin = PB8` / `HUB75_G3_Pin = PB9` / `HUB75_R4_Pin = PE1` / `HUB75_G4_Pin = PE2`。
2. ① **现行第一组与兄弟驱动前两通道口径一致**：兄弟驱动 `dev_display_22_1703.c` 的通道语义 =
   `TOTAL_CHANNELS = MODULE_COLS × 2`、`ch = y / ROWS_PER_CHANNEL`（通道随**垂直位置**递增），
   即**每列模块一对通道**；通道 0/1 = 第一列（= 现行第一组）✔。
   ② **第二组 = 通道 2/3**（本驱动按同序取 `2g`/`2g+1`）；1_263 / 22_1703 的端口分组表也把
   `ch2 = R3/G3/B3`、`ch3 = R4/G4/B4` 列为紧随其后的独立通道 ✔。
3. ③ **这些脚已被配成输出、无外设冲突**：`Core/Src/gpio.c`（CubeMX `MX_GPIO_Init`）把
   `HUB75_G2_Pin | HUB75_B2_Pin | HUB75_R3_Pin | HUB75_G3_Pin`（GPIOB）与
   `HUB75_G4_Pin | HUB75_B4_Pin | HUB75_R5_Pin | HUB75_G5_Pin | HUB75_B5_Pin | HUB75_B3_Pin | HUB75_R4_Pin`
   （GPIOE）配成 `GPIO_MODE_OUTPUT_PP`；GPIOE 上其余占用为 R5/G5/B5（数据）、DIP1/DIP2（PE7/PE8）、
   SW1~SW3（PE10~12）——**与 PB8/PB9/PE1/PE2 无冲突** ✔（B3 = PE0、B4 = PE3 本驱动不用）。
4. 本驱动**只用 R/G 两类脚**（双色屏无蓝 die）：组 1 只写 PB8/PB9/PE1/PE2 四根。

> ⚠ 组 1 的脚位是**按兄弟驱动通道序推得**（用户裁决口径），**未经万用表实测**；若烧新固件后
> HUB2 仍全黑而 HUB1 正常，则「HUB2 = 通道 2/3」这一条不成立（次候选 = 通道 4/5…），
> 换组只需改数据线表行号（`_22_1665_lines[1]` → `[2]`，或按实测脚位改表），代码零结构改动。

### 2.3 分组与帧结构

- **组数 = `MODULE_COLS`**（每列模块 / 每个 HUB 口一组）；组 g 占 HUB75 通道对 `2g` / `2g+1`。
- **组内模块数 = `MODULE_ROWS`**（横向模块同线级联；模型 B 下 1×2 时每组恰好 1 块）。
- **每帧时钟 = `128 × MODULE_ROWS`**（各组**并行**驱动、共享 CLK/LAT/OE；1×2 时 = **128**，模型 A 为 256）。
- **帧状态数组**：`state[组 g × CLOCKS + 时钟位 p]`，长度 = `128 × M`（与模型 A 相同 ⇒ CCM 结构不变）；
  每字节 bit j = **该组第 j 条线**在该时钟位的电平（4 位 / 16 状态，与模型 A 相同）。
- **链首口径**（`_22_1665_CHAIN_HEAD_IS_MODULE0`，默认 0）：模型 B 下表示**组内横向链首**
  （组内最后一块装末 128 位；`=1` 时组内第一块装末 128 位）——**`MODULE_ROWS=1` 时无影响**
  （每组只有一块，整块收满 128 位）。模型 A 下仍为整屏链首口径（原语义）。

### 2.4 合并写表与 scan 开销

- 模型 B：`g_bsrr_tab[组][端口槽 ≤2][16 状态]`；组 0 = {PG, PB}、组 1 = {PB, PE}
  ⇒ 每时钟 **4 次 BSRR 写**（组 0 两次 + 组 1 两次；PB 被两组各写一次，引脚互不重叠、无冲突）。
- 模型 A：保留原 `[端口槽 3][16]` + `g_bsrr_port_cnt`（每时钟 2 次写）。
- scan 热路径（`-Og` 反汇编实测，1×2）：**≈ 55 指令/时钟位**（含两组查表 + 4 次 BSRR 写 + 4×NOP
  建立裕量 + CLK 脉冲 + 循环开销）；每帧 128 时钟 ⇒ **≈ 7000 指令 ≈ 45~60µs**（TIM3 周期 500µs，
  余量 > 8×）。**相比模型 A 反而更省**（模型 A 1×2 = 256 时钟 × 33 指令 ≈ 8500 指令）。

### 2.5 CCMRAM 预算（新通式）

| 模型 | 通式 | 1×1 | 1×2 | 2×2 |
|---|---|---|---|---|
| **B（默认）** | **`1408·M + 256·MODULE_COLS`** | **1664B** | **3328B** | 6144B |
| A（开关） | `1408·M + 384`（原式） | 1792B | 3200B | 5888B |

- 实测（`arm-none-eabi-size -A` 驱动对象）：1×2 **3328B** ✔、1×1 **1664B** ✔（整项目重链差值法：
  1×1 = 39164 − 1664 = 37500 ✔；模型 A 1×2 = 39164 − 128 = 39036 ✔；2×2 = 6144 ✔）。
- 编译期守卫：`_Static_assert(_22_1665_CCM_BYTES ≤ 16384)` + 通道数守卫
  （模型 B：`2 × MODULE_COLS ≤ HUB75_CHANNEL_MAX = 10` ⇒ **MODULE_COLS ≤ 5**）+ 非法开关值守卫。
  竖排最大：模型 B `11×1`（CCM 15744B ✔）；模型 B `12×1` / `6×2` / `1×6` 均编译报错（可读 ASCII 断言）。

## 5. 遗留 / 待用户确认

1. **工具口径确认（ETC）**：现场那台工具发的是 **0-based 行号**（「第一行」= 行号 0 = 全屏）、
   且两次观测之间屏幕被清空？——本轮的解释（H4）依赖这两点；若工具其实是 1-based 且不清屏，
   则七条观测与固件模型无解（需再给一次「只发一行、不切换行号」的原始帧 hex 复核）。
2. **组 1 脚位**：PB8/PB9/PE1/PE2 是**按兄弟驱动通道序推得**（用户指示 1 的口径），未实测；
   现场 HUB2 若不出内容，请回填实测脚位（只改 `_22_1665_lines[1]` 行）。
3. **横向级联（`MODULE_ROWS ≥ 2`）**：组内多块模块同线级联的**顺序**（链首 = 行尾 / 行首）仍无现场证据，
   由 `_22_1665_CHAIN_HEAD_IS_MODULE0` 兜底（默认 0 = 组内最后一块收末 128 位，与模型 A 口径同构）。
4. **ETC 模块本身不改**（测试工具，见 §1.3 末尾的口径说明；`doc/01` §0.x 已记录）。
